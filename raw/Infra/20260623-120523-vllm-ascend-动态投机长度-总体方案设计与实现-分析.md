## 0. 执行摘要（TL;DR）

1. **目标**：运行时热切换投机长度（如并发变化时 3↔8，不重启服务），拿到两个收益——**减草稿前向耗时**（draft 循环少跑）+ **减 verify 耗时**（verify 总 token = `(1+k)×并发` 随 k 减少）。
2. **可行性（精度）**：✅ 高置信度。rejection sampler 原生支持 per-request 变长草稿（`num_draft_tokens` + `PLACEHOLDER_TOKEN_ID`），投机解码数学不变性与草稿数无关 → 输出逐 token 一致。
3. **性能（图模式）**：采用**分档 `uniform_decode_query_len`** 方案（路线 B）——按多个 `1+k` 值分别捕获 FULL decode 图，运行时按 k_active 选档，使 verify 真减 token 且图恒命中。
4. **性能（异步调度）**：✅ **实际兼容**（非理论）。异步占位机制本就用「每步实际草稿数」驱动，只需把 KV 预留与占位 list 上限喂 `K_max`，相邻步 k 不同天然正确。
5. **零同步**：✅ 关键路径无新增 D2H/H2D。`k_active` 是 CPU 整数、不读设备张量；接受核算复用现有 GPU 修正 kernel。
6. **解耦**：决策（`SpecLengthController` 新文件）与执行（≤6 处改动）分离，全在 vllm_ascend 层，启动期覆写 `num_speculative_tokens=K_max` 使框架自动按 K_max 预留 → 跟随上游成本极低。

> **顶层设计一句话**：预留 `K_max`（buffer/图/KV/占位全按 K_max 建），运行时 `k_active∈[1,K_max]` 只控制 worker 侧 draft 循环次数与 verify token 数；异步占位与精度核算本就用实际值驱动，天然兼容动态 k。

## 3. 兼容性机制一：图模式（拿 verify 减 token 收益的核心）

### 3.1 图桶的真相与分档方案

实测（[cudagraph_dispatcher.py:107](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/cudagraph_dispatcher.py)~[117](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/cudagraph_dispatcher.py)、[:211](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/cudagraph_dispatcher.py)~[230](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/cudagraph_dispatcher.py)）：

- FULL decode 图的 dispatch key 是 `BatchDescriptor`，字段只有 `num_tokens`/`num_reqs`/`uniform`（[forward_context.py:37](file:///Users/linyi/code/Documents/code/vllm/vllm/forward_context.py)~[43](file:///Users/linyi/code/Documents/code/vllm/vllm/forward_context.py)）——**无独立 query_len 字段**。投机长度按 `num_tokens=(1+k)×num_reqs` 间接编码。
- `num_reqs = num_tokens_padded // uniform_decode_query_len`，且 `assert num_tokens_padded % uniform_decode_query_len == 0`（[cudagraph_dispatcher.py:115](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/cudagraph_dispatcher.py)）——num_reqs 反推依赖 `uniform_decode_query_len`。

**两条路线对比**：

| 路线 | verify query | 图命中 | verify 减 token 收益 | 代价 |
|------|-------------|--------|---------------------|------|
| A：padding 到 K_max | 恒 `1+K_max` | ✅ 恒命中 | ❌ token 不减 | 多算 PLACEHOLDER 位 |
| **B：分档（推荐）** | 真实 `1+k_active` | ✅ 各档独立命中 | ✅ **token 真减** | 启动多捕获 K 档图 |

> **采纳路线 B**：用户明确要"减 verify token"，是硬需求。做法：启动期对每个常用 k（如 {2,3,5,8}）以 `uniform_decode_query_len=1+k` 各注册一轮 FULL decode 图 key（[initialize_cudagraph_keys](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/cudagraph_dispatcher.py)）；运行时 [uniform_decode 判定](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py) 用 `1+k_active` 命中对应档。代价是启动期多捕获 K 档图（一次性显存+时间，不进热路径）。

### 3.2 收益量化

- verify 计算量 ∝ `(1+k)×并发` → k 从 8 降 3，verify token 减约 55%。
- draft 前向次数 = k → 从 8 降 3，draft 耗时减约 62%。
- 加速比 = `平均接受长度 a(k) / (1 + k×draft_ratio + verify_ratio)`：k 减小省 token，但 `a(k)` 可能降 → **token 节省与接受长度的权衡正是第二阶段寻优的目标**。第一阶段只保证"设某个 k 能真减 token、不劣化、不掉图"。

### 3.3 待验证不确定点

路线 B 需 dispatcher 支持多档 `uniform_decode_query_len` 注册，而 FA3/DSA 的 scheduler_metadata 依赖 exact num_reqs（[cudagraph_dispatcher.py:201](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/cudagraph_dispatcher.py) 注释 "FULL mode needs exact num_reqs"）。**DSA backend 多档图能否正确命中 + 精度无损，是当前最大不确定点**，需 Phase 0 验证；若不通过则退路线 A（padding）。

## 4. 兼容性机制二：异步调度（实际兼容，非理论）

### 4.1 异步遮掩的本质

`execute_model` 把前向 launch 到 NPU 后**立即 `return None`**（[model_runner_v1.py:2315](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)~[2335](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)，注释 "without breaking async scheduling"）→ EngineCore 不等结果就排下一步 → 「下一步 CPU 调度/prepare」与「本步 NPU 前向」重叠。

**矛盾**：排下一步时上一步草稿没验完、接受长度未知。**解法**：用 `num_output_placeholders` 乐观占位，真实结果回来再修正。

### 4.2 异步"提前执行"用到的三个量（你问题的核心）

异步提前执行实际用"投机长度"的有三处，语义不同、对动态投机要求不同：

| 量 | 语义 | 是否依赖固定值 | 动态投机喂什么 |
|----|------|--------------|---------------|
| `num_output_placeholders` | 占位 token 计数 | ❌ **已用本步实际草稿数** | 不用管 |
| `_spec_token_placeholders`（占位 list） | 提前排下一步的草稿占位 | ⚠️ 按固定建，**但会被裁剪** | 建 K_max，运行时裁到 k_active |
| `num_lookahead_tokens` | KV slot 预留 | ✅ 固定 | 喂 K_max |

**证据**：
- placeholder 加：`cur_num_spec_tokens = len(spec_decode_tokens.get(req_id,()))`，`placeholder += num_sampled + cur_num_spec_tokens`（[async_scheduler.py:38](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/async_scheduler.py)）—— ★ 用本步实际草稿数，非常量。
- placeholder 减：`placeholder -= len(new_token_ids)`（[async_scheduler.py:63](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/async_scheduler.py)）—— 用实际产出。
- 占位 list 裁剪：`spec_token_ids[:num_scheduled_spec_tokens]`（[scheduler.py:550](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)）—— ★ 只要够长，多余裁掉 → 建 K_max 即可。
- 真实草稿回填：`update_draft_token_ids` 覆盖占位 list（[scheduler.py:1054](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)）—— worker 实际产出，长度 = k_active。

### 4.3 跨步切换的"实际兼容"走查（坐实）

场景：t 步 k=8、t+1 步切 k=3，逐步走真实代码：

| 步骤 | 代码行为 | 正确？ |
|------|---------|-------|
| t 步排程 | placeholder += 1+8（用实际 8）；占位 list [-1]*K_max 裁到 8 | ✅ |
| t 步 worker | draft range(8) 产 8 草稿；update_draft_token_ids 回填真实 8 | ✅ |
| 切 k=3 | latch_for_step() 在 t+1 步 schedule 开头锁存 k_active=3 | ✅ 边界生效 |
| t+1 步排程 | num_lookahead 按 K_max 预留 KV；placeholder += 1+3 | ✅ KV 够、占位用实际 3 |
| t 步结果回 | placeholder -= 实际产出；接受核算用 t 步实际 8（非本步 3） | ✅ |
| t+1 步 worker | draft range(3) 产 3 草稿 | ✅ |
| prev_num_draft_len | 存 t 步实际草稿数（[model_runner_v1.py:1971](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)），GPU 修正用 | ✅ |

> **核心论点**：placeholder 加/减、接受核算、prev_num_draft_len **全程用"那一步的实际草稿数"，从不假设各步草稿数相同**——这是 async 占位机制的固有能力（相邻步草稿数本就允许不同），不是为动态投机新增。所以 t 步 k=8、t+1 步 k=3 的混合步现有代码本就正确处理 → **实际兼容，非理论推断**。

### 4.4 不破坏遮掩的判断

遮掩比 = `min(CPU_prepare, NPU_forward)/total`。k_active 同时影响分子分母，但**不改 execute_model "launch 后立即返回"的结构** → 遮掩比不退化。切换只改"本步排几个草稿"这个 CPU 标量，不碰 `ExecuteModelState`/stream/event 体系。

## 5. 兼容性机制三：精度不变（输出逐 token 一致）

### 5.1 rejection sampler 原生支持变长草稿

- `metadata.num_draft_tokens`（[rejection_sampler.py:171](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py)）：**per-request list/tensor**，每 req 一个值 → 天然支持每 req 草稿数不同。
- `assert max_spec_len <= MAX_SPEC_LEN`（[rejection_sampler.py:119](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py)）：只要 `k_active ≤ K_max ≤ MAX_SPEC_LEN` 合法。
- `PLACEHOLDER_TOKEN_ID=-1`（[rejection_sampler.py:30](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py)）+ valid_mask（[:269](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py)）：无效/被拒位过滤。

### 5.2 数学不变性

投机解码的正确性保证：verify 阶段用目标模型 logits 做 rejection sampling，被接受 token 的分布严格等于目标模型直接采样——**与草稿数量无关**。草稿多/少只影响"猜几个"，每个被接受 token 都过了目标模型检验。接受核算（[scheduler.py:1477](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)）用本步实际 `num_draft_tokens`，k_active 变化自动适配 → **动态 k 不改变任何被接受 token 的概率分布** → 相同种子下输出逐 token 一致。

## 6. 零 CPU-NPU 同步（关键路径无新增 D2H/H2D）

### 6.1 现有去同步机制（必须沿用、不破坏）

async spec decode 的去同步设计（实测）：[CPU 乐观假设"全接受"、不等设备结果就排下一步，真实接受数在 GPU kernel 用上一步 `valid_sampled_token_count_gpu` 修正](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)（`update_num_computed_tokens_for_batch_change`，[:1051](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)~[1064](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)，`non_blocking=True`）；valid_sampled_token_count 走独立 stream + non_blocking + event（[:1627](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)）。**热路径无 D2H 同步。**

### 6.2 完整路径同步点盘查

| 环节 | 同步行为 | 新增同步？ |
|------|---------|-----------|
| 调度 latch k_active | CPU 整数（GIL 原子） | ❌ |
| draft 循环 range(k_active) | 读 CPU 整数 | ❌ |
| 占位 list 裁剪 | CPU list slice | ❌ |
| verify token 数 (1+k)×C | CPU 算 attn_metadata | ❌ |
| 图档选择 | dispatcher CPU 字典查 | ❌ |
| 接受核算 | 现有 GPU 修正 kernel non_blocking | ❌ 沿用 |

> **硬约束**：`k_active` 全程 CPU 整数、controller 决策**不读任何设备张量**（杜绝 `.item()/.cpu()/synchronize()`）；路线 B（分档）verify 真按 1+k_active 跑，**连 PLACEHOLDER host 填充都省了**，比路线 A 更零同步。唯一新增 host 操作（latch / 选档 / 读循环上界）均 O(1) 纳秒级，无锁竞争、无高耗时步骤。

## 7. 实现设计

### 7.1 SpecLengthController 接口契约（新文件 `vllm_ascend/spec_decode/spec_length_controller.py`）

```python
class SpecLengthController:
    """动态投机长度控制器（CPU 纯整数，进程级单例）。
    红线：所有方法 O(1)、不读设备张量、不触发同步。"""
    def __init__(self, k_max, k_init):
        assert 1 <= k_init <= k_max
        self._k_max = k_max; self._pending = k_init; self._latched = k_init
    def update(self, k) -> bool:            # 热切换入口；越界拒绝；只置 pending
        if not (1 <= k <= self._k_max): return False
        self._pending = k; return True
    def latch_for_step(self) -> int:        # 调度步边界锁存（防线1）
        self._latched = self._pending; return self._latched
    def get_active_len(self) -> int:        # 执行层每步读
        return self._latched
    def decide(self, signals) -> int:       # 第二阶段占位
        return self._pending
```

配置注入（仿 [XliteGraphConfig](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/ascend_config.py)）：`--additional-config '{"dynamic_spec_config":{"enabled":true,"k_max":8,"k_init":3}}'`。

## 8. 可靠性：长稳运行三防线

| 防线 | 风险 | 防护 |
|------|------|------|
| 1 边界锁存 | verify step 中途改 k → 状态错位/assert | latch_for_step 在 schedule() 开头锁存，本步不变 |
| 2 边界值校验 | k_active>K_max → buffer 越界 IndexError | update 强制 `1≤k≤K_max ≤ MAX_SPEC_LEN`（[rejection_sampler.py:119](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py)） |
| 3 跨步状态清理 | prev_num_draft_len 与新 k 不一致 → KeyError | **现有已防护**（[model_runner_v1.py:696](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)）；prev_num_draft_len 存实际值，切换天然安全 |

额外：切换加最小驻留 hysteresis 防图档抖动；K_max 取保守上限（≤8）防显存；buffer 一次性 `__init__` 预分配（[llm_base_proposer.py:208](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/spec_decode/llm_base_proposer.py)），无运行时分配。

## 9. 分阶段交付与验收

### Phase 0：基线 + 命门验证（1 周）
- msprof 实测固定 k=3/5/8 的 TPOT、graph_hit_rate、d2h_sync_count、accept_len、KV 占用。
- **验证核心不确定点**：DSA backend 多档 query_len 图能否正确命中 + 精度无损（§3.3）。不通过则退路线 A。

### Phase 1：静态预留 + 手动热切换（2-3 周）
- 实现 Controller + config + dispatcher 多档 + 三执行层 + 热切换 API。
- **验收红线**：① 动态 k_active=3 vs 固定 k=3，相同并发/数据 TPOT 持平（±2%）；② 减小 k 时 verify token 真减（拿到收益）；③ 3↔8 热切换不重启、不报错、**输出 token 比特级一致**（贪心对拍）；④ graph_hit_rate→1.0、无 capture miss；⑤ **热路径 d2h_sync_count 不增**；⑥ async 遮掩比持平；⑦ 高频切换 1h 长稳无 OOM/assert。

### Phase 2（占位）
- `SpecLengthController.decide(signals)` 自动寻优：按并发/上下文/实时 accept_len 选最优 k_active，最大化加速比（token 节省 vs 接受长度的权衡，§3.2）。
