## 〇、核心方法与总结论

**方法**：把投机长度敏感变量分两类——
- **静态类**（`num_spec` = `num_speculative_tokens`，最大投机长度）：用于 buffer 预分配/ACL Graph 捕获，是**容量上界**。
- **动态类**（`num_decode_draft_tokens` / `num_spec_decodes` / 真实 uql）：当前 step 实际值。

**精度风险 = "本应用动态值的地方用了静态 num_spec" 或 "静态/动态混用导致 stride/布局不一致"**。

**总结论（已坐实的关键风险位置，按风险排序）**：

| # | 位置 | 变量 | 风险 | 状态 |
|---|------|------|------|------|
| **R1** | ascend `gdn.py` ACL Graph conv1d padding | `spec_q_per_seq = size(-1) = num_spec+1`（静态） | 🔴 graph 按静态投机长度 pad，动态 uql 时 token 布局错位 | ✅ 坐实 |
| **R2** | `gdn_attn.py` spec_state_indices 列宽 | `: num_spec+1`（静态） | 🟠 列宽恒为最大值，配合 stride 计算需一致 | ✅ 坐实 |
| **R3** | `qwen_gdn` conv1d `max_query_len` | `spec_state_indices_tensor.size(-1) = num_spec+1` | 🟠 conv kernel 用静态 max_query_len | ✅ 坐实 |
| **R4** | mamba_utils align kernel | `num_draft`（动态）+ `block_size` 对齐 | 🟡 跨 step 切换对齐截断（前篇存疑 A） | ✅ 坐实变量、风险待动态验证 |
| **R5** | ascend attention `decode_threshold` | `num_speculative_tokens`（静态） | 🟡 reorder 阈值用静态，动态下是否需调 | ✅ 坐实 |

## 一、R1（🔴 最高）：ACL Graph conv1d padding 用静态投机长度

### 1.1 代码事实

`vllm_ascend/ops/gdn.py` 的 ACL Graph（cudagraph）conv1d host 参数 padding：
```python
# :439-443
# Query length per spec request during capture (= num_spec + 1).
spec_q_per_seq = int(attn_metadata.spec_state_indices_tensor.size(-1))  # = num_spec + 1（静态）
# 传给 padding 函数当 q_per_seq（:460）
```
padding 逻辑（`_pad_conv1d_host_args_to_capture`）：
```python
pad_tokens = cap_x_dim0 - runtime_qsl_last          # cap_x_dim0 = 捕获时 mixed_qkv.shape[0]
pad_seqs = pad_tokens // q_per_seq                  # :132  用 q_per_seq=num_spec+1 算 padding 序列数
extra_qsl = (runtime_qsl_last + (i+1)*q_per_seq ...)# :136  每个 dummy req 步长 = q_per_seq
```

### 1.2 风险理论（基于代码）

- ACL Graph 捕获时 `cap_x_dim0 = mixed_qkv.shape[0]`（:206）—— 按**捕获时的投机长度**（注释明示 = num_spec+1）记录的 token 总数。
- `q_per_seq` 固定取 `spec_state_indices_tensor.size(-1) = num_spec+1`（:443，静态）。
- **若运行时实际投机长度 < num_spec**（动态投机 mtp1）：runtime 的 `qsl_host` 按真实 uql=2 排布，但 `q_per_seq` 仍是 4，`pad_seqs = pad_tokens // 4`、`extra_qsl` 步长 4——**padding 出来的 dummy req 的 token 边界与 runtime 真实 uql=2 的边界不一致** → conv1d kernel 读的 `query_start_loc` / `cache_indices` 错位 → conv_state 取错块 → 精度异常。

> **判断**：这是**有代码依据的、动态投机特有的精度风险**。`spec_q_per_seq` 写死 `size(-1)=num_spec+1`（注释自己标 "during capture"），ACL Graph 一旦在某投机长度捕获、运行时切到另一长度，padding 对齐就错。**这与"问题 A（ssm 索引）"是不同的独立点——这里是 conv1d 的 ACL Graph padding。**

### 1.3 修改建议

- `spec_q_per_seq` 应取**当前 step 真实 uql**，而非 `size(-1)`（静态）；或
- **动态投机长度变化时重新捕获/选择对应 q_per_seq 的 graph**（按投机长度分桶捕获）；或
- 若 ACL Graph 必须固定 shape，则**动态投机长度时禁用 conv1d 的 graph 捕获**，走 eager。

## 二、R2/R3（🟠）：spec_state_indices 列宽 + max_query_len 用静态 num_spec+1

### 2.1 代码事实

```python
# gdn_attn.py:107  静态最大投机长度
self.num_spec = self.speculative_config.num_speculative_tokens
# gdn_attn.py 多处：spec_state_indices 列宽 = num_spec+1
spec_state_indices_tensor = block_table_tensor[spec_sequence_masks_cpu, : self.num_spec + 1]
# qwen_gdn:1355  conv1d 的 max_query_len 用静态列宽
max_query_len=spec_state_indices_tensor.size(-1)   # = num_spec+1
```

### 2.2 风险理论

- 列宽恒为 `num_spec+1` 本身是**容量预留，合理**（GPU 也这样，靠 stride 寻址）。
- 风险在**消费侧**：kernel 用 `num_accepted-1` 当列偏移、用 stride 跳行。**只要 stride = 列宽 = num_spec+1 且 num_accepted ≤ num_spec+1，就正确**（GPU 实测如此，见前篇）。
- **Ascend 侧风险**：若 ascend kernel 的 stride 计算用了"动态推导"（如 `len/B`）而非 `num_spec+1`，cudagraph padding 下会与列宽不一致（前篇 ③-C）。

> **判断**：R2/R3 本身设计合理，**风险在 ascend kernel 消费时 stride 与列宽是否严格一致**。GPU 用张量真实 stride(0) 保证一致；ascend 需确认。

## 三、R4（🟡）：align kernel 的 num_draft + block_size 对齐

### 3.1 代码事实

```python
# mamba_utils.py:80-93  align 模式 state 提交
num_draft = tl.load(num_draft_tokens_ptr + req_idx)        # 当前 step 动态值（:80）
num_tokens_running_state = num_computed + num_scheduled - num_draft  # :82
new_num_computed = num_tokens_running_state + num_accepted - 1       # :83
aligned_new_computed = (new_num_computed // block_size) * block_size # :84  block 对齐截断
dest_block_idx = aligned_new_computed // block_size - 1              # :93
```

### 3.2 风险

`num_draft` 是动态值（正确），但 `// block_size` 对齐截断在跨 step 投机长度切换时，`aligned_new_computed` 是否落到与上一步 state 物理布局一致的 block——**前篇存疑 A，需动态数值追踪坐实，静态走读不下定论**。

## 四、R5（🟡）：ascend attention decode_threshold 用静态 num_spec

### 4.1 代码事实

```python
# attention_v1.py:245-246（dsa_v1.py:385 / mla_v1.py:263 / sfa_v1.py:200 同模式）
spec_token_num = self.speculative_config.num_speculative_tokens   # 静态
self.decode_threshold += spec_token_num   # reorder_batch 阈值
```

### 4.2 风险

`decode_threshold` 决定哪些请求算 decode（参与投机重排）。用静态 `num_spec`——动态投机下实际 uql < num_spec 时，阈值偏大。**理论上偏大不会漏判 decode（仍 ≥ 实际 uql），风险较低**，但若动态长度逻辑依赖精确阈值则需复核。

> **判断**：R5 用静态值偏保守，**大概率不是精度 bug 源**，列出供完整性核对。

## 六、最终判断与建议

### 6.1 最可能的精度根因（已坐实代码）

> **R1（ACL Graph conv1d 的 `spec_q_per_seq` 写死 num_spec+1）是本次普查中唯一"静态投机长度 + 直接影响 token 布局"的明确风险**，且：
> - 是 conv1d 路径（问题 A 文档没碰）；
> - 是 ACL Graph 路径（动态长度 + graph 固定 shape 的典型冲突）；
> - 注释自己写明 "= num_spec + 1 during capture"——**捕获用静态、运行时若变长就错**。

**这与前篇 conv1d 窗口滚动（③-A）、问题 A（ssm 索引）共同构成"修了一个仍异常"的多 bug 叠加。**

### 6.2 修改建议优先级

| 优先级 | 改动 | 位置 |
|--------|------|------|
| 🔴 P0 | `spec_q_per_seq` 用真实 uql / 按投机长度分桶捕获 graph / 动态长度禁 graph | ascend gdn.py:443 |
| 🟠 P1 | 确认 ascend kernel stride 严格 = num_spec+1（不用 len/B） | ascend kernel |
| 🟠 P1 | conv1d 窗口滚动 + NULL 守卫（前篇 ③-A/③-B） | ascend conv1d op |
| 🟡 P2 | align kernel block 对齐跨 step 验证（R4/存疑A） | mamba_utils.py:84 |

### 6.3 验证

1. **ACL Graph on/off 对比**：若 off 正常、on 异常 → 坐实 R1（graph padding）。
2. **固定投机长度 vs 动态切换**：固定 mtp3 正常、mtp3↔mtp1 异常 → 坐实"静态 q_per_seq vs 动态 uql"。
3. **conv vs ssm 分离**：定位是 conv1d（R1/R3/③-A）还是 ssm（问题 A）。

## 七、待核实/存疑

1. **R1 的 graph 捕获策略**：ascend 是否按投机长度分桶捕获多套 graph，还是单 graph——决定 R1 是否已被规避。需读 ACL Graph 捕获调度。
2. **num_accepted_tokens 跨 step 归属**（R4 关联）：当前 step 真实值 vs 上一步残留，需 worker 侧确认。
3. **ascend kernel stride 实际计算方式**（R2）：用 num_spec+1 还是 len/B——服务器侧 AscendC，本地无法读。
4. **decode_threshold 动态长度下是否需调**（R5）：理论偏保守，但需确认动态逻辑不依赖精确阈值。
