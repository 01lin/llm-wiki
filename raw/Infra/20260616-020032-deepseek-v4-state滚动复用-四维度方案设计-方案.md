# P1-a「Compressor state 准入优化」四维度方案设计

> 日期：2026-06-16
> 基于：[P1-a 代码确认与方案校准](20260616-015038-deepseek-v4-state滚动复用-代码确认与方案校准-分析.md)（已证伪"虚高"定性、标注算子可行性待证）
> 本文按四维度展开：① 最大收益 ② 涉及开发面 ③ 实现设计+伪代码+改动建议 ④ 业界对标

## 0. 前置：P1-a 的精确定义（校准后）

> 原方案"state 滚动复用消除虚高"的表述已被证伪。**校准后的 P1-a 精确目标**：
> **降低 Compressor state 组在 prefill chunk 期间的准入峰值块数**——当前为 `cdiv(sliding_window-1 + max_num_batched_tokens, block_size)+1`（O(chunk)，代码 `kv_cache_interface.py:502`），目标降到接近 O(state_window=8/128)。

---

## 1. 维度一：最大收益

### 1.1 收益量纲（实测口径，13.30 GiB KV 池）

| 项 | 当前（chunk=4096） | P1-a 理想（state O(8/128)） | 来源 |
|----|-------------------|---------------------------|------|
| C4 state 准入块/请求 | `cdiv(7+4096,8)+1 ≈ 514` | `cdiv(8,8)+1 = 2` | `kv_cache_interface.py:502` 公式 |
| C128 state 准入块/请求 | `cdiv(127+4096,32)+1 ≈ 133` | `cdiv(128,32)+1 = 5` | 同上 |
| 104K 单请求准入峰值 | 926 块 = 2.90 GiB | ~419 块 = 1.31 GiB | 实测场景计算 |
| **13.3GiB 池 104K 准入并发** | **4** | **~10** | num_blocks/准入 |

> **最大收益**：104K 上下文准入峰值 **-55%（2.90→1.31 GiB）**，准入并发 **4→~10（2.5×）**。这直接松绑实测发现的"capacity 排队 16"——准入并发从 4 提到 10，排队请求大幅减少。

### 1.2 ⚠️ 收益前提（未证实，见维度三）

> 该收益**完全依赖**"中间 chunk 的 state 不落持久 cache、只留边界"能否实现。代码核查显示**算子当前必写 state**（§3.1），所以这个收益**是"若算子改造成功后"的上界，不是当前可兑现值**。

## 2. 维度二：涉及的开发面（代码核查后的真实清单）

| 层 | 模块 | 改动 | 难度 | 依据 |
|----|------|------|------|------|
| **算子 kernel** | `csrc/attention/compressor/op_kernel/` | **核心障碍**：新增"中间 state 不写持久 cache"模式 | **高** | CACHE_MODE 当前仅 CONTINUOUS/CYCLE，都写 state（`compressor_comm.h:93`） |
| **算子 host** | `csrc/attention/compressor/op_host/compressor_def.cpp` | 扩 `cache_mode` Attr 取值 / 新增 scratch 输出 | 中 | `:98 cache_mode` Attr |
| **算子 tiling** | `compressor_tiling.cpp` (arch32/35) | 新模式的 tiling key | 中 | `compressor_template_tiling_key.h:37` |
| **attention 元数据** | `vllm_ascend/attention/dsa_v1.py` | state slot_mapping 只为边界 token 分配持久 slot；调用算子时传新 cache_mode | 中 | `:2058 compressor` 调用 |
| **准入 cap** | `vllm_ascend/core/single_type_kv_cache_manager.py` | state 组 `max_admission_blocks_per_request` 从 O(chunk) 改 O(state_window) | 低 | `:279` 分支 |
| **调度器** | `vllm/v1/core/sched/scheduler.py` | 配合新准入 cap（多数自动生效） | 低 | — |

> **关键结论**：P1-a **必然涉及 Ascend C++ 算子改动**（不是纯框架优化）。这是 §3.1 钉死的——当前无任何 cache_mode 支持"不写 state"。

## 3. 维度三：实现设计 + 伪代码 + 改动建议

### 3.1 算子现状（代码钉死，决定设计起点）

```cpp
// csrc/attention/compressor/op_kernel/arch35/compressor_comm.h:93
enum class CACHE_MODE : std::uint8_t {
    CONTINUOUS = 1,   // state 连续地址写入
    CYCLE = 2         // state 循环/环形写入
};
// 两个 mode 在 kernel 里都调 WriteToCacheState (compressor_block_vec.h:134/779)
// → 当前没有"不写 state"的模式
```

算子签名（`compressor_def.cpp:40/65/89`）：
```
Input:  state_cache (block_num, block_size, 2*coff*D)
        state_block_table (B, sMax/block_size)
Output: cmp_kv, state_cache (in-place 读写)
Attr:   cache_mode (OPTIONAL, 当前默认 1=CONTINUOUS)
```

> **⚠️ 待确认项（不推测）**：`CYCLE` 模式语义是"循环/环形复用"——它**是否已经在做"只保留最近 state 窗口"的环形 buffer**？若是，P1-a 可能可复用 CYCLE 模式 + 缩小 state cache 物理尺寸，而非新增模式。**这需要读 `compressor_block_vec.h:796/841` 的 CYCLE 分支实现确认**，本文未深入到该层，标注为**方案第一步必须先确认的前置**。

### 3.2 实现设计（两个分支，取决于 §3.1 待确认项）

**分支 A（若 CYCLE 已是环形复用）— 优先验证，改动小：**
```
1. 确认 CYCLE 模式：state cache 物理只需 O(state_window) 个 slot（环形覆盖）
2. 元数据层：C4/C128 state 的 state_block_table 只分配 O(state_window) 个 block
3. 准入 cap：state 组改用 O(state_window) 公式
→ 不改 kernel，只改 metadata + 准入 cap（难度：中）
```

**分支 B（若 CYCLE 也按 chunk 写持久）— 需改算子，难度高：**
```
1. 新增 CACHE_MODE::SCRATCH=3：中间 state 写 UB/L1 scratch，不落 GM 持久 cache
2. 仅在 chunk 末尾（边界 token）用 CONTINUOUS 写一次持久 state
3. kernel WriteToCacheState 增加 scratch 分支
→ 改 kernel + tiling + host def（难度：高）
```

### 3.3 伪代码（分支 A，metadata + 准入层）

```python
# vllm_ascend/core/single_type_kv_cache_manager.py
# 当前 (:279 分支): state 组用 O(chunk) cap
# 改为: state 组用 O(state_window) cap（前提：CYCLE 环形复用，物理 cache 只需窗口大小）
elif isinstance(kv_cache_spec, SlidingWindowMLASpec):
    # state cache 是环形复用的（CYCLE mode），物理只需 state_window 个 slot
    state_window = kv_cache_spec.sliding_window  # 8 (C4) / 128 (C128)
    kwargs["max_admission_blocks_per_request"] = cdiv(state_window, block_size) + 1
    #   原: kv_cache_spec.max_admission_blocks_per_request(max_num_batched_tokens, max_model_len)
```

```python
# vllm_ascend/attention/dsa_v1.py  state 的 block_table 构造
# 当前: state_block_table 覆盖 chunk 内所有 token 的 state slot
# 改为: 只分配 state_window 个 block，依赖 CYCLE 环形寻址
def _build_state_metadata(self, ...):
    # state cache 环形：第 i 个 token 的 state 写到 (i % state_window) slot
    num_state_blocks = cdiv(state_window, self.block_size)  # 而非 cdiv(chunk, ...)
    state_block_table = allocate_blocks(num_state_blocks)   # 大幅减少
    ...
```

> **改动建议的边界**：以上伪代码**成立的前提是 §3.1 待确认项为"CYCLE 已环形复用"**。若不成立（分支 B），则需先做算子改动，伪代码不适用。**本方案不假设前提成立——第一步必须先读 CYCLE kernel 分支确认。**

### 3.4 更稳妥的替代（无需算子改动，立即可拿——推荐先做）

> 在算子可行性确认前，**P0-2 调小 chunk 是 P1-a 收益的安全子集**，代码已支持、实测已验证：

```bash
# 实测脚本已在用 8192→4096，进一步可分队列：
# 长会话队列: max-num-batched-tokens=2048
#   → C4 state 准入 cdiv(7+2048,8)+1 ≈ 258 (vs 4096 的 514，已减半)
```
- chunk 4096→2048：state 准入块再降 ~50%，**零开发、零算子风险**。
- 这是 P1-a 目标的"安全子集"——不依赖任何未证实假设。

## 4. 维度四：业界对标（SGLang / TensorRT-LLM / DeepSeek）

### 4.1 业界对"压缩状态 + chunked prefill 内存"的处理

| 框架 | 做法 | 对 P1-a 的参照 |
|------|------|--------------|
| **TensorRT-LLM** | kvCacheManager 支持 **indexer K cache**，专门 PR 让 DSA"prefill 时把过去 token 存 cache"从而解锁 chunked prefill + KV reuse | 业界把压缩/索引状态作为**一类受管 cache**，与 chunked prefill 协同——印证 P1-a 方向（state 也要被准入精确管理） |
| **SGLang** | 两级内存池（ReqToTokenPool + TokenToKVPool）+ **专门的 indexer key/key_scale cache buffer**；admission 靠 `--mem-fraction-static` / `--max-running-requests` | SGLang 把 indexer 状态单独 buffer 化（类似 DeepSeek scratch 概念）——参照 P1-a 可把 state 独立管理 |
| **vLLM/SARATHI** | chunked prefill **不解决内存**（"32K 请求按 2K chunk 仍预留 32K KV"） | 业界共识：chunked prefill 是调度优化，内存要单独治理——**正是 P1-a 要补的**（state 准入 O(chunk) 是这个共识的具体表现） |

### 4.2 业界没有直接对应方案（P1-a 是相对前沿点）

> 搜索未命中"Compressor state chunk 内 scratch 复用"的业界专门方案。原因：
> - DeepSeek-V4 的 CSA+HCA hybrid（2026-04 发布）是新架构，NVIDIA 报 **KV 内存 -90%**，但公开资料聚焦"压缩主 KV + indexer"，**Compressor state 的准入管理是各框架自己处理的实现细节**。
> - SGLang/TRT-LLM 的公开实践集中在 **indexer K cache** 和 **主压缩 KV**，未见专门优化 **Compressor state 准入峰值**——说明 P1-a 是 vLLM-Ascend 路径上相对独特的点（也可能是其他框架用了不同的 state 管理方式规避了这个问题，需进一步调研）。

### 4.3 可借鉴的工程模式

1. **TRT-LLM 的 indexer K cache 受管模式**：把 state 作为 kvCacheManager 的一类受管 cache，与 chunked prefill 显式协同——比当前 vLLM-Ascend 的"state 也走 SlidingWindow 准入"更精细。
2. **SGLang 的独立 buffer**：state 单独 buffer 化，准入与主 KV 解耦。
3. **业界一致信号**：chunked prefill 的内存问题需单独治理——支撑 P1-a 的必要性，但具体到 Compressor state，**需要 vLLM-Ascend 自己实现**（无现成抄）。

## 5. 一页纸总结

| 维度 | 结论 |
|------|------|
| **最大收益** | 104K 准入峰值 -55%（2.90→1.31GiB），准入并发 4→~10（**前提：算子可行**） |
| **涉及开发** | **必然涉及 Ascend C++ 算子**（CACHE_MODE 当前都写 state）+ 元数据 + 准入 cap |
| **第一步** | **先读 CYCLE 模式 kernel 分支**（`compressor_block_vec.h:796/841`）确认是否已环形复用——决定走分支 A（改 metadata，中）还是 B（改 kernel，高） |
| **安全子集** | **P0-2 调小 chunk（4096→2048）**：state 准入再降 50%，零开发零算子风险，**推荐先做** |
| **业界对标** | TRT-LLM indexer K cache 受管 / SGLang 独立 buffer 可借鉴；但 **Compressor state 准入优化无现成方案，需自研** |
| **诚实标注** | 收益上界依赖未证实的算子可行性；CYCLE 语义需先确认；不推测算子内部行为 |
