## 问题一：RadixCache 提命中率的技术点（不止 token 级粒度）

> 先纠一个常见简化：**RadixCache 并非纯 token 级**。KV 物理存储也是 page 对齐的（`page_aligned`，[radix_cache.py:133](sglang/python/sglang/srt/mem_cache/radix_cache.py)），只是**前缀匹配可以做到 page 粒度的最长匹配**，比 vLLM 的"整 block hash 命中"更细。除此之外，还有下列提命中率手段：

### 1. cache_unfinished_req —— 请求未结束即插树（多轮命中的最大抓手）

`cache_unfinished_req`（[radix_cache.py:493](sglang/python/sglang/srt/mem_cache/radix_cache.py)）：请求**还在跑（没结束）**就把已算出的 KV indices 插进树：
```python
values = kv_indices[: len(radix_key)].to(dtype=torch.int64, copy=True)   # :507 附近
result = self.insert(InsertParams(key=..., value=values, chunked=chunked))
```
**意义**：多轮交互里，上一轮的 KV 不必等整个会话结束，本轮一产出就进树，下一轮请求立即可命中。这是"多轮命中率"区别于一次性请求的核心——vLLM 也有 cache_blocks，但 SGLang 的树插入是连续的、自然形成共享父节点。

### 2. 自动节点分裂 —— 公共前缀天然抽取为共享父节点

`_insert_helper`（radix_cache.py:709）：插入新序列时，若与已有边有公共前缀，**自动分裂节点**，公共部分变父节点、分叉部分变子节点。
**意义**：N 个请求只要有公共前缀，树结构自动让它们共享同一父节点的 KV——多用户共享 system prompt、agent 多分支探索（同一前缀走不同后续）天然高命中。vLLM 的 hash 表是平铺的，公共前缀靠 hash 链一致性隐式命中，但没有"分支共享"的结构表达。

### 3. page_aligned 匹配 —— 比整块 hash 更细的对齐命中

`RadixKey.page_aligned`（radix_cache.py:133）+ `match(page_size)`（:159）：匹配长度按 page_size 向下取整（`(matched // page_size) * page_size`，:188）。
**意义**：page_size 可以设得比 vLLM 默认 block（16/128）更小（甚至 page_size=1 纯 token 级，:134），**命中边界更贴近真实公共前缀长度**，减少"不足一块命中不了"的损失。这是"提高命中长度"的直接来源。

### 4. extra_key 命名空间 —— 隔离的同时不误伤命中

`RadixKey.extra_key`（radix_cache.py:60/72）+ `child_key` 按 extra_key 命名空间（:195）：会话/租户/lora 用 extra_key 隔离，**同租户内仍能充分命中**。隔离做在 key 命名空间而非整棵树拆分，省内存又不漏命中。

### 5. bigram 视图 —— 特定场景的匹配优化

`is_bigram`（radix_cache.py:58/66/74）：token_ids 持有 N+1 raw token、提供 N 个 bigram 的视图，相邻切片共享边界 token。
**意义**：bigram 粒度匹配用于某些需要二元组对齐的场景（如特定 tokenizer/投机解码的对齐），是匹配灵活性的扩展。⚠️ 具体启用场景本次未深挖，标注存在。

### 6. HiRadix 分层命中 —— 命中范围扩到 host/远端

`HiRadixCache.match_prefix`（hiradix_cache.py:1438）覆盖 device→host→storage 三级 + `prefetch_from_storage`（:1471）。
**意义**：device 没命中的，能命中到 host/远端冷层（前篇已述）——**等效扩大了"可命中的 KV 总量"**，超长上下文下显存外溢后仍能复用。

### 7. priority-aware eviction —— 保护高价值前缀不被驱逐

`TreeNode.priority`（radix_cache.py:248 附近）+ `lock_ref`（:232）：驱逐时按 LRU + priority，高优先级/在用节点受保护。
**意义**：命中率不只看"能不能匹配"，还看"匹配的 KV 还在不在"。优先级驱逐让热门前缀（如公共 system prompt）不被冷请求挤掉，**间接保命中率**。

### 小结（问题一）

| 技术点 | 提命中率机理 |
|--------|-------------|
| token 级 / page_aligned 匹配 | 命中长度更贴近真实前缀（减边界损失） |
| **cache_unfinished_req** | 多轮：本轮 KV 即时进树，下轮立即可命中 |
| **自动节点分裂** | 公共前缀/多分支天然共享 |
| extra_key 命名空间 | 隔离但不误伤命中 |
| HiRadix 三级分层命中 | 扩大可命中 KV 总量（host/远端） |
| priority 驱逐 | 保护高价值前缀，间接保命中 |

> **判断**：token 级粒度只是其一。**多轮场景真正的命中率优势来自 cache_unfinished_req（即时进树）+ 自动分裂（分支共享）**，超长上下文则靠 HiRadix 分层把"可命中范围"从 HBM 扩到 host/远端。

## 问题二：相同序列长度，Radix 树显存开销是否更大？

> **直觉答案"树更费显存"是错的。** 必须把显存拆成两块：**(A) KV 张量本体**（大头，GB 级）和 **(B) 管理元数据**（小头，MB 级甚至更小）。代码坐实如下。

### 2.1 关键事实：Radix 树不持有 KV 本体，只持有索引

`TreeNode.value` 是 `Optional[torch.Tensor]`（[radix_cache.py:231](sglang/python/sglang/srt/mem_cache/radix_cache.py)），但内容是 **int64 的 KV 索引数组**（kv_indices），不是 KV 张量本体：
```python
values = kv_indices[: len(radix_key)].to(dtype=torch.int64, copy=True)  # cache_unfinished_req
node.value = values   # 存的是索引，指向 token_to_kv_pool
```
真正的 KV 显存在 **`ReqToTokenPool` / `token_to_kv_pool`**（[memory_pool.py:229](sglang/python/sglang/srt/mem_cache/memory_pool.py)）——一个预分配的大张量池。

vLLM 同理：`KVCacheBlock`（[kv_cache_utils.py:117](vllm/vllm/v1/core/kv_cache_utils.py)）只是元数据（block_id / ref_cnt / _block_hash / free 链表指针），KV 本体在独立的 KV 张量池。

> **结论先行**：**(A) KV 张量本体两边完全相同**——都是预分配 page 池、按需占用，相同序列长度 = 相同 token 数 = 相同 KV 占用。显存大头不存在差异。差异只在 (B) 管理元数据，且这部分基本不在 KV 显存账上。

### 2.2 (B) 管理元数据开销对比

| | vLLM block+hash | SGLang Radix 树 |
|---|----------------|-----------------|
| 元数据单元 | `KVCacheBlock`（每 block 一个） | `TreeNode`（每条树边一个） |
| 单元内容 | block_id, ref_cnt, hash(32B), prev/next 指针 | children dict, parent, key, value(索引张量), lock_ref, last_access, host_value, hash_value, priority |
| 单元数量 | ≈ 总 token / block_size | ≈ 不同前缀的边数（共享前缀合并，通常 < block 数） |
| 单元体积 | 小（几个标量 + 32B hash） | **较大**（dict + 多字段 + 索引张量） |
| 存放位置 | **host 内存（Python 对象）** | **host 内存（Python 对象）** |

**两个关键点**：
1. **元数据在 host 内存，不占 HBM**。TreeNode、KVCacheBlock 都是 Python 对象，在 CPU 侧。**所以"树 vs 块"的元数据差异不消耗 GPU/NPU 显存**——这是问题的核心，常被误判。
2. **单元数量上 Radix 树往往更少**：因为公共前缀合并成一条边（一个 node），而 vLLM 每个物理 block 都有一个 KVCacheBlock 对象。高共享场景树的 node 数 < block 数。

### 2.3 真正影响 KV 显存(HBM)占用的是"碎片/浪费"，不是数据结构

相同序列长度下，HBM 上 KV 占用的差异来自**对齐浪费**，不是树/表本身：

| 浪费来源 | vLLM | SGLang |
|---------|------|--------|
| 尾部不满块 | block_size 对齐，最后不满一块按整块占（如 block=128，序列 130 token 占 2 块=256 槽，浪费 126） | page_size 对齐，同理有尾部浪费，但 **page_size 可设更小**（甚至 1） |
| 前缀复用粒度 | block 对齐，不足一块的公共前缀复用不了 → 重复占用 | page/token 级，公共前缀复用更充分 → **更省** |

> **判断**：page_size 设得越小，SGLang 尾部浪费越少、前缀复用越充分，**相同序列长度下 SGLang 的有效 KV 占用可能反而更低**（命中率高 = 复用多 = 重复 KV 少）。代价是 page_size 小 → 元数据单元变多（host 内存）+ 管理开销变大。

### 2.4 综合结论（问题二）

1. **KV 张量本体（HBM 大头）：两边相同**——相同 token 数占相同 KV 池，数据结构不影响这部分。
2. **管理元数据：在 host 内存，不占 HBM**。Radix 树单个 TreeNode 比 KVCacheBlock 字段多、体积大，但**数量通常更少**（前缀合并），且**不消耗显存**。
3. **真正的 HBM 差异在碎片/复用效率**：page_size 越小，SGLang 尾部浪费越少、前缀复用越充分，**相同序列长度下 SGLang 的实际 KV 显存占用倾向更低或持平**，而非更高。
4. **代价转移**：SGLang 用 host 侧的树维护开销（CPU 内存 + 遍历/分裂的 CPU 时间）换取更高命中率和更省的 HBM 复用——**代价在 host，收益在 HBM**。

> **一句话**：**"Radix 树更费显存"是误解。** 树只持有索引、元数据在 host 不占 HBM、且数量通常更少；真正的 HBM 账由命中率/碎片决定，高命中的 Radix 反而更省 KV 显存。SGLang 付出的是 host 侧 CPU/内存的树维护成本。
