# DeepSeek-V4-Flash DCP 报错根因：代码严谨确认（修正版，零推测）

> 日期：2026-06-16
> 修正对象：[前一版分析](20260616-005422-deepseek-v4-flash-dcp不支持源码级根因分析-分析.md)中"关 MTP 就能跑 DCP"是**未经代码 100% 证实的推测**。本版穷尽 `dsa_cp.py` 与 `dsa_v1.py` 全部 `compressor_ratio` 相关代码，去掉一切推测，只留代码证实的事实。
> 代码基线：`vllm-ascend @ a57a8f0`

## 0. 结论（每一句都有代码行号支撑，无推测）

> **DCP 报错的精确触发条件 = 「投机解码 draft 元数据构建」(`build_for_drafting`) + 「模型含压缩层 (compressor_ratio>1)」。** DeepSeek-V4-Flash 含 C4(ratio=4)/C128(ratio=128) 压缩层，一旦走 draft 路径，断言 `compressor_ratio <= 1` 必然失败。

**断言原文（两处，都在 `build_for_drafting` 内）：**
```python
# dsa_cp.py:354    （DCP 版 builder 的 build_for_drafting）
# dsa_v1.py:1131   （非 CP 版 builder 的 build_for_drafting）
assert self.compressor_ratio <= 1, "vLLM-Ascend only support SWA-layer for Deepseek-V4 now."
```

## 1. 穷尽核查：`compressor_ratio<=1` 断言到底在哪几处（去推测的关键）

对 `dsa_cp.py` + `dsa_v1.py` 全文 grep `assert ... compressor_ratio <= 1`，**全仓仅两处**：

| 行号 | 所在方法 | 方法性质 |
|------|---------|---------|
| `dsa_cp.py:354` | `AscendDSACPMetadataBuilder.build_for_drafting` | **draft 路径**（DCP 版 builder） |
| `dsa_v1.py:1131` | `AscendDSAMetadataBuilder.build_for_drafting` | **draft 路径**（非 CP 版 builder） |

**关键事实：两处断言都在 `build_for_drafting`，没有任何一处在主路径 `build()` / `build_req_metadata()`。**

主路径对 `compressor_ratio>1` 是**有完整处理分支**的（不报错）：
```python
# dsa_cp.py:580  if self.compressor_ratio > 1:  layer_name = f"c{compressor_ratio}"
# dsa_cp.py:744  if self.compressor_ratio <= 1:  ... (else 分支处理 C4/C128)
# dsa_cp.py:796/798/815  compressor_ratio>1 / ==4 / !=4 的分支
```

> **这一步纠正了我上一版的不严谨**：断言确实只在 draft 路径，主路径有 C4/C128 实现——这是代码事实，不是推测。

## 2. `build_for_drafting` 的唯一触发条件（钉死 MTP 关系）

### 2.1 全仓唯一调用点

```bash
grep -rn "\.build_for_drafting(" vllm_ascend/
# → 唯一结果：vllm_ascend/spec_decode/llm_base_proposer.py:1644
```

**`build_for_drafting` 在全仓只有一个调用方：投机解码 proposer。** 没有第二处。

### 2.2 调用点的条件分支（决定性）

```python
# llm_base_proposer.py:1637-1654
if self.use_compress:
    attn_metadata = attn_metadata_builder.build_for_drafting(draft_step, ...)  # ← 走断言
else:
    attn_metadata = attn_metadata_builder.build(0, ...)                        # ← DSv4 进不来
```

### 2.3 `use_compress` 对 DeepSeek-V4 恒为 True

```python
# llm_base_proposer.py:156
self.use_compress = hasattr(self.vllm_config.model_config.hf_config, "compress_ratios")
```
- DeepSeek-V4-Flash 的 hf_config **有 `compress_ratios`**（C4/C128 配置）→ `use_compress = True`（恒成立）。
- → DeepSeek-V4 走 MTP draft 时，**必然进 `if self.use_compress` 分支，必然调 `build_for_drafting`，必然撞断言**。
- → 这条 `if/else` 里 DeepSeek-V4 **永远走不到 `else` 的 `build()`**。

### 2.4 `compressor_ratio` 的取值（断言必然失败）

```python
# dsa_cp.py:186
self.compressor_ratio = getattr(kv_cache_spec, "compress_ratio", 0)
```
- DeepSeek-V4 的 C4 层 `compress_ratio=4`、C128 层 `compress_ratio=128`（`deepseek_v4.py:118-170` + 资料 182107 §3.1：21 层 C4 + 20 层 C128）。
- → draft 构建遍历到任一 C4/C128 层 → `compressor_ratio = 4 或 128 > 1` → **`assert compressor_ratio<=1` 失败**。

## 3. DCP 与 MTP 的关系：代码层面的精确表述（去掉两头推测）

### 3.1 DCP 如何切到 CP builder

```python
# dsa_v1.py get_builder_cls() / get_impl_cls()
from vllm_ascend.utils import enable_dsa_cp
if enable_dsa_cp():
    return AscendDSACPMetadataBuilder   # DCP 版
return AscendDSAMetadataBuilder         # 非 DCP 版
```
`enable_dsa_cp()`（`utils.py:1345`）：模型有 indexer（DSv3.2/DSv4）+ DCP/PCP 配置开启时返回 True。
→ **DCP 一开，DeepSeek-V4 就切到 `AscendDSACPMetadataBuilder`。**

### 3.2 精确因果（这是回答"为什么报错和 MTP 有关"的核心）

> **断言不是"DCP 触发"，也不是"MTP 单独触发"，而是「DCP 模式下的 draft 元数据构建路径」对压缩层未实现。**

逐环（全部代码证实）：
```
开 DCP        → 切 AscendDSACPMetadataBuilder（环节 3.1）
  + 开 MTP    → 存在 proposer → draft step 调 build_for_drafting（环节 2.1/2.2）
  + use_compress=True（DSv4 恒真，环节 2.3）→ 进 if 分支走 build_for_drafting
  + 遍历 C4/C128 层 → compressor_ratio=4/128>1（环节 2.4）
  → assert compressor_ratio<=1 失败 → 报错
```

### 3.3 "关 MTP 能否跑 DCP" —— 代码定性（纠正我上一版的推测说法）

我上一版写"DCP+关MTP 代码支持"是**基于"主路径无断言"的推测**。本版用代码把它定性到可确证的程度：

| 情形 | 代码路径 | 断言是否触发 | 确证程度 |
|------|---------|------------|---------|
| DCP=1 | 不走 CP builder | 否 | ✅ 代码确证 |
| DCP>1 + **开 MTP** | 走 `build_for_drafting`（draft） | **是，必报错** | ✅ **代码 100% 确证** |
| DCP>1 + **关 MTP** | 无 proposer → `build_for_drafting` 永不被调用；主 decode 走 `build()`/`build_req_metadata`（无断言，有 C4/C128 分支） | 否（断言不触发） | ✅ 代码确证「断言不触发」；⚠️ 主路径 CP 切分的**功能正确性**需运行验证 |

> **诚实边界**：代码确证的是——关 MTP 时这个 SWA-only 断言**不会触发**（因为 `build_for_drafting` 唯一调用方是 MTP proposer，全仓 grep 已证）。但"关 MTP + DCP 主路径能否正确产出 C4/C128 的 CP 切分结果"是**功能正确性**问题，断言不触发≠功能一定正确，这一层需实跑验证，不能仅凭"无断言"下定论。**这是我能从代码给到的最严谨边界，再往前就是运行期行为，必须实测。**

## 4. 为什么启动不报错、压测才崩（代码证实）

```python
# platform.py:379  _validate_draft_decode_context_parallel_config
if draft_model_config.use_mla:
    return   # MLA draft 提前放行启动校验
```
- DeepSeek-V4 MTP draft 是 MLA → 启动期 DCP 校验在此 `return`，**不报错**。
- 断言在**运行期** draft step 构建（`build_for_drafting`）才执行 → 压测发起请求、走到 MTP draft 时才崩。

## 5. 修正后的结论（替换前一版的对应表述）

| 问题 | 代码确证的答案 |
|------|--------------|
| DCP 报错根因 | `build_for_drafting` 内 `assert compressor_ratio<=1`（`dsa_cp.py:354` / `dsa_v1.py:1131`） |
| 和 MTP 的关系 | `build_for_drafting` 全仓唯一调用方是 MTP proposer（`llm_base_proposer.py:1644`）→ **断言只在「开 MTP + DCP + 压缩模型」时触发** |
| 是不是 DCP 完全不支持 DSv4 | **否**。主 decode 路径 `build()` 无此断言、有 C4/C128 分支 |
| 是不是"关 MTP 就一定能跑 DCP" | 代码确证「断言不触发」；但主路径 CP 切分**功能正确性需实测**——这一句我上一版说得太满，本版收紧 |
| 我的纠错 | 上一版「关 MTP 代码支持」是基于"无断言"的推测；本版用「全仓唯一调用点 + use_compress 恒真 + 取值 4/128」三重代码证据，把断言触发条件钉死，并明确区分"断言不触发"（代码确证）与"功能正确"（需实测）两层 |
