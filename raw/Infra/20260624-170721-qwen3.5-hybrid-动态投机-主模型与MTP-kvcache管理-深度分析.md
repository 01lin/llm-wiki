## 〇、先把三个前提事实坐实（决定后面所有判断）

### 0.1 Qwen3.5 的 hybrid 结构 = full-attn 层 + GatedDeltaNet 线性层混合

- `qwen3_5.py` 按 `config.layers_block_type[idx]` 决定每层类型：`"attention"`（标准 full attn，有 KV）或 `linear_attn`（[qwen3_5.py:1173-1178](sglang/python/sglang/srt/models/qwen3_5.py)）。
- 线性层是 **`Qwen3_5GatedDeltaNet`**（[qwen3_5.py:144](sglang/python/sglang/srt/models/qwen3_5.py)），用 mamba 风格的卷积状态 + 循环状态（`mamba_v2_sharded_weight_loader`，:225），**不是传统 token KV，而是固定大小的 recurrent state**。

> **关键含义**：hybrid 模型有**两类"缓存"**——① full-attn 层的 KV cache（随序列线性增长）② 线性层的 mamba state（固定大小，每 step 原地更新）。这两类的管理逻辑、以及在投机下的处理**完全不同**，是本题的核心难点。

### 0.2 动态投机 = 运行时按接受率调 num_steps，不同 batch_size 不同候选集

- `AdaptiveStepSlot`（[adaptive_spec_params.py:138](sglang/python/sglang/srt/speculative/adaptive_spec_params.py)）："Adjusts speculative_num_steps at runtime based on observed acceptance lengths"——**用 EMA 跟踪接受长度，动态调 num_steps**。
- 不同 batch_size 用不同候选 num_steps 集合（adaptive_spec_params.py:148 注释）。
- `AdaptiveController`（[adaptive_runtime_state.py:61](sglang/python/sglang/srt/speculative/adaptive_runtime_state.py)）+ `SpecRuntimeState`（:19）做候选状态注册与切换。
- **约束**（adaptive_spec_params.py:58-88，`adaptive_unsupported_reason`）：仅 `eagle_topk=1` 支持、DP 多 rank 不支持（tier 决策不同步）、MultiLayerEagleWorkerV2 不支持、TboAttnBackend 不支持。

### 0.3 MTP draft 模型 = 1 层、强制 full attention（不带 linear）

- `Qwen3NextForCausalLMMTP`（[qwen3_next_mtp.py:42](sglang/python/sglang/srt/models/qwen3_next_mtp.py)）：`mtp_config.num_hidden_layers = 1` + **`full_attention_interval = 1`**（:33/34）——**MTP draft 只有 1 层且强制每层都是 full attention**，不含 GatedDeltaNet 线性层。

> **关键含义**：draft 模型本身**不是 hybrid**——它是个极简的 1 层 full-attn 模型。这大幅简化了 draft 侧的 KV 管理（draft 没有 mamba state 要操心），把 hybrid 的复杂性都留在了主模型侧。

## 一、主模型 & MTP draft 的 KV 管理方案（核心机制）

### 1.1 KV pool 复用：Frozen-KV MTP —— draft 不另存 KV，借用主模型的

SGLang 的核心设计是 **Frozen-KV MTP**：MTP draft 前向时，**临时把 draft 的 attn backend 的 KV pool 指向主模型（target）的 KV pool**，用完换回。

代码（[frozen_kv_mtp_utils.py](sglang/python/sglang/srt/speculative/frozen_kv_mtp_utils.py)）：
```python
def frozen_kv_target_view(...):        # :30
    saved_backend_pool = draft_attn_backend.token_to_kv_pool          # :51 存原pool
    draft_attn_backend.token_to_kv_pool = kv_context.target_token_to_kv_pool  # :52 换成主模型pool
    ...                                 # draft forward 用主模型 KV
    draft_attn_backend.token_to_kv_pool = saved_backend_pool          # :56 换回
```
- `FrozenKVMTPContext`（[frozen_kv_mtp_info.py:28](sglang/python/sglang/srt/speculative/frozen_kv_mtp_info.py)）：持有 `target_token_to_kv_pool`（主模型 KV）+ `physical_layer_ids`（draft 逻辑层 → 主模型物理层的映射，:31/34）。
- **"Frozen（冻结）" 的语义**：draft 读主模型 KV 时，**主模型那段 prefix KV 是只读冻结的**——draft 只读它做预测，不写回污染。draft 自己产生的 KV（投机 token 的）才是临时的。

> **判断**：主模型与 MTP draft **共享同一个 KV pool**（draft 借用主模型的），不是两套独立 KV。这省了 draft 侧的 KV 显存，也避免了主-draft KV 同步问题。`physical_layer_ids` 映射解决了 draft 1 层 ↔ 主模型多层的对应。

### 1.2 full-attn 层 KV：标准 page 管理 + 投机 token 的临时槽位

- 主模型 full-attn 层 KV 走标准 `token_to_kv_pool`（page 对齐）。
- 投机：draft 一次预测 N 个 token（N = 动态 num_steps），verify 时这 N 个 token 的 KV **先写进 pool 的临时槽位**，verify 通过的保留、被拒的回收。
- `set_frozen_kv_positions`（frozen_kv_mtp_utils.py:87）+ `expand_for_topk_draft`（:106）：按 topk/draft 展开 position，让投机 token 的 KV 落到正确位置。

### 1.3 线性层（mamba state）：投机下的真正难题 —— ping-pong + verify 后提交

这是 hybrid + 投机的**最大特殊处理**。mamba state 不是"追加式 KV"，而是**每 step 原地更新的循环状态**——投机的"试探性 token"会污染它，必须能回滚。

代码证据：
- **verify 后才提交 mamba 状态**：`commit_mamba_states_after_verify`（[spec_utils.py:577](sglang/python/sglang/srt/speculative/spec_utils.py)）+ `_update_target_mamba_state_after_verify`（[dflash_worker_v2.py:1047/1086](sglang/python/sglang/srt/speculative/dflash_worker_v2.py)）→ 调 attn backend 的 `update_mamba_state_after_mtp_verify`（:1061/1520）。
- **ping-pong 双 buffer 做回滚**：`HybridMambaDecodeReqToTokenPool`（[decode.py:183](sglang/python/sglang/srt/disaggregation/decode.py)）有 `mamba_ping_pong_track_buffer_size = 2 if enable_overlap_schedule`（:209）+ `enable_mamba_extra_buffer`（:210）——**一个 buffer 存"已确认"状态、一个存"投机试探"状态，verify 后用接受的覆盖、被拒的丢弃**。
- `frozen_kv_mtp_cuda_graph_runner` 是 "recurrent draft-loop step"（:61）——动态长度的循环 draft 用 CUDA graph 固化。

> **判断**：**hybrid + 投机的真正难点在线性层 mamba state，不在 KV。** KV 是 frozen 复用（简单），mamba state 是循环更新（必须支持投机回滚）。SGLang 用 **ping-pong buffer + verify 后提交** 解决：投机阶段在影子 buffer 上推进 state，verify 确定接受长度后才把对应步数的 state 提交为正式状态。

## 二、动态投机长度下的 KV/state 适配（不同 step 不同 spec 长度）

### 2.1 KV 侧：天然适配，无需特殊处理

- full-attn KV 是 page 池按需分配，投机 N 个 token 就申请 N 个临时槽，**N 变化只是申请数量变化**，池本身不需要为"动态长度"做特殊改造。
- `AdaptiveStepSlot` 调的是 `speculative_num_steps`（draft 循环几次），每次循环 draft 产 1 个 token，KV 槽位按实际 num_steps 动态申请/回收。

### 2.2 CUDA graph 侧：动态长度的真正适配点

动态投机长度的麻烦在 **CUDA graph**——graph 是固定 shape 的，num_steps 变了 shape 就变。SGLang 的处理：
- `AdaptiveController.init_states(cuda_graph_bs)`（adaptive_runtime_state.py:94）：**为不同候选 num_steps 各捕获/管理一套 graph 状态**。
- 切换 num_steps = 切换到对应的 graph 状态（`apply_runtime_state`，adaptive_runtime_state.py:58）。
- 约束 0.2 里的"TboAttnBackend 不支持""adaptive state swap 不更新 decode_attn_backend_group"等，都是 graph 状态切换带来的限制。

### 2.3 mamba state 侧：ping-pong buffer 需覆盖最大投机长度

- ping-pong track buffer（decode.py:209）要能容纳**最大候选 num_steps** 的中间状态——动态长度下，buffer 按最大长度预留，实际用多少看当前 step 的 num_steps。
- ⚠️ 动态 num_steps 变化时，mamba 影子 buffer 的复用/重置逻辑本次未逐行确认是否完全无缝（见存疑）。

## 三、是否需要适配/特殊处理 —— 结论清单

| 组件 | 是否需特殊处理 | 处理方式 | 代码依据 |
|------|--------------|----------|----------|
| **主模型 full-attn KV** | ⭕ 轻度 | draft 通过 frozen view 复用主模型 KV pool | frozen_kv_mtp_utils.py:30/51 |
| **MTP draft 自身 KV** | ❌ 不需独立 | 不另存，借用主模型 pool（FrozenKVMTPContext） | frozen_kv_mtp_info.py:28 |
| **draft↔主模型层映射** | ⭕ 需要 | physical_layer_ids 映射 draft 1 层 → 主模型物理层 | frozen_kv_mtp_info.py:31/34 |
| **主模型 mamba 线性状态** | ✅ **重度特殊处理** | ping-pong 双 buffer + verify 后提交，支持投机回滚 | spec_utils.py:577, decode.py:209 |
| **draft 模型 mamba** | ❌ 无 | draft 强制 full_attention（1 层），不含线性层 | qwen3_next_mtp.py:33/34 |
| **动态投机长度 × KV** | ❌ 天然适配 | page 池按 num_steps 动态申请槽位 | — |
| **动态投机长度 × CUDA graph** | ✅ **需特殊处理** | 多候选 num_steps 各管一套 graph 状态 | adaptive_runtime_state.py:94 |
| **动态投机长度 × mamba buffer** | ⚠️ 部分 | ping-pong buffer 按最大长度预留 | decode.py:209（细节存疑） |

### 核心结论

1. **KV 管理本身很简洁**：MTP draft **不另存 KV**，通过 `frozen_kv_target_view` 借用主模型 KV pool（只读冻结），靠 `physical_layer_ids` 做层映射。动态投机长度对 KV 池是透明的（按需申请）。
2. **真正的特殊处理在两处**：
   - **hybrid 的 mamba 线性状态**：投机会污染循环状态，必须 ping-pong 双 buffer + verify 后提交才能回滚——这是 hybrid 独有的、KV 模型没有的难题。
   - **动态长度 × CUDA graph**：num_steps 可变 vs graph 固定 shape 的矛盾，靠多候选 graph 状态切换解决，并带来一串约束（topk=1、不支持 DP/TBO 等）。
3. **设计哲学（拉通看）**：SGLang 把复杂性**集中在主模型侧**——draft 做成极简 1 层 full-attn（不 hybrid、不另存 KV），主模型承担 KV 复用源 + mamba 状态回滚。这让 draft 轻量、verify 高效，代价是主模型的 mamba 状态管理逻辑复杂。

## 四、待核实/存疑

1. **动态 num_steps 切换时 mamba ping-pong buffer 的复用/重置**（2.3）：buffer 按最大长度预留已坐实，但 num_steps 从大切小/小切大时影子 buffer 的清理是否完全无缝，未逐行确认。
2. **Frozen-KV MTP 与 EAGLE 的关系**：`FrozenKVMTPDraftInput(EagleDraftInput)`（frozen_kv_mtp_info.py:44）注释说"reuses the EAGLE scheduler/attention contract"——Frozen-KV MTP 是 EAGLE 的特化，二者边界本次未深挖。
3. **昇腾侧（sgl-kernel-npu）hybrid+spec 适配**：`ascend_hybrid_linear_attn_backend.py` 存在，但它是否实现了 `update_mamba_state_after_mtp_verify`（投机回滚的关键 hook）未确认 —— ❓ 昇腾上 hybrid+动态投机的完整可用性存疑。
4. **dflash vs frozen_kv_mtp 两条 worker 路径**：`dflash_worker_v2.py` 和 frozen_kv_mtp 都处理 mamba verify，二者是不同投机算法（DFlash vs MTP）还是同一套，本次未完全厘清。
5. **Qwen3.5 27B 的 layers_block_type 具体配比**：full:linear 的层数比例未从 config 确认（影响 KV vs state 的显存占比），需实机 config。
