## 0. 一句话设计 + 一个诚实约束

> **设计**：按实时 batch 负载 + 历史接受率，动态决定本步投机几个 token，挂 B 层 `around_propose_draft` hook，零核心 patch。
>
> **诚实约束（走读坐实，改变设计）**：`num_speculative_tokens` **不是 per-step 变量，是 init 期定死的结构常量**——用于 buffer/tensor 固定长度分配（llm_base_proposer.py:210/216/220 `range(self.num_speculative_tokens)`、:158 `decode_threshold=1+num_spec`、:547 `max_query_len=num_spec+1`）。
> **因此 L4 不能"per-step 放大 K"，只能"按 K_max 分配 buffer，per-step 动态用 0..K_max"**。即：投机的"自适应"是**向下调节 + 整体开关**，不是向上扩张。

## 2. 自适应控制器（要构建，挂 B 层 hook）

```
init：num_speculative_tokens = K_max（buffer 按此分配，固定）
每步（around_propose_draft hook 内）：
  load = input_batch.num_reqs / max_num_reqs        # 实时负载率
  acc  = EMA(历史接受率)                            # after_bookkeeping 回灌
  k_eff = policy(load, acc):
    if load > 高阈值:        k_eff = 0   # 高负载关投机（投机吃算力，高负载时净负收益）
    elif acc < 低阈值:       k_eff = 0   # 接受率太低，投机浪费
    else:                    k_eff = min(K_max, f(acc))  # 接受率高→多投
  → 本步只 propose k_eff 个（≤K_max，buffer 够用）
after_bookkeeping hook：读 num_accepted_tokens → 更新 EMA(acc)
```

> **核心 policy 底层逻辑**：投机是"用额外算力换 decode 步数"。**高负载时算力本就紧张，投机净收益转负** → 关；**低接受率时投机基本白算** → 关；**低负载 + 高接受率时** → 投满 K_max。这把"投机"从静态开关变成负载自适应的闭环。

## 4. 收益推导（与主文档 §3.5.4 衔接）

```
有效加速 = 1 + acc × k_eff   （acc=接受率，每步多产出 acc×k_eff 个 token）
官方 recipe k=1：若 acc=0.7 → 有效加速 1.7×（单步多 0.7 token）
自适应 k_eff≤K_max（设 K_max=3）：
  低负载窗口 acc=0.7, k=3 → 1+0.7×3 = 3.1×（理论上界，受 buffer/算量约束打折）
  高负载窗口 k=0 → 1×（不投机，省算力给吞吐）
全局平均（负载有高有低）→ §3.5.4 的 1.5–2.5× 区间
```

> **L4 的真正价值不只是"投更多"，更是"高负载时果断不投"**——避免静态投机在高负载下拖累吞吐（这是 baseline 静态 k=1 在高并发下的隐性损失）。

## 5. 遗留问题（要求 1 + 走读硬约束）

1. **接受率 acc 必须实测，无法分析得出** — 依赖 MTP/eagle draft 模型质量 + 数据分布，无昇腾环境无法定。**这是 5–10× 推导唯一不可参数化消除项**（主文档 §6-2）。对应 §7-E2 实验。❓
2. **num_speculative_tokens 结构性固定** — 已坐实只能向下调，不能 per-step 向上。若要更大 K_max 需重启服务调 config。设计已据此调整（向下自适应）。✅约束已纳入
3. **DSA topk512 × MTP 协同** — MTP 预测的 token 也要过 indexer 选择，协同未见代码验证。❓（主文档 §3-L4 遗留）
4. **DBO × 投机叠加** — microbatching 下投机稳定性未验证（主文档 §3-L2 遗留）。❓
5. **policy 阈值（高负载/低接受率阈值）需实测调参** — 初值靠 E2 实验扫描。❓

## 6. 与验证矩阵衔接
