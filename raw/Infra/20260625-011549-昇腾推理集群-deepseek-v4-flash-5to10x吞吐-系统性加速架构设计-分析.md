## 2. 需求 1：负载驱动的瓶颈定位与 5–10× 推导（口径 A）

### 2.1 为什么必须"先量化浪费，再堵漏"

提吞吐的常规手段（增 batch / 加并发）必然推高 TPOT，与"TPOT 不劣化"硬约束对立。因此 5–10× 的唯一可论证来源是：**同卡、同 TPOT 预算下，把 baseline 空转/重算/浪费的算力，填回有效 token**。下面把 baseline 拆成七个"漏桶"，逐项给回收技术与倍率档（乘性叠加，因各自作用在不同资源维度）。

### 2.2 七漏桶总表

| # | 漏桶 | baseline 损失机理 | 回收技术 | 倍率档 | 档位 | 证据 |
|---|------|------------------|---------|-------|------|------|
| **L1** | agentic 前缀重算 | 多轮每轮重 prefill 历史；无跨实例全局前缀复用，路由看不到 KV 分布 | 集群级全局 KV-aware 路由 + 跨实例前缀索引 | **2–4×** | 🟠需构建 | 🟡 业界数+缺口坐实 |
| **L2** | EP 通信空转 | EP16/EP64 MoE all-to-all 占比高，跨卡带宽弱，不重叠则算力空转 | DBO 计算通信重叠 | 1.3–1.8× | 🟢组合 | ✅ enable_dbo |
| **L3** | host 调度墙 | decode 单 step 算量小（batched 256），Python launch 占比高 | ACL/NPU Graph replay | 1.2–1.5× | 🟢组合 | ✅ 图模式有 |
| **L4** | 投机未充分 | recipe 仅 spec=1；接受率高时可吃更多 token | MTP 多 token + **负载自适应开关** | **1.5–2.5×** | 🔵需增强 | ✅proposer全+🟠策略缺 |
| **L5** | 显存→并发 | bf16 KV 占满显存限 max-num-seqs | 压缩态 KV(ratio4)+c8 量化 KV 换并发槽 | **1.5–2×** | 🟢+🔴验证 | ✅能力有 |
| **L6** | P/D 配比僵化 | P/D 节点静态 4:4，agentic 负载漂移→一侧排队一侧空转 | goodput 驱动 P/D+EPLB 统一弹性 | 1.3–1.6× | 🟠需构建 | 🟡 EPLB有/统一缺 |
| **L7** | 长上下文注意力 | DSA 已大幅降算，但需确保全开+与压缩KV叠加 | DSA(topk512) 全开 + 叠加 | 1.2–1.5× | 🟢有🔴叠加 | ✅ dsa_v1.py |

### 2.3 倍率合成（5–10× 的诚实推导）

> ⚠️⚠️ **本节为初版七漏桶推导，已被两次修正超越——以下式仅存推导轨迹，达标口径以最终版为准**：
> 1. **基线重定义**：L3/L5/L7 实为 DeepSeek-V4 结构默认，**已在基线**，不应计入增量（[[20260625-013023-昇腾集群-512K上下文-基线外5to10x定量推导-方案]]）。
> 2. **bf16-only**：L5 的 c8 量化作废。
> **最终合成（以此为准）**：基线外 `L1(3.2–4×) × L2+L2'(1.5–1.7×) × L6(1.33×) × L4自适应(1.15×) × 0.75折算 ≈ 5.5–10.4×`，见 [[20260625-013625-昇腾集群-bf16only-NPU真实支持-双约束修正与重推导-方案]] §4。

```
保守下界（仅高置信 L1–L5，各取低端）：
  2.0(L1) × 1.3(L2) × 1.2(L3) × 1.5(L4) × 1.5(L5) ≈ 7.0×
扣除漏桶间相互挤占（经验折半系数 0.5）：
  7.0 × 0.5 ≈ 3.5×（仅做 L1 低端的下界）
达标区间：L1 命中率做到 70%+（→3–4×档）+ L4 自适应 + L5 验证通过
  → 现实落点 5–10× 成立，但强依赖三支柱做实
```

**三支柱定生死**：

| 支柱 | 漏桶 | 档 | 缺它的封顶 |
|------|------|----|----------|
| 全局前缀路由 | L1 | 🟠构建 | 封顶 ≈3×（天花板项） |
| 投机自适应 | L4 | 🔵增强 | 少 1.5–2.5× |
| 压缩/量化换并发 | L5 | 🟢+验证 | 少 1.5–2× |
| 地基（白嫖） | L2/L3/L7 | 🟢 | ≈2–3× |

> 结论：地基靠"最佳 recipe 组合"即得 2–3×；**5–10× 必须把 L1+L4+L5 做实，L1 是天花板**。
>
> ⚠️ 本节的"折半系数 0.5"是初版经验估计，已在 **§3.5 第一性原理重算**中用可追溯参数（KV 字节账 / 命中率公式 / DSA 算量差）替代，请以 §3.5 为准。

### 2.4 辅口径 C（goodput）校验

agentic 长尾下，超出 TPOT SLO 的 token 不计入有效吞吐。L1（命中省重算 → 降 TTFT/排队）+ L6（消 P/D 排队）对 goodput 的贡献高于对裸吞吐的贡献，因此 **goodput 口径下 5–10× 比裸吞吐更易达成**（裸吞吐严格，goodput 贴合工程现实）。SLO 阈值需用户按业务定（见遗留问题）。

## 3.5 三支柱倍率的第一性原理重算（把 0.5 折半系数换成可追溯参数）

> 动机：第 2.3 节用了经验折半系数 0.5 + 业界档位，评审最易质疑"三支柱倍率站不站得住"。本节用**已坐实的结构参数**自底向上重算，把不可追溯的系数替换为参数化公式。
>
> **证据边界（严格遵守要求 1）**：
> - ✅ 代码坐实：max_position=**1048576（1M 上下文）**(deepseek_v4.py:11)、DSA index_topk=512/compress_ratio=4、MLA latent=kv_lora_rank+rope(deepseek_v2.py:416-433)、官方 recipe batched P16384/D256、seqs D28。
> - ⚠️ 外部假设（**本仓 config 为薄壳，真实结构数来自 HF 权重 config，不在仓内；以下取 DeepSeek-V3/V4 公开参考值并显式标注，非代码推导**）：num_layers≈61、MLA kv_lora_rank=512/qk_rope=64（latent 576 dim/token/layer）、910B3 单卡 HBM=64GB。这些值变化时公式仍成立，仅数值需替换。

### 3.5.1 KV 字节账（L5 的物理基础）

DeepSeek-V4 用 MLA，每 token 每层只存 latent（576 dim），而非完整 KV head。

```
单 token KV 字节(bf16) = num_layers × latent_dim × 2 bytes
  = 61 × 576 × 2 ≈ 70 KB/token              （⚠️外部参考值）
16k 上下文单序列 KV = 16384 × 70KB ≈ 1.1 GB
```

- **L5 压缩/量化换并发倍率（可推导上界）**：
  - compress_ratio=4（✅坐实）→ 压缩态 KV ≈ 1.1GB/4 ≈ 0.28GB/序列
  - c8（int8/fp8）再 ×0.55（bf16→8bit，**含 per-token scale 开销**，✅ enable_sparse_c8 坐实档位）—— ⚠️ 见 [[20260625-012453-昇腾集群-L5压缩量化换并发-支柱特性详细设计-分析]] 修正：c8 净压缩比含 scale 后 < 名义 2×，叠加后净 ≈7.3× 而非 8×。
  - **显存占用降 ≈7.3×**，但并发提升 ≠ 7.3×（权重/激活/通信 buffer 不随 KV 缩）。
  - 实际：设 KV 占可用 HBM 比 r（需 E1 实测），并发提升 = 1/(1−r+r/7.3)，r=0.5→1.76×，r=0.6→2.07× → **1.5–2×**（与第 2.3 节 L5 档位自洽）。**折半在此被"KV 仅占 HBM 比例 r"这一可实测参数解释，非拍脑袋。**

### 3.5.2 注意力算量账（L7 + 长上下文必要性）

```
稠密注意力 decode 单步算量 ∝ seq_len
DSA 稀疏后 ∝ min(seq_len, index_topk=512)        （✅坐实）
16k 上下文：稠密/稀疏 ≈ 16384/512 = 32× 注意力算量差
```

- 但注意力只占 decode 总算量一部分（MLA+MoE FFN 是大头），故 L7 端到端倍率 **1.2–1.5×**（与 2.3 自洽）。**关键推论：没有 DSA，1M 上下文 agentic 在 910B3 上不可行——L7 是"可行性前提"而非"锦上添花"**，这强化了三支柱必须全开。

### 3.5.3 前缀复用账（L1 倍率的可追溯化）

agentic 多轮：第 N 轮的 prefill 输入 = 历史(N-1 轮累积) + 新增。命中率不靠业界类比，按场景算：

```
设单轮新增 token=x，历史累积=H，命中率 = H/(H+x)
官方场景 in3.5k：若多轮中 H 增长到 12k、单轮新增 x=3.5k
  命中率 = 12k/15.5k ≈ 77%   → prefill 重算省 77%
prefill 占端到端比例越高，L1 收益越大。
```

- **L1 端到端倍率**：省的是 prefill 重算 → 直接降 TTFT + 释放 P 节点算力给更多请求。在 prefill 重算占总算力 30–50% 的 agentic 场景，命中 77% → **吞吐 ×2–4** 区间自洽（与 2.3 一致，但现在命中率是**场景可算**而非业界借来）。
- **遗留收敛**：命中率公式依赖"历史 KV 真在某实例可被路由命中"——这正是 L1 需构建全局索引的原因；索引未建则命中率→实例内 Radix 的局部值（远低于 77%）。❓ 索引一致性开销仍无代码可算。

### 3.5.4 重算后的合成（替代经验折半）

| 支柱 | 第一性原理倍率 | 替代了什么经验值 |
|------|--------------|----------------|
| L1 前缀 | ×2–4（命中率 H/(H+x) 可算） | 业界借来的 70% → 场景公式 77% |
| L4 投机 | ×1.5–2.5（接受率×spec_len，待实测接受率） | 仍需实测接受率 ❓ |
| L5 换并发 | ×1.5–2（KV 缩 8× 但仅占 HBM 半 → 折算） | 0.5 折半 → "KV 占 HBM 比例"物理事实 |
| 地基 L2/L3/L7 | ×2–3（DSA 32× 算量差兜底长上下文可行性） | — |

```
合成（口径 A，同 TPOT）：
  地基 2.5 × L1(3.0) × L4(2.0) × L5(1.7) ≈ 25× 名义上界
  扣资源争抢（L1 命中后 prefill 算力释放被 L5 更多并发吃掉 = 部分重叠）：
  实际可叠加 ≈ 5–10×，落在目标区间
```

> **本节结论**：5–10× 从"区间估计 + 经验折半"升级为"**三支柱倍率各有可追溯来源**"：L1 靠命中率公式、L5 靠 KV 字节账、L7 靠 32× 算量差兜底可行性。**仍存的硬遗留 = L4 接受率必须实测**（无昇腾环境无法定，是 5–10× 推导中唯一无法参数化消除的不确定项）。

## 4. 需求 2：迁移友好的双层接缝架构（工程脊柱）

### 4.1 三项主线决策（已敲定）

| 决策 | 选择 | 理由 |
|------|------|------|
| 接入方式 | **C 混合** | 官方扩展点为主 + 薄 patch 兜底，patch 面积当持续收敛指标 |
| 稳定接缝 | **C 双层** | 集群级挂官方扩展点(A层)/实例内挂 hook(B层)，各自版本契约 |
| B 层挂载 | **B hook 锚点** | patch 面积与特性数量解耦，非子类整方法覆写 |

### 4.2 patch 面积的现实与目标

vllm-ascend 自身即"靠 patch + 继承活在 vllm 之上"的插件（AGENTS.md「Model and Plugin Architecture」：Inheritance `NPUModelRunner(GPUModelRunner)`:255 + Patching patch/platform、patch/worker）。**现状 55 个 patch 文件**，含 patch_scheduler/patch_balance_schedule/patch_kv_cache_*（3）/patch_speculative_config。病症是"每个特性各长一个 patch"的线性增长。

> **本框架价值 = 让新特性不再各长 patch**，收敛到"6 个 hook 锚点 + 既有扩展点"。可迁移性硬指标：**净新增 patch 文件 ≈ 0**。

### 4.3 双层接缝定义

```
A 层（集群级）→ 官方扩展点，近零 patch
  • KVConnector scheduler 钩子 (L1)：get_num_new_matched_tokens/update_state_after_alloc (mooncake_connector.py:1284/1288)
  • Scheduler 子类化 (L6)：SchedulerDynamicBatch(Scheduler) (:122/151)
  • additional_config 开关面 (特性注册入口)：ascend_config.py
B 层（实例内 runner 级）→ hook 锚点 + 薄 patch
  • HookRegistry 挂 NPUModelRunner 子类
  • RunnerContext(ctx) 受控读写 runner 内部态
  • 6 锚点（跨 execute_model + sample_tokens 两相）
```

### 4.4 B 层 6 锚点（grep 实测，横跨两相）

execute_model 为两段式（async scheduling：返回 None@2335 后由 sample_tokens@2338 收尾），锚点横跨两方法：

| 锚点 | 落点 | 行号 | 承接 |
|------|------|------|------|
| after_prepare_inputs | _prepare_inputs 后 | 2036 | 输入改写、L1 命中态注入 |
| after_preprocess | _preprocess 后 | 2196 | embedding/mm 干预 |
| around_model_forward | _model_forward 前后 | 2256 | DBO/CP 协同观测 |
| before_sample | _sample 前(sample_tokens 内) | 2390 | 采样干预 |
| around_propose_draft | propose_draft_token_ids 前后 | 2403 | **L4 投机自适应** |
| after_bookkeeping | _bookkeeping_sync 后 | 2425 | metrics、接受率回灌 L4 |

> patch 面积 = 6 行锚点（1 个 patch_runner_hooks.py），与特性数量解耦。升级时只确认 6 个调用点时序未变（变了挪锚点，个位数改动）。

### 4.5 HookRegistry + RunnerContext 契约（设计意图）

- HookRegistry：`register(anchor, fn, priority)`；锚点处 `self._hooks.run(anchor, ctx)`。特性 = 注册到锚点的纯函数，不碰 runner 其他代码。
- RunnerContext：唯一受控"内部态视图"，白名单暴露 scheduler_output/input_ids/positions/spec_metadata/sampler_output/acceptance_stats。特性只经 ctx 读写，禁止直接摸 self.xxx（隔离：上游改内部字段名只需改 ctx 适配）。
- 版本契约：ctx 字段映射集中 ctx_adapter_v{ver}.py，用既有 vllm_version_is()(utils.py:558，model_runner_v1.py 内 9 处) 分版本——B 层版本吸收点。

### 4.6 "几乎不感知迁移"的可度量验收

| 指标 | 目标 | baseline |
|------|------|----------|
| 净新增 patch 文件 | **0** | 55（现状） |
| B 层锚点行数 | ≤6，与特性数解耦 | 0（待插） |
| 上游小版本升级改动面 | 仅 ctx_adapter + 锚点确认 | 9 处散落 vllm_version_is |
| 特性叠加成本 | O(1) 注册，不改主链路 | ~1 patch/特性 |

## 6. 遗留问题汇总（要求 1：代码无法解释处不硬编）

1. **倍率档位均无昇腾 910B3 实测** — §3.5 已把 L1/L5/L7 参数化（命中率公式、KV 字节账、DSA 算量差），但绝对值仍须实测校准。❓
2. **L4 投机接受率是唯一无法参数化消除的不确定项** — §3.5 把 L1/L5 的经验系数替换为可追溯公式后，5–10× 推导中仅剩 L4 接受率必须实测（无昇腾环境无法定）。这是达标论证的最大单点风险。❓【原 0.5 折半系数已由 §3.5 替代】
3. **DeepSeek-V4 真实结构数不在本仓** — config(deepseek_v4.py) 为薄壳，num_layers/kv_lora_rank/experts 来自 HF 权重 config；§3.5 取 V3/V4 公开参考值并标注，须以实际权重 config 校验。❓
3. **TPOT 不劣化边界未量化** — L5 换并发到何处顶 TPOT 红线，需 batched/seqs 扫描实测。❓
4. **辅口径 C 的 SLO 阈值未定** — goodput 统计需用户按业务给 TPOT/TTFT SLO。❓
5. **三处叠加正确性**：DBO×投机(L2/L4)、DSA×compress×c8(L5/L7)、MTP×DSA-indexer(L4) — 均代码可见接口、未见同开验证。❓
6. **整机弹性是否依赖外部编排**（L6）— 走读未定位实例级容错/滚动升级方案，疑依赖 K8s 上层。❓

### 8.3 倍率合成校准法

```
单节点测得各支柱倍率后，集群级合成需补两项（单节点测不出，标注为外推）：
  • L1 全局索引跨实例命中增量（单节点只能测实例内 Radix 命中下界）❓外推
  • L6 P/D 弹性（需多节点 P/D 分离，单节点测不出）❓外推
单节点可坐实：地基(E4) × L4(E2) × L5(E1)；
集群级 = 上述 × L1 跨实例增量(E3 实例内值 × 全局索引外推系数) × L6
```

### 8.4 这套验证消除/保留的 ❓

- **消除**：E0 定 TPOT 红线（§6-3）、E1 定 L5 真值（§3.5.1）、E2 定 L4 接受率（§6-2 最大风险）、E3 定 L1 实例内命中率、E4 定地基倍率。
- **保留为外推**：L1 全局索引跨实例增量、L6 整机弹性——**这两项必须多节点才能实测**，单节点阶段只能给下界 + 外推系数。诚实标注，不消除。

## 8. 一页纸决策卡

- **目标**：910B3 / DeepSeek-V4-Flash bf16 / agentic / 同 TPOT 吞吐 5–10×（口径 A 主、C 辅）。
- **达成路径**：地基组合 ≈2–3×（白嫖）× 三支柱 L1/L4/L5（必须做实）→ 5–10×；L1 是天花板。
- **架构**：C 混合 / C 双层接缝 / B hook 锚点；可迁移性 = 净新增 patch ≈ 0。
- **切入点**：L1→connector 钩子(A)，L4→around_propose_draft hook(B)，L6→Scheduler 子类(A)，6 锚点全在 model_runner_v1.py 实测行号。
- **最大风险**：无昇腾实测，所有倍率为理论推导，须实测校准（遗留问题 1–6）。
