# vLLM/vllm-ascend GDN 动态投机精度异常：根因定位与代码级修复方案

> 生成时间：2026-06-24
> 走读版本：vllm `0d2961229` / vllm-ascend `8afdf356`
> 现象：动态投机下 **"verify mtp3 + propose mtp1" 切换过程**易出现精度异常
> 目标：聚焦 GDN（GatedDeltaNet）模块，分析 GDN metadata + mamba state 需做的处理/适配，给 E2E 步骤 + 代码修改建议 + 理论论证

## 〇、结论先行（TL;DR）

> 约束：**同 step 内所有 req 投机长度一致**，长度只在 step 之间切换（mtp3→mtp1）。故根因**不在同 step 列宽**，在跨 step 的递归 state 延续。

**根因**：vLLM 异步调度（async scheduling）下，当前 step 在上一步 verify 真实接受数回 CPU 前，**乐观假设上一步 draft 全接受**（`optimistic_num_accepted = prev_num_draft_len`，[gpu_model_runner.py:1310](vllm/vllm/v1/worker/gpu_model_runner.py)），并据此推进 GDN 的 mamba conv_state/ssm_state。**事后修正（correction）只改 `output_token_ids`，不回滚已被多推进的递归 state**。mtp3→mtp1 切换时，上一步（mtp3）乐观值最大、被拒概率最高，多推进的 state 偏差最大；mamba 递归不可逆放大 → 精度异常。稳态不切换时偏差被持续 correction 摊平，故平时不暴露、切换才报。

**与 KV 模型的本质区别**：KV cache 按位置寻址，乐观多写的 KV 下次被覆盖、无副作用；mamba 是递归累积，多推进 = 状态被多卷积/多 gate，**不可逆污染**。

**核心修复**：mamba 递归 state 的推进步数**必须锚定"真实接受数"**而非乐观值——要么对 GDN 层关闭乐观（同步真实 num_accepted），要么乐观推进到影子 buffer、真实值回来后取第 k 步快照覆盖（ping-pong 回滚）。

## 一、GDN 投机的 E2E 推理流程（先建立全景）

以一个 step 为例（Qwen3.5 hybrid，含 GDN 线性层），投机走 metadata→forward→kernel 三段：

### 1.1 metadata 构建（[gdn_attn.py](vllm/vllm/v1/attention/backends/gdn_attn.py)）

`GDNAttentionMetadataBuilder.build()`：
1. `__init__` 时固定 `self.num_spec = num_speculative_tokens`（[gdn_attn.py:107](vllm/vllm/v1/attention/backends/gdn_attn.py)）—— **静态最大投机长度**，全程不变。
2. 由 `num_decode_draft_tokens_cpu >= 0` 求 `spec_sequence_masks` / `num_spec_decodes`（:200/201）。
3. 切投机序列的 state indices：
   ```python
   spec_state_indices_tensor = block_table_tensor[spec_sequence_masks_cpu, : self.num_spec + 1]  # 列宽恒 = num_spec+1（静态）
   ```
4. cudagraph 路径填 `num_accepted_tokens`：真实接受数 + padding（[gdn_attn.py:454/458](vllm/vllm/v1/attention/backends/gdn_attn.py)）。

### 1.2 GDN forward（[qwen_gdn_linear_attn.py](vllm/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py)）

投机分支（:1342-1355、:1456-1472）把 metadata 喂给 kernel：
```python
... = fused_recurrent_gated_delta_rule_packed_decode(
    ssm_state_indices=spec_state_indices_tensor,          # :1471  列宽=num_spec+1（静态）
    num_accepted_tokens=num_accepted_tokens,              # :1472  逐序列真实接受数
    max_query_len=spec_state_indices_tensor.size(-1),     # :1355  = num_spec+1（静态）
    ...)
```

### 1.3 mamba state kernel（[fused_recurrent.py](vllm/vllm/model_executor/layers/fla/ops/fused_recurrent.py)）

投机 decode 的 state 取址（精度命门）：
```python
# IS_SPEC_DECODING = num_accepted_tokens is not None  (:23)
i_t = tl.load(num_accepted_tokens + i_n).to(tl.int64) - 1                      # :106  列偏移 = 接受数-1
state_idx = tl.load(ssm_state_indices + i_n * stride_indices_seq + i_t)        # :110  行偏移 + 列偏移取 slot
# 行 stride 由张量第二维实际宽度决定：
stride_indices_seq, stride_indices_tok = ssm_state_indices.stride()            # :215
```
对比非投机路径（:292）：`state_idx = ssm_state_indices + i_n*stride_indices_seq`（**无 `i_t` 列偏移**）—— 印证投机路径多了 `i_t` 这一维，正是出错维度。

## 二、根因深析：为什么 mtp3→mtp1 跨 step 切换出错

> **重要约束校正**（用户确认）：**同一个 step 内所有 req 投机长度相同**，不存在同 step 混批不同投机长度。投机长度只在 **step 之间**切换（step N = mtp3，step N+1 = mtp1）。因此根因**不是同 step 内的列宽错配（已排除"混批"路径）**，而是**跨 step 的 mamba state 延续**：异步调度的"乐观接受"用上一步的投机长度推进了本步 mamba state，而上一步实际接受数 < 投机长度时，多推进的递归状态无法回滚。

### 2.1 真凶：异步调度的"乐观接受"跨 step 推进 mamba state

vLLM 异步调度（async scheduling）下，为了不阻塞，当前 step 在上一步 verify 结果回 CPU 之前，**乐观假设上一步 draft 全部被接受**，事后再修正：

```python
# gpu_model_runner.py
optimistic_num_accepted = req_state.prev_num_draft_len          # :1310  乐观=上一步draft长度
req_state.output_token_ids.extend([-1] * optimistic_num_accepted)  # :1311 先按乐观值占位
deferred_spec_decode_corrections.append((req_id, optimistic_num_accepted, req_state))  # :1313 排队事后修正
...
num_accepted = valid_sampled_token_count[prev_req_index] - 1     # :1478 真实接受数
correction = optimistic_num_accepted - num_accepted             # :1479 修正量 = 乐观 - 真实
```

`prev_num_draft_len` 是**上一步的投机长度**（注释 [gpu_model_runner.py:1296-1299](vllm/vllm/v1/worker/gpu_model_runner.py)：第三步 `num_computed_tokens = 100 + 2`，prev_num_draft_len=2）。

### 2.2 出错机理（GDN conv_state / ssm_state 的跨 step 推进）

GDN forward 用 `num_accepted_tokens` 推进 **两类递归状态**：
- **conv_state**（因果卷积状态，width-1 个历史 token）：`conv_state_indices=spec_state_indices_tensor[:, 0]` + `num_accepted_tokens`（[qwen_gdn_linear_attn.py:1350/1353](vllm/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py)）；
- **ssm_state**（GatedDeltaNet 递归状态）：`ssm_state_indices=spec_state_indices_tensor` + `num_accepted_tokens`（:1471/1472）；
- `has_initial_state`（:1300）标识是否承接上一步状态。

**mtp3→mtp1 切换的出错链**：
1. **step N（mtp3）**：propose 3 个 draft，verify 实际接受数可能 < 3（如只接受 1 个）。
2. **step N+1（mtp1）异步**：在 step N 的真实 `num_accepted` 回 CPU 前，用 `prev_num_draft_len = 3`（mtp3 的长度）做乐观值，**按"接受 3 个"推进 mamba conv_state/ssm_state**（多推进了 2 个未被接受的 draft token 的状态）。
3. **事后修正只改 token id，不回滚 mamba state**：`correction`（:1479）修正的是 `output_token_ids`（删掉多占位的 -1），但 **mamba 的 conv_state/ssm_state 已经按乐观值多推进了 2 步**——递归状态一旦多卷积/多递归，无法靠改 token id 回退。
4. **mtp1 这步又承接了被污染的 state**（`has_initial_state=True`）→ 后续全错。

> **底层逻辑**：KV cache 是"按位置寻址"的，乐观多写的 KV 下次直接被覆盖、无副作用；但 **mamba 是"递归累积"的，多推进 = 状态被多卷积/多 gate 了几步，是不可逆的污染**。mtp3→mtp1 切换恰好是"上一步长投机（乐观值大、被拒概率高）→ 本步短投机"的组合，乐观接受的偏差最大，所以**切换处最易暴露**。

### 2.3 为什么"平时不报、切换才报"

- **稳态 mtp3 不切换**：每步 `prev_num_draft_len` 都是 3，乐观偏差在稳态下被 deferred correction 持续修正，且接受率稳定时偏差小、被 correction 覆盖。
- **mtp3→mtp1 切换瞬间**：`prev_num_draft_len`（=3，上一步）与本步实际投机（=1）的语义跨度最大，乐观推进的 state 与真实接受的 state 偏差累积到阈值，mamba 递归放大 → 精度异常。这与现象"切换过程易出现精度异常"精确吻合。

> ⚠️ **与上一版的区别**：上一版（误）归因为"同 step 列宽错配/混批"。在"同 step 投机长度一致"的真实约束下，列宽在同 step 内是自洽的，**真凶是跨 step 的异步乐观接受对递归 state 的不可逆污染**。下面修复方案据此重写。

## 三、代码级修复方案（围绕"递归 state 不可乐观推进"）

> 核心思路：**mamba 递归 state 的推进必须用"真实接受数"，绝不能用"乐观接受数"**；若架构上必须乐观（异步调度），则要么对 state 推进**单独同步真实 num_accepted**、要么**对 state 部分可回滚**。三个修复点按代价从低到高。

### 修复点 1（最稳，推荐）：mamba state 推进强制等真实 num_accepted（对 GDN 层关闭乐观）

`output_token_ids` 可以乐观占位再事后修正（KV 模型无副作用），但 **mamba state 的推进步数不可乐观**。修复：让 GDN forward 推进 state 时，用**同步过的真实 `num_accepted_tokens`**，而非 `prev_num_draft_len` 派生的乐观值。

```python
# qwen_gdn_linear_attn.py forward — 推进 state 前，num_accepted 必须是真实值
# 当前：num_accepted_tokens = attn_metadata.num_accepted_tokens  (:1318) 可能含乐观成分
# 修复：GDN 层强制同步上一步真实接受数（牺牲该层的异步性）
num_accepted_tokens = sync_real_num_accepted(attn_metadata)   # 阻塞等 prev verify 的真实结果
```
**代价**：GDN 层失去异步收益（要等上一步真实 num_accepted），但 GDN 只占 hybrid 的部分层，影响可控。**收益**：state 推进步数 = 真实接受数，从根上杜绝多推进。

### 修复点 2（折中）：mamba state 支持"乐观推进 + 回滚"（ping-pong 影子状态）

借鉴 SGLang 的 ping-pong 思路（见 [[20260624-170721-qwen3.5-hybrid-动态投机-主模型与MTP-kvcache管理-深度分析]]）：乐观推进写**影子 state buffer**，真实 num_accepted 回来后，用"接受到第 k 步"的影子 state 覆盖正式 state、丢弃多推进部分。
```python
# 推进时写影子 buffer，保留每个中间步的 state 快照
shadow_states[step] = advance_mamba_state(...)   # mtp3: 存 3 个中间态
# 真实 num_accepted=k 回来后：
ssm_state = shadow_states[k - 1]                 # 取第 k 步的，丢弃 k 之后的乐观推进
```
**代价**：每层多存 max_spec 份影子 state（显存 + 拷贝）。**收益**：保留异步性。这正是 hybrid+投机的通用解。

### 修复点 3（保险）：切换 step 显式 barrier，重置 has_initial_state 链

mtp3→mtp1 切换的那个 step，强制 GDN 的 `has_initial_state`（[qwen_gdn_linear_attn.py:1300](vllm/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py)）承接的是**已修正的正式 state**，而非乐观 state：在投机长度发生变化的 step 前插入一次真实 num_accepted 同步（barrier），确保 state 链不带乐观污染进入新长度。

### 修复点 4（vllm-ascend NPU 算子侧）

vllm-ascend 的 `recurrent_gated_delta_rule`（[csrc/attention/recurrent_gated_delta_rule/](vllm-ascend/csrc/attention/recurrent_gated_delta_rule/)）是 GDN 的 NPU 原生算子。无论选修复点 1/2，**state 推进步数的"真实 vs 乐观"语义必须在 NPU 算子调用侧对齐**——若 NPU 路径同样按上层传入的 num_accepted 推进 state，则上层修复（传真实值）即可覆盖 NPU；若 NPU 算子内部另有 state 累积逻辑，需同步核对 `recurrent_gated_delta_rule.cpp` 的 state 更新。⚠️ 本次未逐行核对 NPU 算子的 state 推进语义（见存疑）。

## 四、为什么这些修改能"完全解决"——理论 + 代码双重论证

### 4.1 理论论证（不变式角度）

精度正确的**充要不变式**：
> 每个序列在 step N 结束时，mamba 的 conv_state/ssm_state 必须**恰好推进了 step N 真实接受的 token 数**，不多不少；step N+1 承接的 initial_state 必须是这个"恰好推进"的 state。

出错的本质是**违反了这个不变式**：乐观推进让 state 多走了 `(乐观 - 真实)` 步，且不可逆。

- **修复点 1**：直接用真实 num_accepted 推进 → state 推进步数 = 真实接受数，不变式**直接成立**。
- **修复点 2**：乐观推进到影子 buffer，真实值回来后取第 k 步快照覆盖 → 等效于"只推进真实步数"，不变式**等效成立**。
- 二者都把 state 推进锚定到**真实接受数**，无论投机长度怎么跨 step 切换，state 永远只前进真实接受的步数 → **多推进/不可逆污染在数学上不可能发生**。

### 4.2 代码论证（覆盖触发条件）

新约束（同 step 长度一致）下，触发条件只有一条主线：

| 触发条件 | 出错原因 | 对应修复 |
|---------|---------|---------|
| 跨 step 投机长度切换 + 异步乐观接受 | state 按 `prev_num_draft_len`（乐观）多推进，不可回滚 | 修复点 1（真实值推进）或 2（影子回滚） |
| 切换 step 承接乐观 state | has_initial_state 链带污染 | 修复点 3（barrier 重置链） |
| NPU 算子 state 推进语义不一致 | NPU 侧另有累积 | 修复点 4（对齐 NPU） |

主线由修复点 1（或 2）闭环，3/4 是保险与平台适配 → 完全消除此类精度风险。

### 4.3 验证方法（落地闭环）

1. **单测（决定性）**：连续 step 切换 mtp3→mtp1→mtp3，对比"全程关闭异步（同步基准）"与"开启异步+修复"的逐 token logits。**mamba 递归错一步必发散**，故 token 级 bit-exact = state 推进零偏差 = 修复成功。
2. **state 快照断言**：在 GDN 层 forward 后，断言 `state 推进步数 == 真实 num_accepted`（修复前在切换 step 必不等，修复后恒等）。
3. **E2E**：长序列 + 动态投机，对比"投机解码"与"纯自回归贪心"输出一致性——投机解码理论上应与贪心 bit-exact，切换处不一致即未修复干净。

## 五、待核实/存疑

1. **vllm-ascend NPU 算子的 state 推进语义**（修复点 4）：`recurrent_gated_delta_rule.cpp` 内部 state 累积是否完全由上层 num_accepted 控制，未逐行核对 —— ❓ 若 NPU 内部另有逻辑，需按其实现调整。
2. **`num_accepted_tokens` 进入 GDN forward 时是否已含乐观成分**：本文判断异步调度下 `attn_metadata.num_accepted_tokens`（qwen_gdn_linear_attn.py:1318）可能源自 `prev_num_draft_len` 乐观值，需在 worker→metadata 的传递链确认其是"真实"还是"乐观"——这是修复点 1 是否必要的前提，**最高优先级待核实**。
3. **是否关闭异步调度就能规避**：若 `use_async_scheduling=False` 时 num_accepted 是当前 step 真实值，则该 bug 仅在异步调度下出现——可先用"GDN 模型禁用异步"快速验证根因（代价是吞吐）。
4. **deferred correction 是否已覆盖 state**：`correction`（gpu_model_runner.py:1479）目前修正 output_token_ids，需确认它是否**完全没碰** mamba state（本文假设没碰，若已有部分 state 修正逻辑，方案需调整）。
5. **cudagraph 与跨 step 长度切换的交互**：graph 按 num_spec 捕获，切换长度时 state buffer 的 has_initial_state 链在 graph 重放下是否正确承接，未确认。
