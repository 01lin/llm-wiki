## 一、计算/通信效率层（大规模 EP 下的核心瓶颈）

### 1.1 计算-通信重叠：Two-Batch Overlap（TBO / DBO） — ✅ 已有，是大规模 EP 的关键抓手

**问题**：大规模 EP（专家并行）下，MoE 的 dispatch/combine all-to-all 通信占比极高，A2 这类跨卡带宽弱的硬件上更甚。通信时算力空转 = 集群利用率被腰斩。

**已有能力**：
- SGLang **TBO**（Two-Batch Overlap）：`two_batch_overlap.py` 把一个 batch 拆成两个微批，`MaybeTboDeepEPDispatcher`（[two_batch_overlap.py:1054](sglang/python/sglang/srt/batch_overlap/two_batch_overlap.py)）用 `num_inner_dispatchers = 2 if is_tbo_enabled()`（:1057）—— **微批 A 的 MoE 通信与微批 B 的计算重叠**。配套 `TboForwardBatchPreparer`（:484）、`TboCudaGraphRunnerPlugin`（:317，与图模式叠加）、`TboDPAttentionPreparer`（:374，DP attention 下的 gather 重叠）。
- vllm-ascend 侧 `model_runner_v1.py` 有 micro-batch overlap 痕迹（DBO，Dual-Batch Overlap）。

**进一步优化点**：
1. TBO 的微批切分粒度（颗粒度）在 A2 带宽下的最优值需调优——切太细 host 开销大，切太粗重叠不足。
2. TBO × CP × 投机解码三者叠加时的调度协同（`split_spec_info`，two_batch_overlap.py:193 已有，但三者同时开的稳定性待验证）。

### 1.2 MoE 通信：DeepEP / 低延迟 dispatch-combine — ✅ 已有，昇腾已适配

**已有能力**：
- SGLang token_dispatcher 全家桶：`deepep.py` / `moriep.py` / `mooncake.py` / `nixl.py` / `flashinfer.py`（多通信后端可插拔）。
- **DeepEP low-latency 模式**：`enable_low_latency`（[deepep.py:193/238](sglang/python/sglang/srt/layers/moe/token_dispatcher/deepep.py)）+ `set_dispatch_mode_as_low_latency`（:278）+ RDMA buffer + hook 异步回调（:82）——decode 阶段小 batch 的低延迟专家分发。
- **昇腾 DeepEP 算子**：`sgl-kernel-npu/csrc/deepep/`（deep_ep.cpp/hpp + ops/ops2）——昇腾原生 all-to-all。

**进一步优化点**：
1. 昇腾 DeepEP 的 low-latency 路径成熟度 vs GPU 版（ops2 看似是迭代版本，覆盖度待核实）。
2. dispatch-combine 与 attention 计算的细粒度流水（当前 TBO 是 batch 级，可探索算子级流水）。

### 1.3 图模式：NPU Graph / ACLGraph 降 host 开销 — ✅ 已有

**问题**：大规模集群 decode 阶段，单 step 计算量小，**host 侧 Python 调度开销（launch、调度、采样）占比高**，成为吞吐天花板。

**已有能力**：
- SGLang NPU graph：`NPUGraphRunner(DecodeCudaGraphRunner)`（[npu_graph_runner.py:87](sglang/python/sglang/srt/hardware_backend/npu/graph_runner/npu_graph_runner.py)）+ `npu_cudagraph_backend.py`，捕获 decode 计算图 replay，消 host 开销。
- 与投机解码叠加：`eagle_draft_npu_graph_runner.py` / `multi_layer_eagle_draft_extend_npu_graph_runner.py`（draft 模型也走 graph）。
- vllm-ascend：`dsa_v1.py` / `attention_v1.py` 有 cudagraph 痕迹。

**进一步优化点**：动态 shape（变长 batch/seq）下 graph 的捕获覆盖率——长上下文 + 变并发场景，graph 难全覆盖，padding 浪费 vs 多 graph 捕获的内存权衡。

## 二、算法-系统协同层

### 2.1 投机解码在集群侧的部署：MTP / Eagle — ✅ 已有，但集群级编排是缺口

**问题**：投机解码（draft + verify）能把 decode 吞吐翻倍，但在 PD 分离集群里，**draft 模型放哪、verify 在 D 节点怎么调度、draft 与 EPLB/CP 怎么共存**是系统级难题。

**已有能力**：
- vLLM：`v1/spec_decode/` 全套——`EagleProposer`（[eagle.py:10](vllm/vllm/v1/spec_decode/eagle.py)）、medusa、ngram、suffix_decoding、`extract_hidden_states`。
- SGLang：DeepSeek V4 的 **MTP（Multi-Token Prediction）** 深度集成进稀疏后端——`dsa_backend_mtp_precompute.py` / `dsa_mtp_verification.py`、`nsa_mtp_verification.py`，以及 NPU graph runner 对 eagle draft 的支持。
- 模型侧 MTP：`deepseek_v4_nextn.py` / `qwen3_moe_mtp.py`。

**进一步优化点 / 缺口**：
1. **PD 分离下投机解码的角色编排**：draft 计算放 P 还是 D？MTP 与 DSA topk 的协同（MTP 预测的 token 也要过 indexer 选择），`dsa_mtp_verification` 已有但集群级调度策略未见。
2. 投机解码的接受率随负载/上下文变化，**动态开关投机**（高负载时关、低负载时开）的自适应策略——代码未见，是缺口。

### 2.2 量化：W8A8 / FP8 / KV 量化 — ✅ 已有，与稀疏 KV 的叠加是看点

**已有能力**：
- vllm-ascend `quantization/`：`fp8_config.py`、`modelslim_config.py`（昇腾 ModelSlim）、`compressed_tensors_config.py`、`method_adapters.py`。
- 实证：测试配置里大量 `DeepSeek-*-W8A8`、`W8A8FP8 dynamic quantization on Ascend950`（最新 commit 主题）。
- DSA 侧已有 c8 KV scale：`model_runner_v1.py` 的 `c8_k_scale_cache_dtype`（前篇 5.x 走读时见）。

**进一步优化点**：量化 × 三档稀疏压缩 KV 的叠加——c4/c128 压缩态再做 KV INT8 量化的精度/收益权衡，是 A2 显存进一步压榨的方向。

## 三、集群编排层（最大的真实缺口所在）

### 3.1 全局 KV-aware 路由 / 亲和调度 — ⚠️ 部分有，集群级全局索引是缺口

**问题**：大规模集群多实例下，请求路由到"已有该前缀 KV 的实例"才能命中复用。这是 agentic 多轮 + 长上下文场景吞吐的命门（前篇问题二已点出）。

**已有能力**：
- SGLang 有 router 雏形：`entrypoints/ollama/smart_router.py` 的 `SmartRouter`（[smart_router.py:23](sglang/python/sglang/srt/entrypoints/ollama/smart_router.py)）；MoE 层内 `layers/moe/router.py`（这是模型内专家路由，不是请求路由，别混）。
- 调度模拟器 `debug_utils/schedule_simulator/`（routers: round_robin/sticky/random + schedulers + gpu_state + metrics）——**有离线评估调度策略的基建**，说明团队在研究路由策略。

**缺口**：
1. **集群级全局前缀索引**：哪个实例/远端池持有哪段前缀 KV，需要一个全局可查的索引服务——当前 cache-aware 仍偏单实例（Radix 树是实例内的）。
2. **KV-aware + 负载 的联合路由**：既要命中前缀又不能把请求都压到一个热实例，sticky_router 是雏形，生产级联合决策待构建。

### 3.2 P/D + MoE 的统一弹性闭环 — ❓ 缺口（前篇已点，此处归位到编排层）

前篇问题三已详述：EPLB（专家重排，昇腾有 `dynamic_eplb`）与 PD 扩缩是**独立两条线**，缺 goodput 驱动的统一决策器；昇腾**无 elastic_ep 整机弹性**（前篇 5.6 坐实）。属本层最大缺口。

### 3.3 容错 / 故障恢复 / 滚动升级 — ❓ 本次走读未见系统性方案，标注存疑

**问题**：千卡级集群，单卡/单节点故障是常态。PD 分离下 P 或 D 节点挂掉、EP 某卡挂掉，如何快速摘除 + KV 不丢 + 不中断在途请求，是生产级硬需求。

**状态**：本次走读**未系统定位**到三个框架的故障恢复/热迁移/滚动升级方案（kv_transfer 的 HeartbeatInfo 算连接级健康检查，但实例级容错编排未见）。❓ **不确定**，需专项走读或确认是否依赖外部编排（K8s + 上层调度）。

## 四、汇总判断：优先级排序（结合 A2 + DeepSeek V4 + 框架层优先原则）

| 方向 | 现状 | 对本场景价值 | 优先级 |
|------|------|-------------|--------|
| TBO/DBO 计算通信重叠 | ✅ 已有 | A2 带宽弱，重叠收益极大 | ⭐⭐⭐ 调优即见效 |
| 全局 KV-aware 路由 | ⚠️ 雏形 | agentic 多轮命中率命门 | ⭐⭐⭐ 缺口大、价值高 |
| P/D+MoE 统一弹性闭环 | ❓ 缺口 | P/D 打满不互相拖累 | ⭐⭐⭐ 缺口大 |
| 投机解码集群编排 | ✅ 算子有/编排缺 | decode 吞吐翻倍 | ⭐⭐ 需编排层补 |
| 量化×稀疏KV叠加 | ✅ 量化有 | A2 显存进一步压榨 | ⭐⭐ |
| NPU 图模式覆盖率 | ✅ 已有 | 降 host 开销 | ⭐⭐ 动态shape待优化 |
| MoE 通信 low-latency | ✅ 已有 | decode 小batch延迟 | ⭐ 成熟度核实 |
| 容错/滚动升级 | ❓ 未定位 | 生产级硬需求 | ⭐⭐ 先确认现状 |

> **结论（对齐"框架引擎层优先于算子"）**：最高杠杆的三个是**集群编排层**的——全局 KV 路由、P/D+MoE 统一弹性、TBO 调优。它们都在框架/引擎层，不依赖改算子，且直击 A2 弱带宽 + 长上下文 + agentic 多轮的核心痛点。算子层（DeepEP/图模式/量化 kernel）已相对成熟，优先级靠后。

## 五、明确标注的存疑/缺口

1. **容错/故障恢复/滚动升级**（3.3）：未系统定位到方案，❓不确定是否依赖外部编排。
2. **投机解码的 PD 角色编排 + 自适应开关**（2.1）：算子/verification 有，集群级调度策略未见。
3. **昇腾 DeepEP low-latency 成熟度**（1.2）：ops2 疑似迭代版，覆盖度未核实。
4. **TBO×CP×投机三者叠加稳定性**（1.1）：`split_spec_info` 已有接口，三者同开未验证。
