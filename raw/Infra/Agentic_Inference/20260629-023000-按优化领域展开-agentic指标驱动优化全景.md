> 组织维度：**按引擎子系统/优化领域分组**（KV Cache 管理 / 动态投机 / 调度），每个领域内讲清「采集哪些指标 → 优化思路 → 怎么用指标 → 推理执行时序步骤」。重点是把**优化思路和方案解释清楚**。

## 总览：三大优化领域 × agentic 指标

| 领域 | 引擎子系统 | 核心 agentic 指标 | 优化特性 |
|---|---|---|---|
| **A. KV Cache 管理** | kv_cache_manager / connector / swap | 工具阻塞、剩余轮次、前缀复用、工具返回占比 | 前缀 Pin、主动换出、段级压缩 |
| **B. 动态投机** | spec_decode/proposer | 输出段类型、分段接受率 | 段类型自适应投机长度 |
| **C. 调度** | recompute_scheduler | 剩余轮次、抢占次数、DAG 拓扑 | 价值逐出、组完成调度 |

底层逻辑贯穿三领域：**agent 知道、引擎推不出的轨迹状态（时序/结构/关系）下沉为带外信号，让引擎从"被动响应"升级为"预判式编排"。** 下面逐领域展开。

## 领域 A：KV Cache 管理优化

KV 是 910B3（单卡 64GB HBM）的硬约束。agentic 长会话（SWE R=24）+ 工具返回堆积（占上下文 79%）+ 26% 截断 → KV 是头号瓶颈。三个特性。

### A.1 采集哪些指标

| 指标 | 含义 | 采集层 |
|---|---|---|
| `expected_idle_ms` | 工具调用预期阻塞时长（未来量）| [报] |
| `prefix_reuse_rate` ρ | 跨请求共享前缀复用率 | [推] hash |
| `prefix_cache_hit_rate` | 实际命中率（< ρ 即误逐出）| [埋] |
| `tool_return_token_ratio` | 一次性工具返回占上下文比 | [推]/[报] |
| `hbm_kv_utilization` | HBM KV 实时占用 | [埋] |

### A.2 特性 A-1：共享前缀 Pin

**优化思路**：agentic 负载的 system prompt + 工具定义是跨轮高复用前缀（SWE ρ=14%、1218 token 单模板、复用 24 轮），但 prefix cache 在高并发下可能误逐出它，导致反复重算 prefill。给声明的前缀打 pin，逐出时跳过。

**怎么用指标**：联合 `prefix_reuse_rate`（高复用）+ `prefix_cache_hit_rate`（低命中=确实被误逐出）判断"该不该 pin"——单看 reuse 会盲目 pin，联合 hit_rate 才知道是否真有误逐出损失。

**执行时序步骤**：
```
① 会话建立，agent 声明 pin_prefix（system+tools 的 hash）
② 请求进入，KV 命中查找
   find_longest_cache_hit (single_type_kv_cache_manager.py:195)
   逐 block_hash 调 get_cached_block (:224)   ← 命中处采集 hit_rate（+1行 counter）
③ HBM 不足触发逐出（BlockPool 层 free queue）
   ← 【本特性介入】逐出选择时跳过 pinned block
④ pinned 前缀常驻，后续轮次稳定命中，跳过重算 prefill
```
**代码依据**：命中路径在 `single_type_kv_cache_manager.py:195` `find_longest_cache_hit`（vllm-ascend 自有），但**逐出在 BlockPool 层**（上游）——pin 插入点可能需 patch 上游，落地前先确认上游是否有引用计数原语。

### A.3 特性 A-2：工具阻塞主动换出

**优化思路**：agent 工具调用阻塞数秒~数十秒，被阻塞 seq 白占 KV slot 压低有效并发。现状是 HBM 耗尽才被动抢占。优化：阻塞前主动把该 seq KV 从 HBM 换出到 host，阻塞结束前换回。

**怎么用指标**：联合 `expected_idle_ms`（即将长阻塞）+ `hbm_kv_utilization`（HBM 紧张）+ `num_preemptions`（换它比反复抢占别人划算）三者触发主动换出。

**执行时序步骤**：
```
① agent 发起工具调用，上报 expected_idle_ms
② 调度循环 (recompute_scheduler.py:171 schedule) 主动扫描带 idle 标记的 running seq
   ← 【本特性介入】不等 allocate_slots 失败，提前选 idle seq 换出
③ 走 preempt hook (recompute_scheduler.py:302 update_state_before_preempt)
④ 底层异步换出 (cpu_npu.py:142 transfer_async → :217 swap_blocks_batch D2H)
⑤ expected_idle_ms 将尽时预取换回 (H2D)，避免换入延迟暴露在关键路径
```
**代码依据**：swap 算子（`cpu_npu.py:217`）、preempt hook（`recompute_scheduler.py:302`）、connector 全现成。增量是"主动扫描触发"。**最大风险**：动态 swap 改变 block 物理驻留，是否破坏 torchair/aclgraph 图捕获静态地址假设——需 910B3 实测（P0 关口）。

### A.4 特性 A-3：段级 KV 语义压缩

**优化思路**：SWE 工具返回占上下文 79%，多是一次性历史（Traceback、ls 输出），后续轮次不再引用。按语义段压缩/降级，而非逐 token LRU。直接降 26% 截断率（让长会话不撞上下文上限）。

**怎么用指标**：`tool_return_token_ratio`（可压缩段占比）定位压缩目标；联合段角色标注识别"一次性"段。

**执行时序步骤**：
```
① 上下文拼装时，agent 标注历史段语义角色（哪些是一次性 tool result）
② KV manager 已是压缩感知的 (single_type_kv_cache_manager.py:33 compress_ratio 贯穿 :49/:94/:179)
   ← 【本特性介入】把"语义段"映射到 block 区间，按段聚合压缩/逐出
③ 一次性工具返回段整体降级（压缩态 MLA，compress_ratio>1）
```
**代码依据**：KV 路径**已经压缩感知**（`compress_ratio` 贯穿 manager），段级压缩与既有压缩机制协同。**难点**：语义段边界与 `block_size`/`compress_ratio` 粒度对齐——可行性中等偏低，中长期项。

## 领域 B：动态投机优化

agentic 输出结构化程度高（SWE tool_call 段 27%、JSON/命令 accept rate 高），是投机解码的收益区。但受 NPU 静态 shape 约束。

### B.1 采集哪些指标

| 指标 | 含义 | 采集层 |
|---|---|---|
| `output_segment_type` | 当前生成段（thinking/tool_call/answer）| [报]/[埋] |
| `accept_rate_by_segment` | 各段历史接受率 | [埋] proposer |

### B.2 特性 B-1：段类型自适应投机长度

**优化思路**：tool_call/结构化段 accept rate 高 → 用长 draft 多赚 token；thinking 段发散 accept 低 → 短 draft 少浪费。把投机加速从"事后运行时反馈"提前为"事前按段预判"。

**怎么用指标**：`output_segment_type` 决定当前段 → 查 `accept_rate_by_segment` 先验表 → 设定该段的有效投机长度。

**执行时序步骤 + 关键约束**：
```
① agent 标注/解码状态机识别当前 output_segment_type
② 投机 proposer 提议 draft tokens
   dflash_proposer.py:28  max_query_tokens = max_batch_size × (1 + num_speculative_tokens)
   ← ⚠ num_speculative_tokens 参与静态 shape 计算（:81/:88/:242 切片）
③ 【本特性介入，必须降级】不能每步改 num_speculative_tokens（破坏 shape→图模式 recompile）
   → 改为：固定 num_speculative_tokens=K_max（shape 不变），按段动态调"有效验证长度 K_eff"（valid_len mask）
   thinking 段 K_eff 调小（早停）、tool_call 段 K_eff=K_max
④ target 验证按 K_eff，accept rate 回流校正段先验
```
**代码依据 + 否定性发现**：`dflash_proposer.py:28` 确认 `num_speculative_tokens` 参与静态 shape（query token 数、buffer、切片）→ **只看指标会推出"按段变 draft 长度"，但读代码发现这会破坏 shape 契约**，必须降级为「静态 K_cap + 动态 K_eff」（与已入库 [[20260608-124000-hybrid-speculation-mtp-suffix-概念]] 解耦思路一致）。这是代码约束倒逼的设计修正——**只看指标推不出，必须落代码才暴露**。

## 领域 C：调度优化

调度是 agentic 任务级协同的主战场。两个特性：节点级（价值逐出）和任务级（组完成）。

### C.1 采集哪些指标

| 指标 | 含义 | 采集层 |
|---|---|---|
| `remaining_turns` | session 剩余轮次 | [报] |
| `num_preemptions` | 历史抢占次数（引擎已有）| 已有 |
| `dag_fanout` / `dag_parallelism` / `join_wait` | DAG 拓扑 | [报] |

### C.2 特性 C-1：价值逐出（节点级）

**优化思路**：HBM 不足抢占时，现状按 `(priority, arrival_time)` 选，不看请求还要用多久 → 可能逐出"剩 20 轮高复用"的 session。改为按"剩余价值"选，保住还要用很多轮的。

**怎么用指标**：联合成 `remaining_value = remaining_turns / (1 + num_preemptions)`——剩余轮次高（复用价值高）且抢占少（不颠簸）的留住。

**执行时序步骤**：
```
① 请求进入调度循环 (recompute_scheduler.py:210 while)
② allocate_slots 分配 KV (:282)，返回 None=HBM 不足
③ PRIORITY 策略选抢占目标 (:348 if)
   ← 【本特性介入】(:351) key 从 (priority, arrival_time)
      改为 (priority, -remaining_value(r), arrival_time)
      读 r.num_preemptions（已有）+ r.sampling_params.extra_args["remaining_turns"]（[报]）
④ 移出 running (:353) → 归还 token_budget (:357) → 执行抢占 (:372)
```
**代码依据**：抢占点 `recompute_scheduler.py:351`（自有子类，唯一点 + `scheduler_dynamic_batch.py:244` 同构）。`num_preemptions` 引擎自动维护（`scheduler.py:1104` +=1）。~10 行，不 patch 上游。详见 [[价值逐出特性-可施工级方案设计]]（已写到可施工）。

### C.3 特性 C-2：DAG 组完成调度（任务级）

**优化思路**：gaia2 multi-agent fan-out 5.3 个并行子任务，并行度 2.6 → 早完成的子任务 KV 空占等 join（木桶效应，浪费 ≈62% 并行时段）。以 DAG 为单位调度，join 前不逐出组内前置。

**怎么用指标**：`dag_fanout>1`（启用开关）+ `dag_parallelism`（浪费规模）+ `join_wait`（等待时长）联合触发组保护。

**执行时序步骤**：
```
① agent 规划后上报 task_id + dependencies（DAG 边）
   经 sampling_params.extra_args 透传（routed_experts_prompt_start :328 先例证明可行）
② 调度循环识别同 task_id 请求为一组
③ 抢占目标选择 (recompute_scheduler.py:350 max key)
   ← 【本特性介入】加"组保护集合"：同 DAG 未完成组的请求不被选为抢占目标
   （复用 C-1 的 key 注入位）
④ 早完成的组内节点可走 A-2 主动换出（而非被动逐出），join 后统一释放
```
**代码依据**：现有调度器是请求级循环（`recompute_scheduler.py:210`），无组抽象。组保护可注入抢占 key（`:350`，复用 C-1 注入位），但"组完成"完整语义（join 同步、组级 SLO）是新增任务级子系统。`extra_args` 透传 task_id 现成。**复杂度最高，护城河最深**（Dynamo 未做）。

## 跨领域的统一抓手

三领域不是孤立的，三个系统级抓手把它们串成闭环：

1. **统一信号透传通道**：所有 [报] 指标（expected_idle_ms / remaining_turns / task_id / dag_edges）经 `SamplingParams.extra_args`（`sampling_params.py:324`）透传，一个通道服务三领域。

2. **评分函数注入点复用**：调度的抢占 key（`recompute_scheduler.py:351`）是统一的"评分式调度"注入点——价值逐出（C-1）、组保护（C-2）、换出优先级（A-2）都注入这里，不重写主循环。

3. **闭环反馈校正先验**：所有"信任 agent 先验"的优化（idle/turns/segment）都必须有运行时指标（accept_rate/hit_rate/实际阻塞）回流校正——先验失真时退化兜底，不盲信。

## 三领域优化总表

| 领域 | 特性 | 核心指标联合 | 代码介入点 | 思路一句话 | 可行性 |
|---|---|---|---|---|---|
| KV | A-1 前缀Pin | reuse×hit_rate×tools_token | BlockPool 逐出 | 高复用前缀常驻不逐出 | 采集高/pin待确认 |
| KV | A-2 主动换出 | idle×hbm_util×num_preempt | :302 hook+swap | 阻塞期腾 HBM 给在跑请求 | 中高/图模式待验 |
| KV | A-3 段级压缩 | tool_return_ratio×段角色 | :33 compress | 一次性工具返回段整体压缩 | 中/粒度对齐难 |
| 投机 | B-1 段DSL | segment_type×accept_rate | dflash:28 K_eff | 结构化段长draft/思考段短 | 降级可行 |
| 调度 | C-1 价值逐出 | remaining_turns×num_preempt | :351 key | 保住还要用很多轮的 session | **高** |
| 调度 | C-2 组完成调度 | fanout×parallelism×join | :350 key+任务层 | DAG 组同进退避免木桶 | 中/护城河 |

## 关键解释：为什么按领域组织能讲清优化思路

1. **同领域指标共享、机制协同**：KV 三特性共用 hbm_util / 都走 connector-swap-compress 一套基础设施 → 一起设计避免重复造轮子。
2. **领域内有内在优先级**：KV 领域里 A-1（pin，最易）→ A-2（换出，设施现成）→ A-3（压缩，最难），是同一子系统的渐进改造，不是孤立特性。
3. **跨领域靠统一抓手串成闭环**：三个抓手（信号通道、评分注入点、反馈校正）让三领域不各自为政——这是"从请求级优化升维到任务级系统协同"在工程上的落地形态。
