## 优化一：(remaining_turns × num_preemptions × prefix_reuse) 联合 → 价值逐出重排

### 指标联合条件
单看 `remaining_turns` 不够——一个快结束的 session 若**前缀复用率高且已被抢占多次**，逐出它反而亏。三指标联合判断"逐出谁最不亏"：
- `remaining_turns` 小（复用价值低）
- `num_preemptions` 已高（反复换进换出，再抢占成本大）
- `prefix_reuse` 低（逐出后重算代价小）

### 触发的真实代码决策点
vllm-ascend 抢占目标选择写死为二元组 key：
```python
# recompute_scheduler.py:351
preempted_req = max(self.running, key=lambda r: (r.priority, r.arrival_time))
# scheduler_dynamic_batch.py:244 同构
```
**关键发现**：引擎**已经记录** `request.num_preemptions`（`recompute_scheduler.py:163` 已用 `request.num_preemptions > 0` 做判断）——这意味着 num_preemptions 是**现成可读字段，零新增采集**。

### case 数据算收益
SWE 负载 R=24、26% 截断（高抢占压力）。现状 key 只按 priority+arrival，与"剩余价值"无关：
- 一个 R 已到 22/24 的 session（剩 2 轮）和一个 R=2/24 的（剩 22 轮）被同等对待 → 可能逐出后者，损失 22 轮的前缀复用。
- 改 key 为 `(priority, remaining_value(r), arrival_time)`，`remaining_value = remaining_turns × prefix_reuse / (1+num_preemptions)`：
  - 优先逐出"快结束 + 低复用 + 已反复抢占"的，保住"还要用很多轮 + 高复用"的。
- 收益量级：SWE ρ=14%(1218 token)、R=24 → 保住一个长 session 的前缀 ≈ 省 1218×剩余轮 的重复 prefill。

### 可行性 / 风险判断
- **可行性高**：改动落在 vllm-ascend **自有子类**（`RecomputeScheduler(Scheduler)`），一行 key 改动，不 patch 上游。
- **复用已有数据**：num_preemptions 现成；remaining_turns 需 `[报]`，但可先用 `R` 后验近似 + osl 估。
- **风险**：① priority 必须仍是第一关键字（不破坏 SLO 分层）；② `remaining_value` 计算必须全程 CPU 标量——`recompute_scheduler` 在 NPU 上，若引入 `.item()` 触发 D2H 同步会拖慢热路径（AGENTS.md 明确警告）。→ 评分用 Python 标量，不碰 device tensor。

## 优化二：(expected_idle_ms × hbm_kv_utilization × num_preemptions) 联合 → 主动换出 vs 被动抢占

### 指标联合条件
现状是 HBM 耗尽才被动抢占。联合三指标可**预判式主动换出**：
- `expected_idle_ms` 大（某 seq 即将长阻塞）
- `hbm_kv_utilization` 高（HBM 紧张，需要腾）
- 该 seq `num_preemptions` 低（换出它比反复抢占别人划算）
→ 阻塞前主动把这个 seq 换出，而非等 HBM 满了被动抢占跑得正欢的请求。

### 触发的真实代码决策点
```python
# recompute_scheduler.py:282  allocate_slots 失败才触发抢占链
new_blocks = self.kv_cache_manager.allocate_slots(...)
# :302-310  preempt hook：决定换出(host保留)还是 free(重算)
preempt_hook = getattr(self.connector, "update_state_before_preempt", None)
offloaded = preempt_hook(...)
# cpu_npu.py:217  底层换出算子现成
torch.ops._C_ascend.swap_blocks_batch(batch_src, batch_dst, batch_sizes, direction)
```
现状：**被动**——`allocate_slots` 返回 None 才进抢占链。优化：在 `schedule()` 主循环（`:210 while req_index < len(self.running)`）里，**主动**扫描带 `expected_idle` 标记的 running seq，提前走 swap，不等 allocate 失败。

### case 数据算收益
SWE 工具调用频繁（mean 24 轮，每轮一次工具返回），26% 截断 = HBM 压力实证。gaia2 fan-out 5.3 个并行子任务，join 前并行度 2.6 = 大量 seq 同时占 KV。
- 联合 `hbm_kv_utilization` 高 + `expected_idle_ms` 大时换出：把"即将空闲数秒~数十秒"的 seq 的 KV 腾给在跑请求 → 有效并发提升。
- swap 基础设施现成（cpu_npu.py），增量是"主动触发逻辑"。

### 可行性 / 风险判断
- **可行性中高**：swap 算子、preempt hook、connector 全现成；增量是主动扫描触发。
- **最大风险（坐实）**：动态 swap 改变 KV block 物理驻留，**是否破坏 torchair/aclgraph 图捕获的静态地址假设**——需 910B3 实测。这是 P0 验证关口，不能跳过。
- **expected_idle_ms 需 `[报]`**：估不准时必须运行时校正（实际换回早于/晚于预测的兜底），不盲信先验。

## 优化三：(prefix_reuse_rate × prefix_cache_hit_rate × tools_token) 联合 → 前缀 Pin + 命中率闭环

### 指标联合条件
- `prefix_reuse_rate` 高（声明的前缀确实高复用）
- `prefix_cache_hit_rate` 低（说明高复用前缀**被误逐出了**）
- `tools_token` 大（前缀主体是工具定义，pin 收益大）
→ 三者联合才能区分"该 pin"（高复用但低命中=误逐出）vs"不必 pin"（已稳定命中）。**单看 reuse_rate 会盲目 pin**。

### 触发的真实代码决策点
```python
# single_type_kv_cache_manager.py:195  命中路径
def find_longest_cache_hit(self, block_hashes, ...):
    for block_hash in itertools.islice(logical_block_hashes, max_num_blocks):  # :220
        if cached_block := block_pool.get_cached_block(block_hash, ...):       # :224
```
**关键判断**：`find_longest_cache_hit` 只**读命中链**、不做逐出决策——逐出发生在 **BlockPool 层**（上游 vLLM 的 free block queue）。所以：
- `prefix_cache_hit_rate` 采集：在 `:224` 命中处 +1 行 counter（命中 token 数）→ **L1 轻量采集，引擎已算只差导出**。
- pin 插入点：在 BlockPool 逐出选择处跳过 pinned block → **可能需 patch 上游**（除非上游已有引用计数原语）。

### case 数据算收益
SWE ρ=14%、system 1218 token **单一模板**、R=24：
- 若实测 `prefix_cache_hit_rate` < ρ（命中低于复用潜力）→ 确认存在误逐出 → pin 收益 = (ρ − hit_rate) × 1218 × R 的重复 prefill。
- pin 配额极小（1 模板 × 1218 token），几乎零挤占 → **联合判断后 pin 是无脑收益**。
- 但若实测 hit_rate 已≈ρ（已稳定命中）→ pin 边际收益≈0，**该把人力让给换出**。这就是联合指标防止盲目优化的价值。

### 可行性 / 风险判断
- **采集侧可行性高**：hit_rate 是 L1（命中处加 counter，~3 行，复用 Prometheus）。
- **pin 侧关口**：上游 BlockPool 是否有 pin/引用计数原语可复用为软 pin——落地前必须先确认，否则要 patch 上游（评审成本上升）。

## 优化四：(segment_type_ratio × accept_rate_by_segment × num_speculative_tokens 约束) 联合 → 段类型 DSL 的真实可行性

### 指标联合条件
- `segment_type_ratio`：当前在 thinking 还是 tool_call 段
- `accept_rate_by_segment`：该段历史接受率（tool_call 段高、thinking 段低）
→ 联合驱动：tool_call 段用长 draft，thinking 段用短 draft。

### 触发的真实代码决策点（含一个否定性发现）
```python
# dflash_proposer.py:28
self.max_query_tokens = self.max_batch_size * (1 + self.num_speculative_tokens)
# :81  num_query_per_req = 1 + self.num_speculative_tokens
# :88  batch_size * self.num_speculative_tokens  ← 参与 buffer/shape 预分配
```
**关键否定性发现**：`num_speculative_tokens` 在 dflash_proposer 里**参与静态 shape 计算**（query token 数、buffer 大小、token_indices_to_sample 切片）。这意味着：
- **按段动态变 draft 长度会破坏静态 shape 契约** → 在 torchair 图模式下大概率触发 recompile 或越界。
- 所以"段类型 DSL"**不能简单地每步改 num_speculative_tokens**。

### case 数据 + 可行性判断（务实降级）
SWE think:tool=73:27 → 27% 是结构化高 accept 段。但受上面约束：
- **不可行**：每 step 动态改 draft 长度（破坏 shape）。
- **可行的降级方案**：固定 `num_speculative_tokens = K_max`（静态 shape 不变），但**按段类型动态调整"实际验证长度" K_eff**（通过 valid_len mask，与已入库的 hybrid-speculation 方案 §K_cap/K_eff 解耦思路一致，见 [[20260608-124000-hybrid-speculation-mtp-suffix-概念]]）。thinking 段 K_eff 调小（早停），tool_call 段 K_eff=K_max。
- **结论**：段类型 DSL 的收益面真实（27% 结构化段），但**实现必须走"静态 K_cap + 动态 K_eff"**，不能动 num_speculative_tokens。这是代码约束倒逼的设计修正——单看指标推不出，必须读代码才知道。

## 优化五：(dag_fanout × dag_parallelism × join_wait × hbm_kv_utilization) 联合 → 组完成调度

### 指标联合条件
multi-agent 专属，四指标联合：
- `dag_fanout` > 1（有并行子任务）
- `dag_parallelism` 高（早完成的多）
- `join_wait` 大（等待久）
- `hbm_kv_utilization` 高（KV 紧张时空占代价大）
→ 联合触发组完成调度：把同 DAG 的并行子任务作为一组，join 前不逐出组内前置。

### 触发的真实代码决策点
```python
# recompute_scheduler.py:210  请求级循环（无任务/组抽象）
while req_index < len(self.running) and token_budget > 0:
    request = self.running[req_index]
# :350  抢占目标 max(self.running, key=...)  ← 组保护的注入点
```
现状是**请求级**循环，无"组"抽象。组完成调度需在抢占 key（`:350`）处加"组保护集合"：保护集合内（同 DAG 未完成组）的请求不被选为抢占目标。**复用优化一的 key 注入位**，不重写主循环。

### case 数据算收益
gaia2 fan-out 5.3、并行度 2.6、67% 有 join：
- 并行期 KV 空占浪费 ≈ (并行度−1)/并行度 = (2.6−1)/2.6 ≈ **62%** 的并行时段存在早完成子任务空占等待。
- 组完成调度回收这部分：join 前不逐出组内前置（避免逐出后重算拖垮整组），早完成的可被主动换出（联合优化二）而非被动抢占。
- **对 SWE 零收益**（fan-out=1）→ 必须 `dag_fanout>1` 作为启用开关（负载分类器判别特征）。

### 可行性 / 风险判断
- **可行性中**：组保护集合可注入现有抢占 key（`:350`），不重写循环；但"组完成"完整语义（join 同步、组级 SLO、task_id 透传）是**新增任务级子系统**，源码无现成实现。
- **task_id/dag_edges 需 `[报]`**：gaia2 的 dependencies 证明结构存在，但生产需 agent 上报。
- **承载现成**：`request.sampling_params` 已支持自定义字段（代码有 `routed_experts_prompt_start` 等先例，`:988`）→ task_id 透传有现成通道。

## 关键方法论结论

1. **指标必须联合**：单指标会误判——pin 单看 reuse_rate 会盲目 pin（优化三需联合 hit_rate 判断是否真误逐出）；价值逐出单看 remaining_turns 会逐出高复用 session（优化一需联合 reuse + num_preempt）。
2. **代码约束倒逼设计修正**：段类型 DSL 单看指标"该按段变 draft 长度"，但读代码发现 num_speculative_tokens 参与静态 shape，**必须降级为静态 K_cap + 动态 K_eff**——这是只看指标推不出、必须落代码才暴露的可行性边界。
3. **复用已有数据/字段的杠杆**：num_preemptions、sampling_params 自定义字段、find_longest_cache_hit 命中链——引擎已算/已支持，采集和透传都是轻量增量。
