## 问题二：关键指标 → 推理性能优化的推导（基于实例化数据）

逐条用真实数据驱动优化设计，而非泛泛而谈。

### 2.1 ρ=14% 单模板 → 前缀 Pin（收益可定量）

**数据**：SWE system prompt 固定 1218 token，全样本**同一模板**，占上下文 14%，平均复用 R=24 轮。
**推导**：
- 不 pin 时，prefix cache 在高并发下可能逐出 system 段 → 每次重算 1218 token prefill。
- pin 后，1218 token 常驻，每轮命中。**单 session 省算量 ≈ 1218 token × (R−1) 轮 = 1218×23 ≈ 28K token 的重复 prefill**。
**设计判断**：ρ 模板单一 → pin 配额极小（1 个模板 ×1218 token），几乎零挤占代价，收益确定。→ **前缀 pin 是本类负载的 P0**。

### 2.2 工具返回 79% → 段级 KV 压缩（潜力最大）

**数据**：SWE 上下文构成 = system 14% + 工具返回(user) 79% + ai 输出 21%（注：含重叠计数，工具返回是绝对主体）。
**推导**：
- 长会话（R=24）里，历史工具返回（Traceback、ls 输出、文件内容）大量堆积，多数后续轮次不再引用。
- 这 79% 是「一次性历史段」，可按语义段压缩/降级，而非逐 token LRU。
**设计判断**：压缩潜力 ≈ 79% 上下文 × 可丢弃比例。**结合 26% 截断率** → 段级压缩能直接降低截断（让长会话不撞上下文上限）。→ 中长期高收益，但需段角色标注 `[报]`。

### 2.3 截断率 26% → 价值逐出 + 换出的紧迫性

**数据**：SWE **26% 轨迹因 exit_context 截断**（上下文超限）。
**推导**：截断 = 上下文/KV 压力的直接证据。26% 任务因此失败（解决率仅 17%，截断是失败主因之一）。
**设计判断**：这是 KV 优化的**刚需证据**——不是锦上添花，是 26% 任务的成败线。价值逐出（保住还要用的 session KV）+ 阻塞换出（腾 HBM）直接缓解。

### 2.4 fan-out 5.3 / join 67% / 并行度 2.6 → DAG 组完成调度（multi-agent 专属）

**数据**：gaia2 每 scenario fan-out 5.3、67% 有 join、并行度 2.6、关键路径 3.5。
**推导**：
- fan-out 5.3 个子任务并行执行，各占 KV slot。
- 并行度 2.6 = 8.5 节点压到 3.5 步 → **早完成的子任务要空占 KV 等 join**。
- 浪费规模 ≈ (并行度−1)/并行度 = (2.6−1)/2.6 ≈ **62% 的并行期存在 KV 空占等待**。
**设计判断**：组完成调度以 DAG 为单位仲裁，join 前不逐出组内前置 → 回收这 62% 空占。**但对 SWE（fan-out=1）零收益** → 必须按负载类型差异化启用（L2 负载分类器的判别特征就是 fan-out>1）。

### 2.5 think:tool=73:27 → 段类型 DSL（投机长度先验）

**数据**：SWE ai 输出 73% thinking、27% tool_call（结构化命令）。
**推导**：tool_call 段（命令、JSON）结构化、accept rate 高 → 长 draft；thinking 段发散 → 短 draft。
**设计判断**：27% 的结构化段是 DSL 长 draft 的收益区；段边界检测可由 `output_segments` 先验 `[报]` 或 detokenize `[埋]`。

### 2.6 优化优先级（两类负载分别排序，数据驱动）

| 负载类型 | 判别特征 | 优化优先级（数据支撑）|
|---|---|---|
| SWE 类（单 agent 长会话）| fan-out=1, R=24, 截断 26% | 前缀 pin(ρ确定) ≈ 价值逐出(截断26%) > 段级压缩(79%) > 段DSL(27%) > 阻塞换出(待β) |
| gaia2 类（multi-agent DAG）| fan-out=5.3, join 67% | **DAG 组完成调度(并行度2.6)** > 前缀 pin > 价值逐出 |

## 问题三：轻量指标采集方案（尽量复用已有数据，最小改代码）

### 3.1 设计原则：三档「采集成本」，优先零改动

| 档位 | 手段 | 改代码量 | 覆盖指标 |
|---|---|---|---|
| **L0 零改动** | 复用 OpenAI 响应 `usage` + 网关日志 | 0 行 | 9 个 ✅可算指标 |
| **L1 读已有内部态** | 引擎内部已算、只是没透出的量，加 metric 导出 | ~每指标 1-5 行 | 5 个引擎基线 ✗ |
| **L2 新增上报** | agent/router 带新字段 | 协议层改动 | 2 个 [报] |

**核心抓手**：L0+L1 能覆盖 14/20 指标，且 L1 全是「引擎已经算了、只差导出」——这是「尽量复用已有数据」的最大杠杆。

### 3.2 L0 零改动采集（9 指标，复用 OpenAI usage + 网关日志）

直接从 `/v1/chat/completions` 响应的 `usage`（prompt_tokens/completion_tokens）+ 请求体（messages/tools）+ 网关时间戳算：
- osl_actual, has_tools/tools_token, segment_type_ratio(``` 近似), segment_length, one_shot_history_ratio, session_key(前缀hash), prefix_reuse_rate(hash比对)
- **零引擎改动**，网关侧一个 access log middleware 即可。

### 3.3 L1 读已有内部态（5 引擎基线，每指标 1-5 行）

**关键发现：这 5 个指标对应的量，vllm-ascend 内部都已经算了，只是没作为 metric 导出。** 复用现有 Prometheus 通道（见 SOP `20260608-130000-...monitoring-sop`），逐个挂载：

| 指标 | 已有内部态（已验证文件存在）| 轻量做法 |
|---|---|---|
| prefix_cache_hit_rate | `single_type_kv_cache_manager.py` 的 `find_longest_cache_hit` 已算命中链长度 | 在命中返回处 +1 行 counter.inc(hit_tokens) |
| preempt_count/recompute | `recompute_scheduler.py:302` preempt hook 已触发 | hook 处 +1 行 counter.inc() |
| hbm_kv_utilization | block pool 已知 free/used block 数 | 调度循环 +1 行 gauge.set(used/total) |
| ttft/tpot | 引擎已记 step 时间 | 复用已有 timing，+导出 |
| effective_concurrency | 调度器已知 running/waiting 队列 | +1 行 gauge.set(len(running)) |
| accept_rate_by_segment | `draft_proposer.py` 已算 accept | +按段标签的 counter |

**改动量估计**：5-6 个 metric × 平均 3 行 ≈ **20 行内**，全是「读已有变量 + Prometheus 导出」，无逻辑改动、无热路径侵入（注意 NPU 上避免 `.item()` 同步，用 CPU 标量）。

### 3.4 L2 新增上报（2 指标，仅这两个需协议改动）

只有 expected_idle_ms、priority 真正需要 agent/router 带字段（priority Dynamo 已有）。→ 把上报需求收敛到最小集，附两份实例化报告作证据（"离线数据确实推不出"）。

### 3.5 轻量采集落地排序

```
P0（零改动，1 周）：L0 网关日志 → 9 指标 + 补充的 context_truncation_rate/tool_return_ratio
P0（~20 行）：     L1 引擎 metric 导出 → 5 引擎基线，复用 Prometheus
P1（协议）：       L2 expected_idle_ms 上报（priority 复用 Dynamo）
```

**复用率**：20 指标里，**18 个靠复用已有数据/已算内部态**（L0+L1），仅 2 个需新增上报。改引擎代码 ≈ 20 行。这就是「最小改动」的量化答案。

## 总结：三问闭环

1. **指标体系**：20 指标 9✅/4△/7✗，缺失全是引擎运行时+未来量（验证三层分层准确）；建议补 4 个（截断率/工具返回占比/关键路径/并行度）达 24 指标。
2. **推理优化**：每条优化都有真实数据支撑的定量推导（pin 省 28K token、压缩潜力 79%、DAG 回收 62% 空占、截断 26% 是刚需），并按负载类型差异化排序。
3. **轻量采集**：18/20 指标复用已有数据（L0 网关 + L1 引擎已算内部态），仅 2 个需上报，引擎改动 ≈20 行。

> 待验证边界：① token 用 char/4 估，绝对值待接 tokenizer；② L1 的 20 行估计需落 PR 时按真实 metric 框架核实；③ DAG 收益 62% 是理论上界，实际受调度策略折损。
