# 基于 Agentic 应用与推理引擎协同优化的方案设计

> [!abstract] 核心命题
> 传统推理引擎（含标准 vLLM）是**无状态、请求独立、语义盲**的——只看到一个个 token 序列，看不到序列背后的 agent 执行逻辑。协同优化的本质是：把 agent 应用"知道、但引擎不知道"的执行轨迹状态，作为带外信号下沉到引擎，让引擎从"被动响应请求"升级为"理解任务轨迹、主动编排资源"。
>
> 对应主线：**从请求级优化升维到任务级系统协同**。

---

## 0. 背景：Dynamo + SGLang 的现状与局限

参考实现：[ai-dynamo/dynamo](https://github.com/ai-dynamo/dynamo) 的 agent hints 机制。

### 0.1 Dynamo 已定义的接口

**通道 1 — 请求体 `nvext.agent_hints`（4 字段）**

| 字段 | 类型 | 含义 | 是否下沉到引擎 |
|---|---|---|---|
| `priority` | i32 | 跨层软优先级 | **是**（SGLang 消费） |
| `strict_priority` | u32 | router 队列硬分层 | 否（router-only） |
| `osl` | u32 | 预期输出长度 | 否（仅 router 用） |
| `speculative_prefill` | bool | 预测性预热下一轮 | 间接（触发普通预热请求） |

**通道 2 — HTTP header 会话身份**
- `X-Dynamo-Session-ID`：会话标识
- `X-Dynamo-Session-Final`：会话是否结束（SGLang 当前版本**还不处理**这个 hint）

### 0.2 SGLang 引擎侧的对接

| Flag | 作用 |
|---|---|
| `--enable-priority-scheduling` | priority 排序内部队列，替代 FCFS，同优先级按到达时间 |
| `--radix-eviction-policy priority` | radix tree 按优先级堆逐出（低优先级先逐出），不依赖 HiCache，只控 GPU radix tree |
| `--enable-session-radix-cache` | 用归一化 session ID 给可逐出 radix KV 打标签（当前需源码编译） |

与 HiCache 两级协同：GPU 满时低优先级降级到 host，host 满时低优先级先删；`write_through` 下 GPU 逐出只是降级，真正删除发生在 host 逐出。

### 0.3 关键局限（=优化空间）

> [!warning] 现状局限
> Dynamo 只下沉了 **priority（调度+逐出）和 session ID（KV 打标签）** 两类窄信号。`osl` / `strict_priority` 都停在 router 层，没进引擎。
>
> 传的都是**标量先验**（一个 priority 数、一个 osl 数），而 agent 真正高价值的状态是**时序的、结构的、关系的**——即 agent 的执行计划。

## 1. 有价值的 Agent 状态信息 → 推理优化点全集

按三个引擎不可见的维度归类：**时间维（未来会发生什么）、结构维（这段 token 流是什么）、关系维（请求之间的关系）**。

### 1.1 时间维信息

| Agent 状态信息 | 引擎盲区 | 可优化的推理过程 | 收益 | 复杂度 |
|---|---|---|---|---|
| 下一轮稳定前缀（模板稳定/可变切分） | 等本轮结束才知道下一轮 | KV 预计算/预留：decode 阶段就预热下一轮稳定前缀 | 多轮 TTFT 进一步压缩，利用 decode 空闲算力 | 中 |
| 工具调用阻塞时长预告 | 不知道某 session 即将空闲数十秒 | KV 主动换出换入：阻塞期降级 KV 到 host，释放 HBM | 解决长尾任务占 KV slot 不释放，提升有效并发 | 中高 |
| 剩余轮次预算（max_iterations 进度） | 不知道哪些 session 快结束 | 逐出决策升级：按"剩余复用价值"而非纯 LRU/priority | 命中率提升，KV 留给真正还要用的 session | 低 |
| 输出长度预期（osl，已有但未下沉） | 不知道要生成多长 | batch 组织、投机长度、显存预留 | batch 更紧凑、减少重调度 | 低 |

### 1.2 结构维信息

| Agent 状态信息 | 引擎盲区 | 可优化的推理过程 | 收益 | 复杂度 |
|---|---|---|---|---|
| 输出结构类型（thinking/tool_call/answer 占比） | 对所有输出段一视同仁 | 动态投机长度（DSL）按段类型切换：结构化输出用长 draft，thinking 用短 draft | 投机加速从"事后反馈"变"事前预判"，长输出尤其有效 | 中 |
| 历史段语义角色（哪些是一次性工具返回、可压缩） | 只能逐 token LRU | 段级 KV 压缩/逐出：语义段而非 token 粒度 | 超长上下文 KV 占用大降，提升并发 | 高 |
| 生成格式约束（JSON schema/工具参数结构） | 被动接收约束解码 | 投机解码 + 约束解码协同：结构位置 accept rate 接近 1 | 结构化段近乎免费生成 | 中 |

### 1.3 关系维信息

| Agent 状态信息 | 引擎盲区 | 可优化的推理过程 | 收益 | 复杂度 |
|---|---|---|---|---|
| 请求优先级（priority，已有） | 默认 FCFS | 队列排序、抢占、KV 逐出 | 关键路径请求优先 | 低 |
| Multi-agent DAG 拓扑（请求间依赖/join 点） | 视每个请求独立 | 组完成调度：join 前置请求协同完成，避免木桶效应 | 解决 multi-agent 同步等待的 KV 空占和尾延 | 高 |
| 共享前缀显式声明（system prompt/工具定义/few-shot） | Prefix Cache 被动发现，可能误逐出 | 前缀级 pin：高复用前缀常驻不逐出 | 命中率从 <30% 提升至 >60% | 低 |
| 会话边界（session 开始/结束） | 不知道 KV 何时可彻底释放 | 会话结束主动释放 KV | 及时回收，减少碎片 | 低 |
| 请求幂等/可中断语义 | 不敢激进抢占 | 安全抢占：可重试请求可被 kill 重来 | 抢占调度更灵活 | 中 |

## 2. 协同优化整体架构

### 2.1 三个设计原则

1. **泛化性**：协议层语义声明式——应用只声明"我是什么状态"，不关心引擎怎么用。
2. **解耦性**：信号采集、决策翻译、引擎执行三层分离（Dynamo 已证明 router/engine 解耦可行）。
3. **自适应**：agent 先验可能不准（osl 估错、阻塞估偏），必须有运行时反馈闭环校正，不盲信声明。

### 2.2 四层架构

```
┌─────────────────────────────────────────────────────────────┐
│ L0  Agentic 应用层（多应用并发，负载差异大）                   │
│     Code Agent │ Search Agent │ Multi-Agent DAG │ 运维 Agent  │
└───────────────────────────┬─────────────────────────────────┘
                            │ 状态信号上报（带外元数据，执行轨迹关键节点）
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ L1  统一状态协议层（兼容性/泛化性入口）                         │
│     时间维: osl/阻塞时长/剩余轮次                              │
│     结构维: 输出段类型/历史段角色/格式约束                      │
│     关系维: DAG拓扑/共享前缀/优先级/会话/可中断                 │
│     [归一化采集：应用声明语义，协议层翻译引擎差异]               │
└───────────────────────────┬─────────────────────────────────┘
                            │ 语义信号
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ L2  协同决策层（多 Agent 编排 + 负载感知策略）                  │
│     任务级调度器     │ KV 生命周期管理 │ 弹性策略寻优 │ 投机调控│
│     DAG组完成/抢占    │ 预热/换出/价值逐出│ PD配比/并行  │ 段类型DSL│
│     [把语义信号翻译为引擎可执行的调度/内存指令]                 │
└───────────────────────────┬─────────────────────────────────┘
                            │ 下沉为引擎参数/指令         ▲
                            ▼                          │ 运行时反馈
┌─────────────────────────────────────────────────────────────┐
│ L3  推理引擎执行层（vllm-ascend / SGLang 内核）                │
│     优先级调度队列  │ 分级KV/RadixCache │ 自适应批/PD │投机内核 │
│     (替代FCFS)      │ 价值堆逐出+段压缩  │ 长短分离组批 │MTP/Suffix│
│     [感知 agent 轨迹的引擎，区别于"只收请求"的传统引擎]         │
└───────────────────────────┬─────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────────┐
│     昇腾算力底座（910B/C，HBM→DRAM→NVMe 分层）                 │
└─────────────────────────────────────────────────────────────┘

闭环：引擎运行时指标（accept率/KV命中/队列深度）回流，校正上层先验
```

### 2.3 各层职责

- **L0 应用层**：在执行轨迹关键节点（轮次开始、工具调用前、规划后）上报独有的执行计划信息——不报引擎能自己推断的东西。
- **L1 协议层**：三维信息归一化采集。应用只声明语义，协议层适配各引擎差异（如 priority 极性归一化，参考 Dynamo 对 vLLM "低值即高优" 的处理）。
- **L2 决策层**：把语义信号翻译成引擎可执行指令。四模块：任务级调度器（DAG组完成+抢占）、KV 生命周期管理（预热/换出/价值逐出/pin）、弹性策略寻优（聚合多 agent 负载调 PD配比和并行）、投机调控（段类型先验喂 DSL）。
- **L3 引擎层**：从无状态请求处理器变成 agent 轨迹感知执行器。
- **闭环反馈**：运行时 accept rate / KV 命中率 / 队列深度回流 L1/L2，防止盲信不准先验。

## 3. 多 Agent 并发与负载差异的处理

### 3.1 负载差异（不同应用）—— 靠 L1 语义抽象屏蔽
Code Agent（输出长、结构化多）、Search Agent（轮次多、工具阻塞频繁）都归一化成统一三维信号。L2 弹性策略寻优**聚合**所有在跑 agent 的信号，算出集群混合负载画像，动态调整全局策略，而非为每种应用硬编码。

### 3.2 多 Agent 同时运行 —— 靠 L2 任务级调度器
引入"任务"作为调度单元（而非请求）：
- 同一 multi-agent 任务的多请求经 DAG 拓扑识别为一组，做组完成调度，避免木桶效应（早算完的 worker KV 空占着等慢的）
- 不同任务间靠 priority + 剩余价值仲裁资源
- 会话级 KV 复用让同一 agent 多轮共享前缀高效命中

## 4. 对比传统 vLLM 的差异化优势

> [!note] 根本区别
> 传统引擎优化的是"单请求怎么算得快"（天花板=单点算子/内核效率）；协同引擎优化的是"整个 agent 任务轨迹怎么编排得高效"（打开任务级资源编排空间）。

| 维度 | 传统 vLLM | 协同优化引擎 |
|---|---|---|
| 调度单元 | 独立请求，FCFS | 任务（DAG感知），优先级+组完成 |
| KV 逐出 | LRU（纯时间局部性） | 剩余复用价值（语义局部性） |
| KV 生命周期 | 被动随请求结束 | 主动预热/阻塞期换出/会话结束释放 |
| 投机长度 | 固定 or 纯运行时反馈 | 输出段类型先验 + 反馈修正 |
| 组批 | 长短混批阻塞 | 按 osl/段类型分离组批 |
| 并行策略 | 静态部署 | 多 agent 聚合负载感知动态寻优 |
| Prefix 复用 | 被动发现，可能误逐出 | 显式 pin，保障命中率 |

## 5. 收益场景与落地路径排序

### 5.1 近期高杠杆（低-中复杂度，收益明确）

- [ ] **工具阻塞预告 → KV 主动换出**：解决长尾任务占 KV slot 不释放（agentic 集群有效并发低的头号原因）。与 Ascend HiCache 分层卸载天然契合。
- [ ] **共享前缀显式 pin**：保障 Prefix Cache 命中率（目标 <30%→>60%），实现简单。
- [ ] **剩余轮次 → 价值逐出**：逐出策略从 LRU 升级，改动小。
- [ ] **输出段类型 → DSL 先验**：接上已有 DSL 工作，用 agent 先验补足运行时反馈滞后。

### 5.2 中长期差异化（高复杂度，护城河）

- [ ] **Multi-Agent DAG 组完成调度**：解决多 agent 同步等待的 KV 空占和关键路径拖尾。Dynamo 当前完全没碰，最有想象空间。
- [ ] **段级 KV 语义压缩**：把一次性工具返回的历史段语义压缩，而非逐 token LRU。

### 5.3 优化空间的本质判断

> [!tip] 最大未开发空间
> 把 agent 的**时序信息（未来要等多久、还有几轮）和关系信息（请求间依赖）**真正下沉到引擎，让引擎"预判式"编排 KV 和算力，而非被动响应。这恰好是 Ascend 上可做差异化、且 GPU 阵营也还没做透的地方。

## 6. vllm-ascend 落地切入点（待用 Claude Code 展开）

> 以下为代码方案设计的 TODO 锚点，留待 Claude Code 展开。

### 6.1 工具阻塞预告 → KV 换出
- 接口：在请求 metadata 增加 `expected_idle_ms` 字段
- vllm-ascend 侧：`ModelRunner` 调度循环识别 idle 标记的 seq，触发 KV block 从 HBM 降级到 host（复用现有 swap 机制 / NIXL 传输）
- 关键点：换入时机预测（阻塞快结束时提前换回），避免换入延迟暴露在关键路径
- 难点：与 torchair graph mode 的兼容（动态 swap 是否破坏图捕获）

### 6.2 共享前缀 pin
- 接口：`pin_prefix: bool` 或 prefix hash 声明
- vllm-ascend 侧：RadixCache / PrefixCache 增加 pin 标记位，逐出时跳过 pinned 节点
- 关键点：pin 配额管理，避免 pin 过多挤占动态 KV 空间

### 6.3 剩余轮次 → 价值逐出
- 接口：`remaining_turns_estimate: u32`
- vllm-ascend 侧：KV block 逐出评分函数从 LRU 改为 `score = f(recency, remaining_value)`
- 关键点：评分函数权重调参，与 priority 逐出策略融合

### 6.4 输出段类型 → DSL
- 接口：`output_segments: [{type, expected_len}]`
- vllm-ascend 侧：投机解码模块按当前生成段类型查先验表调 draft 长度，叠加运行时 accept rate 修正
- 关键点：段类型边界检测（何时从 thinking 切到 tool_call），与现有 DSL 阈值机制融合
