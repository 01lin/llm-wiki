# 价值逐出（Value-Aware Preemption）特性 — 可施工级方案设计

> 本文按用户四问逐步深入，对**单个特性**做到能落 PR 的颗粒度：① 指标含义 → ② 方案+执行时序+代码依据 → ③ case 收益预估 → ④ 复杂度/范围/可行性/泛化性。
>
> 选这个特性的理由：在前几轮 5 条优化里，价值逐出**可行性最高**（落 vllm-ascend 自有子类、复用已有 `num_preemptions` 字段）、**收益最明确**（SWE R=24 长会话）、**最能讲透时序**。先把它做到可施工，作为后续特性的范式。
>

> 数据 case：SWE-agent（R=24/ρ=14%/截断26%）、gaia2（fan-out5.3）。

## 第 1 问：需要哪些指标，含义是什么

价值逐出的核心是回答「HBM 不够时，逐出**哪个** running 请求最不亏」。需要 4 个指标，分两类：

### 1.1 引擎已有（零新增采集）

| 指标 | 含义 | 代码出处（实测）|
|---|---|---|
| `num_preemptions` | 该请求历史被抢占次数。越高 = 反复换进换出，再抢占成本越大 | `request.py:171` 初始化，`scheduler.py:1104` 每次抢占 `+=1`，引擎自动维护 |
| `priority` | 请求优先级（SLO 分层）| `request.py:83`，必须保持为第一关键字 |
| `arrival_time` | 到达时间 | `request.py:95` |

### 1.2 需 agent 上报（[报]，经 SamplingParams 透传）

| 指标 | 含义 | 透传机制（实测）|
|---|---|---|
| `remaining_turns` | 该 session 还剩几轮。小 = 复用价值低，可优先逐出 | 经 `SamplingParams.extra_args: dict`（`sampling_params.py:324`）透传；先例 `routed_experts_prompt_start`（`:328`）证明自定义字段可行 |

### 1.3 指标联合的「剩余价值」定义

```
remaining_value(r) = remaining_turns(r) / (1 + num_preemptions(r))
```
- 分子 remaining_turns：还要用很多轮 → 留住（复用价值高）
- 分母 (1+num_preemptions)：已反复抢占 → 再抢占不划算 → 降低保护
- **联合意义**：单看 remaining_turns 会保住一个"剩很多轮但一直在颠簸"的请求；除以 num_preemptions 后，把"颠簸大户"释放掉，整体更优。

## 第 2 问：优化方案 + 执行时序 + 代码实现步骤

### 2.1 方案设计：改抢占目标选择

**现状**（`recompute_scheduler.py:348-351`）：
```python
if self.policy == SchedulingPolicy.PRIORITY:
    preempted_req = max(self.running, key=lambda r: (r.priority, r.arrival_time))
```
按 `(priority, arrival_time)` 选——priority 最高（值最大=最该逐出）、到达最晚的被逐出。**完全不看请求还要用多久**。

**优化**：插入 remaining_value 作为第二关键字：
```python
preempted_req = max(self.running, key=lambda r: (r.priority, -remaining_value(r), r.arrival_time))
```
- priority 仍是第一关键字（不破坏 SLO 分层）
- `-remaining_value`：剩余价值**低**的优先被逐出（负号使 max 选到价值最低者）
- arrival_time 兜底

### 2.2 执行时序逻辑（哪一步用哪个指标）

调度主循环 `schedule()`（`recompute_scheduler.py:171`）单步时序：

```
① 请求进入调度循环           :210  while req_index < len(self.running)
      ↓
② 尝试分配 KV slot           :282  allocate_slots(request, num_new_tokens)
      ↓ 返回 None（HBM 不足）
③ 判断调度策略               :348  if self.policy == PRIORITY
      ↓
④【本特性介入】选逐出目标     :349  max(self.running, key=...)
   读取指标：
     - r.priority           （已有，第一关键字）
     - remaining_value(r)   ← 读 r.sampling_params.extra_args["remaining_turns"]
                              + r.num_preemptions（已有）
     - r.arrival_time       （已有）
      ↓
⑤ 移出 running               :353  self.running.remove(preempted_req)
      ↓
⑥ 归还 token_budget          :357  token_budget += num_scheduled_tokens.pop(...)
      ↓
⑦ 执行抢占（换出/free）       :372  self._preempt_request(preempted_req, ...)
```

**关键**：本特性只动 ④（一行 key），其余步骤（②分配、⑤移出、⑥归还、⑦执行）完全复用现有逻辑。指标只在 ④ 读，不进入 ②⑦ 的热路径计算。

### 2.3 具体实现步骤（可落 PR）

**Step 1 — 信号透传**（agent → 引擎）
agent 在请求的 `extra_args` 带 `remaining_turns`：
```python
# 应用侧（agent harness 构造请求时）
SamplingParams(..., extra_args={"remaining_turns": 8})
```
引擎侧无需改透传——`extra_args` 是 upstream 已有通道（`sampling_params.py:324`）。

**Step 2 — 定义 remaining_value 辅助函数**（vllm-ascend 自有，新增）
```python
# recompute_scheduler.py 内新增模块级函数
def _remaining_value(r) -> float:
    ea = getattr(r.sampling_params, "extra_args", None) or {}
    rt = ea.get("remaining_turns")
    if rt is None:
        return 0.0  # 无上报 → 退化为不影响排序（价值=0，等价于旧行为兜底）
    return float(rt) / (1.0 + r.num_preemptions)   # 全程 CPU 标量，无 device tensor
```

**Step 3 — 改抢占 key**（一行）
```python
# recompute_scheduler.py:351
- key=lambda r: (r.priority, r.arrival_time),
+ key=lambda r: (r.priority, -_remaining_value(r), r.arrival_time),
```

**Step 4 — 同步 scheduler_dynamic_batch.py:244**（同构一行，保持两调度器一致）

**Step 5 — 兜底与开关**
- `remaining_turns` 缺失 → `_remaining_value` 返回 0，排序退化为旧行为（安全）。
- 加配置开关 `enable_value_aware_preempt`（默认 False），灰度上线。

### 2.4 代码依据解释（为什么这样改是对的）

- **为什么落 `:351`**：这是 PRIORITY 策略下**唯一**的抢占目标选择点（`:348` if 分支）。grep 确认只此一处 + `scheduler_dynamic_batch.py:244` 同构，改这两处即全覆盖。
- **为什么用 extra_args 不新增字段**：`routed_experts_prompt_start`（`:328`）证明 vllm-ascend 已用 SamplingParams 自定义字段；extra_args 是 dict，更灵活，不改 SamplingParams 类定义。
- **为什么 num_preemptions 直接读**：`scheduler.py:1104` 引擎每次抢占自动 `+=1`，是 Request 生命周期内自动维护的状态，读它零成本。
- **为什么必须 CPU 标量**：`recompute_scheduler` 跑在 NPU 调度侧，AGENTS.md 警告 `tensor.item()` 触发 D2H 同步拖慢热路径。`_remaining_value` 全用 Python float，不碰 device tensor。

## 第 3 问：基于 case 数据的收益预估

### 3.1 SWE 负载（R=24，26% 截断）

**场景还原**：SWE 是长会话（mean R=24），26% 因 exit_context 截断 = HBM/KV 压力实证，抢占频繁发生。
**现状损失**：抢占按 arrival_time 选 → 可能逐出一个 `remaining_turns=20`（剩 20 轮、ρ=14% 高复用）的请求。逐出后该 session 后续 20 轮全部 prefix cache miss → 每轮重算 ρ×ctx ≈ 1218 token system + 历史。
**优化后**：remaining_value 把"剩 20 轮"的请求保护住，优先逐出"剩 2 轮"的。
**收益量级（单次抢占避免的重算）**：
```
保住一个剩 R_rem 轮、前缀 P_tok 的 session ≈ 省 R_rem × P_tok 的重复 prefill
SWE 典型：R_rem≈15、P_tok=1218 → 单次 ≈ 18K token prefill 避免
```
**截断率联动**：被错误逐出的长 session 更易撞上下文上限 → 价值逐出间接降低 26% 截断率（保护长 session 的 KV 连续性）。

### 3.2 gaia2 负载（multi-agent）

gaia2 fan-out 5.3 个并行子任务，若把一个 DAG 组里"剩余子任务多"的逐出 → 拖垮整组（join 等待）。remaining_value 天然保护"还有很多后继的节点"。但完整 DAG 保护需组完成调度（另一特性），本特性提供**节点级**的价值排序基础。

### 3.3 收益边界（诚实标注）

- 收益强依赖 `remaining_turns` 上报准确度。估偏时退化（但不劣于旧行为，因兜底=0）。
- 18K token 是**单次抢占**避免的重算上界；实际收益 = 单次收益 × 抢占频次 × 估准率。
- 无 remaining_turns 上报的请求不受益（退化旧行为）。

## 第 4 问：复杂度 / 修改范围 / 可行性 / 泛化性

### 4.1 实现代码复杂度：**极低**

| 项 | 量 |
|---|---|
| 新增函数 `_remaining_value` | ~5 行 |
| 改抢占 key | 2 处 × 1 行 |
| 配置开关 | ~3 行 |
| **总计** | **~10 行，无新增数据结构、无新增热路径计算** |

### 4.2 修改代码范围：**2 个自有文件，不 patch 上游**

| 文件 | 改动 | 是否 patch 上游 |
|---|---|---|
| `recompute_scheduler.py:351` | key + 新增 _remaining_value | 否（自有子类）|
| `scheduler_dynamic_batch.py:244` | key 同构 | 否（自有子类）|
| agent harness | extra_args 带 remaining_turns | 应用侧，非引擎 |

**关键**：`RecomputeScheduler(Scheduler)` / `SchedulerDynamicBatch(Scheduler)` 都是 vllm-ascend 自有子类，改它们符合插件架构（AGENTS.md），**无需上游评审**。

### 4.3 可行性：**高**

- ✅ 落点精确（grep 确认唯一抢占点 + 同构点）
- ✅ 复用已有字段（num_preemptions/priority/arrival_time 全现成）
- ✅ 透传通道现成（extra_args，有 routed_experts 先例）
- ✅ 安全兜底（无上报退化旧行为）+ 配置开关灰度
- ⚠ 唯一约束：CPU 标量计算（已规避 .item() 同步）
- ⚠ 依赖 remaining_turns 上报（[报]），但可先用 osl/历史 R 后验近似启动

### 4.4 泛化性：**中高**

- **跨调度器**：两个自有调度器同构，一次设计两处复用。
- **跨负载**：对单 agent（SWE）和 multi-agent（gaia2）都适用（后者提供节点级价值基础）。
- **可扩展评分**：`_remaining_value` 是一个评分函数注入点，未来可叠加 prefix_reuse、expected_idle 等指标（联合优化），不改调用处。这是**为后续特性预留的扩展点**——价值逐出是"评分式调度"的第一块基石。
- **局限**：依赖 PRIORITY 策略分支（`:348`）；非 PRIORITY 模式走 `:370 self.running.pop()`（FIFO 尾弹），本特性不覆盖——需单独处理或要求启用 PRIORITY 策略。

## 总结：四问闭环

1. **指标**：num_preemptions（已有）+ priority + arrival_time + remaining_turns（[报]），联合成 `remaining_value = remaining_turns/(1+num_preemptions)`。
2. **方案+时序**：只改调度循环 ④ 抢占目标选择一行 key（`:351`），时序其余步骤复用；信号经 extra_args 透传。
3. **收益**：SWE 单次抢占避免 ≈18K token 重算，间接降 26% 截断率；gaia2 提供节点级价值基础。
4. **复杂度/可行性**：~10 行、2 自有文件、不 patch 上游、安全兜底+开关 → 可行性高；评分函数注入点为后续联合优化预留扩展。

> 待验证：① 行号落 PR 前重 grep；② remaining_turns 上报准确度需实测；③ 18K token 是单次上界，整体收益需 × 抢占频次 × 估准率；④ 非 PRIORITY 策略分支不覆盖。
