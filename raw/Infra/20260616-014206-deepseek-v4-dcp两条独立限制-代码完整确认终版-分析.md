# DeepSeek-V4-Flash DCP 报错：两条独立限制的代码完整确认（终版）

> 日期：2026-06-16
> 本版相对前两版的进展：前版只找到「限制①（MTP draft）」并误以为"关 MTP 即可"。本版按相同严谨度核查 SWA prefix caching 路径，**发现第二条独立的 DCP 断言**——即使关 MTP 也绕不过，除非再关 prefix caching。这是对"DCP 能不能跑"的完整代码闭环。
> 代码基线：`vllm-ascend @ a57a8f0`、`vllm @ 0d29612`
> 实测脚本：`run_node0.sh`（`--enable-prefix-caching` + `--speculative-config deepseek_mtp` 均开启）

---

## 0. 终版结论（两条独立断言，均代码钉死）

> **DeepSeek-V4-Flash 开 DCP 报错，是两条相互独立的断言所致，不是一条。** 实测脚本同时开了 MTP 和 prefix caching，两条限制都会撞上。

| 限制 | 断言原文 | 文件:行 | 触发开关 | 实测脚本 |
|------|---------|---------|---------|---------|
| **① MTP draft 压缩层** | `assert self.compressor_ratio <= 1, "vLLM-Ascend only support SWA-layer for Deepseek-V4 now."` | `dsa_cp.py:354` + `dsa_v1.py:1131` | `--speculative-config`（MTP） | ✅ 开 |
| **② SWA prefix caching** | `assert dcp_world_size == 1, "DCP not support sliding window attn now."` | `single_type_kv_cache_manager.py:616`（+ `kv_cache_interface.py:512`） | `--enable-prefix-caching` | ✅ 开 |

## 1. 限制①：MTP draft 路径不支持压缩层（前版已证，复述）

证据链（全部代码证实，可 grep 复核）：
```
开 DCP → 切 AscendDSACPMetadataBuilder (dsa_v1.py get_builder_cls + enable_dsa_cp)
 + 开 MTP → proposer 调 build_for_drafting (llm_base_proposer.py:1644，全仓唯一调用点)
 + use_compress=True (llm_base_proposer.py:156, DSv4 有 compress_ratios 恒真)
 + 遍历 C4/C128 层 → compressor_ratio=4/128 > 1 (dsa_cp.py:186)
 → assert compressor_ratio<=1 失败 (dsa_cp.py:354)
```
触发条件 = **DCP + MTP + 压缩模型** 三者同开。

---

## 2. 限制②：SWA group + prefix caching 不支持 DCP（本版新增，决定性）

### 2.1 断言原文

```python
# vllm/vllm/v1/core/single_type_kv_cache_manager.py:616-617
#   SlidingWindowManager.find_longest_cache_hit()
assert dcp_world_size == 1, "DCP not support sliding window attn now."
assert pcp_world_size == 1, "PCP not support sliding window attn now."
```
另有 `kv_cache_interface.py:512` 同义限制 "DCP not support sliding window."（双重佐证）。

### 2.2 为什么 DeepSeek-V4 + prefix caching 必触发

逐环代码：
1. **DeepSeek-V4 有 SWA group**：44 层滑动窗口（资料 182107 §5.1：两个 22 层 SWA group）→ 用 `SlidingWindowManager`。
2. **prefix caching 开启 → 必调 `find_longest_cache_hit`**：
   ```python
   # vllm/vllm/v1/core/kv_cache_manager.py:218  get_computed_blocks()
   if not self.enable_caching or request.skip_reading_prefix_cache:
       return ...   # 只有关 caching 才跳过
   # 否则 → coordinator.find_longest_cache_hit → 各 group manager.find_longest_cache_hit
   ```
3. **SWA group 的 manager 在 DCP>1 时断言失败**（`:616`）。
→ **DCP>1 + prefix caching + 有 SWA group（DeepSeek-V4 必有）= 断言失败。**

### 2.3 这条限制与 MTP 完全独立

- 限制①在 `build_for_drafting`（投机解码路径），限制②在 `find_longest_cache_hit`（prefix 命中路径）。
- **两条路径无交集**：关 MTP 能绕过①，但**绕不过②**——只要 prefix caching 开着，SWA manager 的 find_longest_cache_hit 仍会被调用并断言。

## 3. 修正前版结论："关 MTP 能否跑 DCP"的完整答案

| 配置 | 限制① (MTP) | 限制② (SWA prefix) | 结果 |
|------|------------|-------------------|------|
| DCP>1 + MTP + prefix caching（**实测现状**） | ❌ 触发 | ❌ 触发 | **报错** |
| DCP>1 + **关 MTP** + prefix caching | ✅ 不触发 | ❌ **仍触发** | **仍报错**（前版漏判！） |
| DCP>1 + 关 MTP + **关 prefix caching** | ✅ 不触发 | ✅ 不触发（不调 find_longest_cache_hit） | 断言不触发，但失去 Agentic 多轮复用 |
| DCP=1（实测现状） | — | — | 正常（不走 CP / 不卡 DCP） |

> **前版纠错**：我前版说"关 MTP 即可跑 DCP"是**漏判了限制②**。完整答案是：**要让 DCP 跑通，需同时关 MTP 和关 prefix caching**——而关 prefix caching 直接废掉 Agentic 多轮历史复用（实测脚本注释明确"强烈建议开"），**得不偿失**。

## 4. 对方案的最终影响（DCP 此路基本不通）

### 4.1 扩 KV 池：DCP 实质不可用，L2 卸载是唯一可行主力

| 扩容手段 | 代码确认状态 | 结论 |
|---------|------------|------|
| DCP（任意配置） | ① + ② 两条断言，关 MTP 仍被 ② 卡，关 prefix caching 失多轮复用 | **实质不可用**（除非接受关闭 prefix caching + MTP） |
| **L2 host 零拷贝卸载** | omni-cache 零拷贝可用，不依赖 DCP | **唯一无副作用的扩容主力** |
| 权重量化 W8A8/FP8 | 待查 DSV4 量化支持 | 备选 |
| 补齐 DCP（开发） | 需同时实现：draft 压缩层 CP（`dsa_cp.py:347`/`dsa_v1.py:1124`）+ SWA manager 的 DCP 切分（`single_type_kv_cache_manager.py:601`） | **改动面比前版评估更大**（两条独立路径都要补） |

### 4.2 这把方案的优先级进一步明确

> DCP 实质不可用 → **L2 host 零拷贝卸载（P1-c）从"扩容主力之一"升为"扩容唯一无副作用主力"**。这强化了 omni-cache 收编（v2 §7）的价值——它是不依赖 DCP、不牺牲 prefix caching 的扩容路径。

## 6. DCP 实现逻辑与收益预期（代码依据，补充）

> 这一节回答"DCP 到底怎么省 KV、能省多少"——全部从代码取证，**不确定处明确标注**。

### 6.1 实现逻辑（代码证实）

**机制：把一个请求的 KV 序列按 token 交错切分到 dcp_size 个卡，每卡只存 1/dcp_size。**

| 环节 | 代码 | 事实 |
|------|------|------|
| KV 按 interleave 切分 | `parallel.py:351` `cp_kv_cache_interleave_size`（默认 1） | "token `i` 存到 total_cp_rank `i % total_cp_world_size`"（注释原文）→ 默认逐 token 轮流分到各 dcp rank |
| 每 rank 只存部分 token | `kv_cache_interface.py:230` 注释 | "each dcp rank only need save (max_model_len//dcp_world_size) tokens locally"（源码注释原文） |
| 单请求 KV 显存除以 dcp | `kv_cache_interface.py:233` `max_model_len = cdiv(max_model_len, dcp_world_size * pcp_world_size)` | **`max_memory_usage_bytes` 把单请求有效 token 数除以 dcp_size** |
| 逻辑 block_size 放大 dcp 倍 | `single_type_kv_cache_manager.py:70` `self.block_size *= dcp_world_size` | 每个逻辑 block 覆盖 dcp 倍 token → 同样 token 需要的 block 数变 1/dcp |
| decode 跨卡聚合 | `mla_cp.py:444/498` `all_gather` + `dcp_comm_backend="ag_rs"`（AllGather+ReduceScatter） | decode 时把各卡的部分 KV/output 聚合 |

### 6.2 收益预期（代码可推导部分 + 需实测部分）

**代码可推导（确定）：**
```
# kv_cache_interface.py:233-234
单请求最大 KV 显存 = cdiv(max_model_len // dcp_size, block_size) × page_size_bytes
→ 单卡每请求 KV 占用 ≈ 1/dcp_size
```
- dcp=2 → 单卡每请求 KV 降到 ~1/2 → 同 13.3GiB 单卡 KV 池，**理论可容请求数 / 单请求上下文 放大 ~2 倍**。
- 1M 单请求：无 DCP 需 6.64GiB（资料 182107），dcp=2 → 单卡 ~3.3GiB。

**⚠️ 必须标注的不确定/需实测点（不推测）：**
1. **DCP 不省 KV 总量，只是摊到多卡**：dcp=2 用 2 张卡存原本 1 张卡的 KV。**收益是"单卡放得下更长/更多"，不是"集群 KV 总容量增加"**。是否净赚取决于这 2 张卡是否本来就在 TP 组内复用（`parallel.py:332` 注释："dcp 不改变 world size，复用 TP 组的 GPU，tp_size 需被 dcp_size 整除"）——**即 DCP 不额外占卡，是在 TP=8 内部再切 dcp 维度**。这一点代码注释明确，是真收益。
2. **AllGather+ReduceScatter 通信开销对 TPOT 的影响**：`mla_cp.py` 每层 decode 要跨 dcp rank 聚合，`dcp_comm_backend` 注释提到 a2a 后端"把 NCCL 调用从 3 降到 2"——**说明通信不可忽略，DCP 省显存的代价是增通信，对 TPOT 的净影响需实测**，代码读不出。
3. **DeepSeek-V4 上 DCP 因两条断言实质不可用**（§1-4）——所以上述收益对 DeepSeek-V4 **当前不可兑现**，是"若补齐 DCP 实现后"的预期。

### 6.3 一句话

> DCP 实现逻辑（KV 按 token 切到 dcp 卡、单卡 KV 降 1/dcp）和收益（单卡容量放大 ~dcp 倍）**有代码依据**；但①净收益依赖"dcp 复用 TP 组卡不额外占卡"（代码注释确认是真收益），②通信开销对 TPOT 的影响**需实测**，③对 DeepSeek-V4 因两条断言**当前不可兑现**。
