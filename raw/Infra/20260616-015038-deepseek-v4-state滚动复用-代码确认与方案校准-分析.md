# P1-a「state 滚动复用」优化点：代码确认与方案校准

> 日期：2026-06-16
> 用途：按 DCP 同样的严谨度，核查方案 [v2 §2 P1-a](20260615-000018-deepseek-v4-flash-910b3-kvcache多级缓存提吞吐-总体方案设计.md)「state 滚动复用降准入峰值 51.7%」是否有代码依据。
> 结论预告：**部分前提被代码证伪，P1-a 收益预估需降级并打问号**——这是核实的价值，不回避。
> 代码基线：`vllm-ascend @ a57a8f0`、`vllm @ 0d29612`

---

## 0. 结论（诚实版：方案假设需修正）

> P1-a 原论断：「state 准入按 O(chunk) 是**虚高**，滚动复用降到 O(state_window=8/128)，准入峰值 -51.7%」。
> **代码核查后修正**：
> 1. ✅ **O(chunk) 公式属实**（代码证实，`kv_cache_interface.py:502`）。
> 2. ❌ **"虚高"定性错误**——这个 O(chunk) cap 是 **vLLM PR #40946 的封顶优化结果**，不设它会退化到 O(max_model_len)（更糟）。它是 chunk 期间的**真实持有量上界**，不是浪费。
> 3. ⚠️ **"滚动复用降到 O(state_window)"是方案假设，未经 kernel 代码证实**——需确认 Compressor 算子能否"本 chunk 中间 state 不持久化"，这在 `_C_ascend.compressor` 算子内部（C++），Python 层读不出。

---

## 1. 已证实的部分（代码确实支撑）

### 1.1 state 组 = SlidingWindowMLASpec

```python
# deepseek_v4.py:130/201  AscendCompressorStateCache.get_kv_cache_spec
return SlidingWindowMLASpec(...)
```
DeepSeek-V4 的 C4 state / C128 state 缓存用 `SlidingWindowMLASpec`（继承 `SlidingWindowSpec`）。

### 1.2 准入 cap 公式 = O(chunk)（属实）

```python
# kv_cache_interface.py:488-508  SlidingWindowSpec.max_admission_blocks_per_request
num_tokens = min(self.sliding_window - 1 + max_num_batched_tokens, max_model_len)  # :502
return cdiv(num_tokens, self.block_size) + 1                                       # :508
```
- `max_num_batched_tokens` = chunk size → 准入随 chunk 线性增长，**O(chunk) 属实**。
- state 组走 `get_manager_for_kv_cache_spec:279` 分支应用此 cap（代码证实）。

> 这部分我方案没错：state 准入确实是 O(chunk)，chunk=8192 时 state 块数远大于稳态。

## 2. 被证伪的部分（"虚高"定性错误）

### 2.1 O(chunk) cap 是优化结果，不是浪费

```python
# single_type_kv_cache_manager.py:249-286  docstring + 注释
# vLLM PR #40946 does for SlidingWindowSpec / ChunkedLocalAttentionSpec.
# ... without re-applying it here SlidingWindowMLASpec groups have no cap and
# full_sequence_must_fit admission reserves the full max_model_len worth of
# blocks per request, exhausting the pool at cc>=2 on DSv4 (see issue #40863).
```

**代码事实**：
- 若**不设**这个 O(chunk) cap → 准入按 `full max_model_len` 预留 → DSv4 在 cc>=2 时直接耗尽池（issue #40863）。
- 这个 O(chunk) cap **正是把准入从 O(max_model_len) 降到 O(chunk) 的优化**（对标 vLLM PR #40946）。

### 2.2 docstring 明确：这是"真实持有量"，不是虚高

```python
# kv_cache_interface.py:491-508  max_admission_blocks_per_request docstring
# "Per-request real-held blocks plateau at this bound because
#  SlidingWindowManager.remove_skipped_blocks runs from allocate_slots
#  before each chunk's get_num_blocks_to_allocate."
# "we hold KV for the last sliding_window-1 computed tokens plus the
#  newly scheduled tokens"
```

**代码事实**：这个 cap = chunk 期间**真实需要同时持有**的块数 = 旧窗口尾部（sliding_window-1）+ 本 chunk 新 token（max_num_batched_tokens）。**不是预留虚高，是真实占用上界。**

> **校准我方案**：我说"state 真实窗口只有 8/128，O(chunk) 是虚高"——这混淆了两件事。state cache 的**逻辑窗口**确实是 8/128，但 **prefill chunk 期间为本 chunk 每个 token 计算压缩状态时，需要的 slot 是 O(chunk) 的真实工作集**。docstring 说得很清楚：hold 旧窗口尾 + 本 chunk 新 token。

## 3. 未证实的部分（方案假设，需 kernel 确认）

### 3.1 "滚动复用降到 O(state_window)"依赖 Compressor kernel 行为

```python
# dsa_v1.py:2058-2075  prefill compressor 调用
compressed_kv = torch.ops._C_ascend.compressor(
    hidden_states, ...,
    state_cache.squeeze(-2),                                  # state 写入分页 cache
    state_block_table=compressor_state_prefill_metadata.block_table,
    cu_seqlens=actual_seq_lengths_query,
    cmp_ratio=self.compress_ratio, ...
)
```

**关键疑问（不推测，标注）**：
- P1-a 要成立，需证明"本 chunk 中间 token 的 state 可以走算子 scratch、不写持久分页 cache，只留 chunk 末尾状态"。
- 但 `_C_ascend.compressor` 是 **C++ 算子**，它内部是否为本 chunk 每个 token 都写 `state_block_table` 指向的持久 slot，**Python 层读不出**——需要看算子实现或 profiler 实测。
- **如果算子必须为本 chunk 每 token 写持久 state slot**，那 P1-a 的"滚动复用"在不改算子的前提下**不可行**；要改就是 kernel 级改动（难度高，方案已标 P1-a 涉及 kernel）。

### 3.2 这对 P1-a 收益的影响

| P1-a 论断 | 代码确认状态 |
|-----------|------------|
| state 准入 O(chunk) | ✅ 属实 |
| O(chunk) 是"虚高" | ❌ 错误，是 PR#40946 封顶优化结果 |
| 滚动复用降到 O(state_window) | ⚠️ **未证实**，依赖 Compressor 算子能否不持久化中间 state（kernel 层，需实测/读算子） |
| 准入峰值 -51.7% | ⚠️ **建立在未证实假设上**，需先确认算子可行性才能兑现 |

## 4. 修正后的 P1-a 定位（替换方案中的表述）

> **P1-a 不是"消除虚高"，而是"减少 chunk 期间 state 的真实持有量"——这需要改 Compressor 算子让中间 state 不落持久 cache。** 难度从方案原标的"中"上修到"高（kernel 级，且可行性未证实）"。

**更稳妥的替代（代码已支持、无需算子改动）：**
- **直接调小 chunk**（P0-2）：`max_num_batched_tokens` 从 8192→2048，state 准入 `cdiv(sw-1+2048, block)+1` 直接降——这是**代码已支持、零开发**的准入峰值优化，且不依赖任何未证实假设。
- 实测脚本已经在用（8192→4096，脚本注释自证缓解抢占）。**这是 P1-a 想要的收益的一部分，且已被实测验证可行。**

> **结论**：P1-a 的"滚动复用"部分**降级为 P2（kernel 级、可行性待证）**；其"降 state 准入峰值"的目标**改由 P0-2 调小 chunk 兑现**（代码已支持、实测已验证）。准入峰值的精确收益应按"调 chunk"重算，不用"滚动复用"的 51.7%（那个数字建立在未证实假设上）。
