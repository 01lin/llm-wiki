## 1. 核心结论

TileRT 是一个面向 **ultra-low-latency LLM inference** 的 tile-level runtime。它不是传统意义上以动态 batch、高吞吐服务为第一目标的推理框架，而是围绕单请求/低延迟 decode，把模型结构、权重布局、临时 buffer、KV cache、投机/MTP、采样、通信和原生 runtime 做深度耦合。

从当前本地开源代码看，TileRT 的 Python 层更像是：

1. 模型结构描述层。
2. 权重转换和加载层。
3. 固定 ABI 的 buffer 准备层。
4. 原生 `libtilert.so` 的调用封装层。
5. 简单 generation / benchmark 控制层。

真正的高性能执行、tile-level scheduling、CUDA graph/native kernel orchestration 主要在 `libtilert.so` 内部。当前仓库没有看到 `.cu`、`.cpp`、`.hpp` 或原生 runtime 源码，因此开源 Python 代码只能完整观察 **控制面和 ABI 设计**，无法完整审计底层编译器/runtime/kernel 实现。

一句话概括：

> TileRT 的性能关键不是单个算子优化，而是把 decode step 改造成一个固定形状、固定地址、固定状态布局、原生 runtime 驱动的低开销流水线，并通过 MTP 提高每次 forward 的有效 token 产出。

## 2. README 侧定位与性能声明

README 对 TileRT 的定位非常清楚：

- 目标：降低 LLM 单 token 生成延迟，让大模型获得毫秒级 TPOT。
- 目标场景：高频交互、实时决策、长程 agent、AI coding 等对单请求响应敏感的场景。
- 核心方法：tile-level runtime engine，把 LLM operators 分解成细粒度 tile tasks，并在多设备上重排 compute、I/O、communication。
- 当前预构建包：README 明确写到当前 pre-built package 面向 **8x NVIDIA B200**。
- 模型：DeepSeek-V3.2、GLM-5。
- MTP：README 示例中 MTP 平均 accepted length 可接近 2.77。
- 性能声明：README 新闻区提到 GLM-5-FP8 最高 500 tokens/s、DeepSeek-V3.2 最高 600 tokens/s，以及早期 v0.1.2-alpha.1 synthetic workload 下 MTP=3 达到 590 tokens/s。

需要注意：

- 这些性能数字依赖特定硬件、模型、权重格式和 runtime。
- 本地开源代码没有底层 native runtime 源码，无法仅凭仓库源码复现或解释全部性能细节。
- README 当前硬件要求是 B200，而不是通用 H100/A100/Ascend 环境。

## 3. 开源边界：Python 控制面 + Native Runtime

入口文件 `TileRT/python/__init__.py` 中最关键的是：

```python
torch.ops.load_library(str(lib_path))
_load_library("libtilert.so")
```

这说明 TileRT 主要通过 PyTorch custom op 机制加载 `libtilert.so`。后续大量核心调用都形如：

```python
torch.ops.tilert.xxx(...)
```

例如：

- `dsa_show_hands_prepare_money`
- `dsa_show_hands`
- `dsa_mtp_e2e_show_hands`
- `mtp_preprocess_layer`
- `rmsnorm_proj_qa_kva_ki_op`
- `expert_select_up_gate_silu_op`
- `rmsnorm_head_proj_op`
- `top1_allreduce_op`

当前仓库没有 native 源码，因此可以确认：

1. Python 代码暴露了 TileRT 的高层结构和 ABI。
2. Native library 才是真正执行高性能 kernel、graph capture、runtime scheduling 的主体。
3. `prepare_money` 很可能是“准备/注册/捕获/初始化 native runtime”的关键阶段。
4. `show_hands` 是 decode step 的 native 执行入口。

## 5. 执行时序

### 5.1 包加载阶段

导入 `tilert` 时：

1. 初始化 logger。
2. 通过 `torch.ops.load_library` 加载 `libtilert.so`。
3. 注册 native custom ops 到 `torch.ops.tilert`。

如果 `libtilert.so` 不存在或无法加载，Python 包无法正常工作。

### 5.2 Generator 初始化

`DSAv32Generator.__init__` 负责：

1. 设置 PyTorch CPU threads。
2. 加载 tokenizer。
3. 固定 `batch_size = 1`。
4. 创建 `ShowHandsDSALayer`。
5. 根据 `with_mtp` 设置 `mtp_seq_len`，MTP 模式下为 4。

这反映出 TileRT 当前 generation 代码明显偏向 **batch=1 低延迟**，而不是通用 serving。

### 5.3 权重加载与 runtime 准备

`ShowHandsDSALayer.from_pretrained` -> `_init_weights` 是关键流程：

1. 对每个 device 启动 Python thread。
2. 每个 device 只加载后缀匹配 `dev_{device_id}` 的权重。
3. 构造 `Dsa` 模块。
4. 调用 `Dsa.init_tilert_weights` 把 state_dict 中的权重加载到各个 op。
5. 收集 `params`，即每个 native op 所需的权重列表。
6. 收集 `caches`，包括 MLA/DSA KV、PE、KI cache。
7. 创建 `temp_vars`，并通过 `generate_params_with_continuous_storage` 变成一块连续显存上的多个 view。
8. 若开启 MTP，追加 `MTP` 模块权重和 cache。
9. 为每个 device 创建 `profile_logs` tensor。
10. 所有 device 初始化完后，逐 device 调用 `dsa_show_hands_prepare_money`。

`prepare_money` 是 native runtime 初始化的核心入口。它拿到：

- `params`
- `temp_vars`
- `cache_vars`
- `profile_logs`
- `forward_max_seq_len`
- `with_mtp`
- `is_glm5`

从代码注释看，采样参数会在 `prepare_money` 时进入 CUDA graph/native instruction，因此采样参数变化需要 teardown + recapture。

### 5.4 非 MTP decode

`_generate_without_mtp` 的逻辑：

1. 把 prompt token 写入 GPU 上的 `tokens` buffer。
2. 从位置 1 到 `total_len` 循环。
3. 每步调用：

   ```python
   self.decode_layer.forward(tokens[0, prev_pos], with_mtp=with_mtp)
   ```

4. `ShowHandsDSALayer.forward` 内部调用：

   ```python
   dsa_show_hands(token_id.cpu(), active_mtp, self.is_glm5)
   ```

5. native runtime 把输出 token 写入 `temp_vars[Idx.TOKEN_OUT]`。
6. Python 从 `intermediates[Idx.TOKEN_OUT]` 读取下一 token。
7. 遇到 EOS 或达到长度后 reset sequence。

注意：

- Python 层仍有 loop，但重计算逻辑由 native `show_hands` 完成。
- `token_id.cpu()` 是控制面 API 的一部分，说明 native 入口可能接受 CPU token id 驱动全局 runtime 状态。
- 单步计时在 Python loop 中做，适合展示/benchmark，但真正低开销来自 native runtime 内部。

### 5.5 MTP decode

`_generate_with_mtp` 分为 prefill 和 decode 两段。

Prefill：

1. 按 `mtp_seq_len=4` 将 prompt 切成 non-overlap chunks。
2. 每个 chunk 补齐到 4 token。
3. 设置 MTP preprocess 需要的 extra token。
4. 设置 valid token 数。
5. 调用 `decode_layer.forward(draft_tokens, with_mtp=True)`。
6. 前进 `cur_pos`。

Decode：

1. 第一轮使用 last prompt token 重复作为 draft placeholder。
2. 后续轮次使用上一轮 runtime 生成的 `NEXT_DRAFT_TOKENS`。
3. 调用 `decode_layer.forward(draft_tokens, with_mtp=True)`。
4. 读取：
   - `ACCEPTED_TOKENS`
   - `PREDICTED_TOKENS`
   - `NEXT_DRAFT_TOKENS`
5. 把 accepted token 写入输出 buffer。
6. `cur_pos += num_accepted`。

MTP 的性能收益来自：

```text
effective_tps = sum(accepted_tokens) / sum(decode_forward_time)
```

而不是单次 forward latency 单独降低。也就是说，只要每次 forward 平均接受 2-4 个 token，即使单次 forward 比非 MTP 稍重，也可能显著提高 effective token/s。

## 6. 核心数据结构：temp_vars ABI

`temp_var_indices.py` 定义了 51 个固定槽位：

```text
0  Q
1  KV
2  KI
...
24 LOGITS_OUT
25 TOKEN_OUT
...
31 CUR_POS
32 TOKEN_ID
33 LAST_HIDDEN_STATES
34 DRAFT_TOKENS
35 PREDICTED_TOKENS
36 PREDICTED_HIDDEN
37 ACCEPTED_TOKENS
38 NEXT_DRAFT_TOKENS
39 X_QUANT
40 X_SCALE
41 MOE_UP_GATE
42 IDX_SEL_WS
43 MTP0_TOKEN_OUT
44 MTP1_TOKEN_OUT
45 MTP0_EXP_OUT
46 SAMPLING_SEED
47 SAMPLING_POSITIONS
48 SAMPLING_CONFIG
49 TOP_P_SCORES
50 TOP_P_DEBUG
```

这个设计非常关键：

1. Python 和 C++ 通过固定 index 共享 runtime state。
2. 每个 tensor 的 shape、dtype、device 在初始化时固定。
3. Native runtime 不需要动态查找 Python 对象语义，只按 slot 访问。
4. MTP、sampling、token output、accepted count、next draft token 都走同一张 buffer table。
5. `validate_temp_vars_layout` 会尝试检查 Python enum 与 C++ `DsaTempVars::temp_vars_size` 一致。

### 6.1 连续显存布局

`ShowHandsDSALayer.generate_params_with_continuous_storage` 会把所有 temp_vars 重新映射到一块 `torch.uint8` 大 tensor 上，并按 1024 byte 对齐切成 view。

这个设计的意义：

- 保持地址稳定，便于 graph/native runtime capture。
- 降低碎片化和 allocator 干扰。
- 让 native runtime 可以假设固定输入/输出地址。
- 更接近“persistent runtime state”的设计。

这是 TileRT-like 设计里非常值得迁移到其他后端的部分。

## 7. 模型结构与模块编排

### 7.1 `SerializableTileRTModule`

`SerializableTileRTModule` 是 Python 层模型组装的核心抽象：

- `exec_seq` 保存子 op 顺序。
- `prefix_seq` / `suffix_seq` 用于权重 key 映射。
- `retain_weights_seq` 控制权重是否保留。
- `get_cache_vars` 汇总所有子 op cache。
- `get_weights_list` 汇总所有子 op 权重。
- `init_tilert_weights` 按 op alias 从 state_dict 中抽取权重并初始化。

这说明 Python 模型层不是直接执行动态图，而是把模型拆成一个有序 op 序列，再序列化成 native runtime 可消费的 weights/cache/temp buffers。

### 7.2 `Dsa`

`Dsa` 是 DeepSeek-V3.2 端到端 decode 主体：

1. 遍历 `n_layers`。
2. 前 `n_dense_layers` 使用 `MlpBlock`。
3. 后续层使用 `MoeBlock`。
4. 最后注册 `RMSNormHeadProj`。
5. 附加 embedding 和 RoPE freqs。

结构上：

```text
Dsa
  layer_0..dense:
    MlpBlock
      Mla
      Mlp
  layer_dense..n_layers:
    MoeBlock
      Mla
      Moe
  final:
    RMSNormHeadProj
```

### 7.3 `Mla`

`Mla` 是 attention/DSA 相关核心模块，按 op 序列注册：

1. `RMSNormProjxWqkvia`
2. `LayerNormRoPERotate`
3. `RmsnormProjqWqib`
4. `ProjxWis`
5. `ProjqWqb`
6. `KVRMSNorm`
7. `ProjoWKVb`
8. `UnProjOAllReduce`

它还持有三类 cache：

- `ki_cache`
- `kv_cache`
- `pe_cache`

每层 cache shape 以 `max_seq_len + kv_cache_pad` 为基础，说明 runtime 强依赖固定最大长度和 padding。

### 7.4 `MlpBlock`

`MlpBlock`：

```text
MlpBlock
  Mla
  Mlp
    RMSNormUpGateSiLU
    DownAllReduce
```

Dense 层中，MLP 被拆成 fused up/gate/activation 和 down/allreduce 两部分。

### 7.5 `MoeBlock`

`MoeBlock`：

```text
MoeBlock
  Mla
  Moe
    RMSNormExpertProj
    ExpertSelectUpGateSiLU
    ExpertDownAllReduce
```

MoE 关键 fused path 包括：

- RMSNorm + router/expert projection
- expert select + up/gate + SiLU
- expert down + allreduce

这是大 MoE decode 中的主要性能战场。

### 7.6 `MTP`

`MTP` 模块用于 speculative / multi-token prediction：

```text
MTP
  MTPPreprocessLayer
  MoeBlock
  RMSNormHeadProj
```

`MTPPreprocessLayer` 做：

- embedding RMSNorm
- hidden RMSNorm
- concat / projection

然后经过一个 MoE block 和 head projection，生成 draft/predicted token 相关状态。

## 8. 权重转换与布局优化

TileRT 中大量 op 都有 `WeightsConverter`，例如：

- `RMSNormProjxWqkviaWeightsConverter`
- `RmsnormProjqWqibWeightsConverter`
- `ExpertSelectUpGateSiLUWeightsConverter`
- `ExpertDownAllReduceWeightsConverter`
- `RMSNormHeadProjWeightsConverter`
- `MTPPreprocessWeightsConverter`

这些 converter 不只是做简单 rename，而是做面向 kernel 的布局转换，例如：

- 按 device 切分。
- reshape / transpose。
- swizzle MMA layout。
- FP8/FP16/BF16 特定格式。
- expert 权重重排。
- GLM-5 与 DeepSeek-V3.2 分支。

`weight_converter.py` 会把官方模型权重转换成 TileRT 权重目录，从 README 看 v0.1.3 起推荐用户下载官方权重后本地转换。

这体现了 TileRT 的一个核心原则：

> 权重不是在 runtime 中临时适配 kernel，而是在离线转换阶段就变成 runtime/kernel 最舒服的形态。

这类设计对低延迟很重要，因为 decode 热路径不能再承担 layout transform 成本。

## 9. 关键优化点总结

### 9.1 Native persistent runtime

TileRT 的 Python 层只传入固定的 params/temp/cache，真正执行在 native `show_hands` 内部。这避免了 Python 调度大量小 op。

收益：

- 降低 Python overhead。
- 降低 kernel launch 调度开销。
- 便于 native runtime 进行 tile-level schedule。

### 9.2 `prepare_money` 阶段预注册/预捕获

`prepare_money` 接收所有权重、临时 buffer、cache、profile logs。采样参数改变时需要 recapture，说明这个阶段很可能绑定了 CUDA graph 或类似固定执行计划。

收益：

- decode loop 中只 replay/execute。
- 避免每步重新构造执行图。
- 让 runtime 可以假设固定地址和固定 shape。

### 9.3 固定 temp_vars ABI

51 个固定槽位把所有中间结果、token state、MTP state、sampling state 都显式化。

收益：

- Python/C++ 通信简单。
- native runtime 无需动态查表。
- 状态更新全在 device buffer 中完成。
- 易于 capture。

### 9.4 连续显存和地址稳定

`generate_params_with_continuous_storage` 把 temp vars 放入一块大 tensor。

收益：

- 减少 allocator 干扰。
- 保持 pointer 稳定。
- 降低碎片。
- 有利于 native graph replay。

### 9.5 融合算子

TileRT Python ops wrapper 可以看到大量 fused op：

- RMSNorm + projection
- RMSNorm + quant
- Q/KV/Index projection
- RoPE / rotate
- sparse MLA
- expert select + up/gate + SiLU
- down + allreduce
- RMSNorm + head projection
- top1/top-p sampling

收益：

- 减少中间 tensor 读写。
- 减少 kernel launch。
- 减少 HBM 往返。
- 合并通信和计算边界。

### 9.6 Weight layout swizzle / FP8MMA

多个 converter 中出现 swizzle MMA layout、FP8MMA、FP16MMA、BF16 等算法分支。

收益：

- 提高 tensor core / MMA 利用率。
- 降低 decode matmul 的访存和格式转换成本。
- 针对不同模型选择不同 kernel layout。

### 9.7 MTP 提高 effective token/s

MTP 模式下 `mtp_seq_len=4`，每次 native forward 可能接受多个 token。生成统计用：

```text
effective_tps = total_accepted_tokens / total_decode_time
```

收益：

- 减少 autoregressive 串行深度。
- 当平均 accepted length > 1 时，token/s 可以成倍提升。
- README 示例中 accepted length mean 接近 2.77。

风险：

- accepted token 判断路径必须极其稳定。
- MTP preprocess、draft token、predicted token、next draft token 状态必须一致。
- Python 中 `get_num_accepted` 当前会 `.item()`，这对纯展示没问题，但在更极致 runtime 中应尽量 device-side 化。

### 9.8 多设备固定切分

`ShowHandsDSALayer.num_devices = 8`，权重按 `dev_{device_id}` 加载。README 也要求 8x B200。

收益：

- 强假设硬件拓扑和 TP/EP 布局。
- 可以为固定 8 卡做深度 schedule 和通信优化。

代价：

- 泛化性降低。
- 更换硬件或卡数时需要重新适配。

### 9.9 Profile logs

大量 op 传入 `profile_logs`，并有 `parse_profile_log_tensor`。

收益：

- native op 可以写入轻量 profile。
- 有利于逐 op 分析瓶颈。
- 支持自优化闭环中的指标反馈。

## 10. 性能收益来源模型

TileRT 的 token/s 可以抽象为：

```text
effective_tokens_per_sec =
  accepted_tokens_per_step / step_latency
```

其中：

```text
step_latency =
  python_control_overhead
  + native_runtime_dispatch
  + attention_or_sparse_mla
  + moe_or_mlp
  + lm_head_and_sampling
  + communication_exposed_time
  + synchronization_stall
```

TileRT 的优化基本对应：

| 优化 | 影响项 |
|---|---|
| native show_hands | 降低 Python/control overhead |
| prepare_money/capture | 降低 dispatch/graph build overhead |
| temp_vars 固定 ABI | 降低状态管理开销 |
| 连续显存 | 降低 allocator/地址变化风险 |
| fused ops | 降低 kernel launch 和 HBM 中间读写 |
| weight swizzle | 降低 matmul layout 成本，提高 MMA 利用率 |
| MTP | 提高 accepted_tokens_per_step |
| allreduce 融合 | 降低 communication exposed time |
| profile logs | 支持定位瓶颈并继续优化 |

所以 TileRT 的性能不是来自单点 magic，而是来自端到端 decode path 的全链路静态化、融合化、native 化和 MTP 化。

## 11. 与传统推理框架的差异

### 11.1 传统 vLLM/SGLang 类框架

通常强调：

- 多请求调度。
- continuous batching。
- KV cache allocator。
- 通用模型支持。
- OpenAI-compatible serving。
- throughput/latency tradeoff。

### 11.2 TileRT

更强调：

- 单请求极限 TPOT。
- 固定硬件/固定模型/固定 shape。
- native persistent runtime。
- tile-level schedule。
- 自定义权重格式。
- MTP/spec 集成。
- 牺牲部分通用性换低延迟。

TileRT 更像“为特定模型和特定硬件写出的低延迟推理系统”，而不是通用 serving framework。

## 12. 当前代码中的限制和注意点

### 12.1 Native 源码不可见

当前本地仓库没有底层 native runtime 源码，无法直接分析：

- tile scheduler 细节。
- CUDA graph capture 细节。
- kernel fusion 内部实现。
- 多流/多卡调度细节。
- actual communication overlap。

只能通过 Python wrapper、ABI 和 README 推断。

### 12.2 硬件强绑定

README 当前硬件要求为 8x B200，`ShowHandsDSALayer` 也写死 `num_devices=8`。

这说明当前版本不适合作为通用环境直接复现。

### 12.3 Python generation 仍有同步点

例如：

- `dsa_show_hands(token_id.cpu(), ...)`
- `get_num_accepted` 中 `.item()`
- decode 输出写回 Python `tokens`
- tokenizer decode 中逐 token `.item()`

这些对 demo/benchmark 可能可接受，因为核心 runtime 已经 native 化；但如果追求更极限，需要进一步把 token accept、sampler、stop 判断更多留在 device/native runtime 内部。

### 12.4 Sampling 参数改变需要 recapture

`update_sampling_config` 注释明确表示 sampling parameters baked into CUDA graph instructions at `prepare_money` time。也就是说动态 sampling 配置不是免费能力。

这换来固定图优化，但降低了在线服务灵活性。

### 12.5 Batch=1 假设明显

`DSAv32Generator` 固定 `batch_size = 1`，代码主要围绕 single sequence generation。这符合低延迟目标，但和高吞吐 batch serving 不是同一设计点。

## 13. 可迁移的设计思想

即使不能直接复用 TileRT native runtime，也可以迁移这些思想：

1. **固定 runtime ABI**
   用明确的 temp buffer table 管理 token、draft、accepted、logits、sampling、KV state。

2. **persistent decode state**
   decode 热路径中不重新分配核心 buffer。

3. **shape bucket + address stability**
   对常见 decode shape 做固定捕获和 replay。

4. **权重离线转换**
   让权重在加载前就满足 kernel layout。

5. **MTP 内生化**
   不把 MTP 当外部 proposer，而是和主模型 runtime 一起调度。

6. **device-side acceptance**
   accepted token、next draft token、predicted token 尽量留在 device/native 侧。

7. **融合通信和计算**
   MoE down projection、allreduce、expert combine 应尽量融合或 overlap。

8. **标准化 profiling**
   每个关键 op 能输出 machine-readable profile，便于自动迭代优化。

---

## 14. 对 Ascend / vLLM Ascend 复刻的启示

如果要在 Ascend A2/A3 上实现 TileRT-like 思想，不建议“移植 TileRT 代码”，而应复刻架构方法：

1. 以 `vllm-ascend` 为载体。
2. 用 ACLGraph / TorchAir graph mode 替代 CUDA graph/native capture。
3. 用 AscendC / Triton-Ascend / torch_npu custom op 实现关键 fused op。
4. 用 `AscendTileRuntimeContext` 管理 persistent buffers。
5. 把 `temp_vars` 思想映射到 NPU tensor state table。
6. 先做 DeepSeek-V3.2-W8A8 + MTP 单请求 decode。
7. 以 `FULL_DECODE_ONLY` graph replay、D2H sync 清理、MTP accept path、MoE/MC2 overlap 为优先方向。

TileRT 给出的最重要方向是：

> 在低延迟 decode 中，推理框架、模型结构、编译器/runtime、硬件拓扑必须一起设计。只优化框架调度或只优化单个 kernel，都很难达到极限 token/s。

## 15. 后续建议分析项

如果继续深入 TileRT，可以按以下顺序做：

1. **权重转换深入分析**
   逐个分析 converter 如何 reshape、swizzle、shard。

2. **ops wrapper 分类**
   将 `ops/` 下所有 native op 按 attention、MoE、head、sampling、communication 分类。

3. **MTP 数据流画图**
   详细画出 `DRAFT_TOKENS`、`PREDICTED_TOKENS`、`ACCEPTED_TOKENS`、`NEXT_DRAFT_TOKENS` 的流转。

4. **和 vLLM Ascend 对照**
   对照 `vllm_ascend/ops/mla.py`、`dsa.py`、`fused_moe.py`、`acl_graph.py`，找可迁移点。

5. **性能复现边界说明**
   明确哪些能力依赖 `libtilert.so`，哪些可以通过 Python 层观察。

6. **Ascend TileRT-like ABI 设计**
   设计一份类似 `temp_vars` 的 NPU runtime state table。

## 16. 总结

TileRT 的当前开源代码展示了一个高性能推理系统的“表层控制面”和“关键 ABI”：

- Python 层负责模型结构、权重、cache、temp vars、MTP 控制和 generation。
- Native `libtilert.so` 负责真正的高性能执行。
- `ShowHandsDSALayer` 是端到端 runtime 封装核心。
- `Dsa` / `Mla` / `MlpBlock` / `MoeBlock` / `MTP` 描述了模型和 op 序列。
- `temp_vars` 是 Python/C++ 协同的核心状态表。
- `prepare_money` 是 runtime capture/prepare 的关键阶段。
- `show_hands` 是 decode step 的核心 native 执行入口。
- MTP 是提高 effective token/s 的关键策略。
- 权重转换、连续 buffer、融合 op、固定 8 卡拓扑和 profile logs 共同构成低延迟路径。

最重要的工程启示是：

> 低延迟大模型推理不是一个单纯的 scheduler 问题，也不是一个单 kernel 问题，而是模型、权重布局、runtime 状态、图捕获、采样/MTP、通信和硬件拓扑共同收敛后的系统工程。
