## 二、重点机制深挖（关键技术原理）

### 2.1 vLLM：KV Connector 抽象化的 PD 分离

vLLM v1 把 PD 分离做成**插件化 connector 体系**，核心抽象 `KVConnectorBase_V1`（[base.py:171](vllm/vllm/distributed/kv_transfer/kv_connector/v1/base.py)），调度侧/worker 侧分离：

- **拉/推两态**：NIXL 后端同时提供 `NixlPullConnector`（[connector.py:321](vllm/vllm/distributed/kv_transfer/kv_connector/v1/nixl/connector.py)）和 `NixlPushConnector`（connector.py:349）。Pull=Decode 主动从 Prefill 拉 KV；Push=Prefill 算完主动推。两态对应不同的网络打洞与背压策略。
- **生命周期钩子**：`start_load_kv` / `save_kv_layer` / `get_finished`（base.py），让 KV 传输与前向计算解耦、可异步。`register_kv_caches`（[base_worker.py:843](vllm/vllm/distributed/kv_transfer/kv_connector/v1/nixl/base_worker.py)）把本地 KV 内存注册给 NIXL agent 做 RDMA 单边读写。
- **后端齐全**：NIXL（RDMA 通用）、Mooncake（[mooncake_connector.py](vllm/vllm/distributed/kv_transfer/kv_connector/v1/mooncake/mooncake_connector.py)）、LMCache、hf3fs（DeepSeek 3FS 分布式文件系统直存 KV）、MoRIIO、FlexKV。`MultiConnector`（[multi_connector.py:128](vllm/vllm/distributed/kv_transfer/kv_connector/v1/multi_connector.py)）可叠加多后端。

> **判断**：vLLM 走的是「统一抽象 + 后端可插拔」路线，优势是生态广、能接 DeepSeek/Mooncake 等第三方 KV 池；代价是抽象层多，PD 握手/心跳逻辑分散在 `metadata.py`（HeartbeatInfo:143、RemoteMeta:153）。

### 2.2 vLLM：EPLB（专家并行负载均衡）+ 弹性 EP

MoE 大模型在 EP 部署下，热门专家会让个别卡过载。vLLM 的 `EplbState`（[eplb_state.py:210](vllm/vllm/distributed/eplb/eplb_state.py)）：

- `step()`（eplb_state.py:477）每步累计专家负载统计，达到阈值触发 `rearrange()`（eplb_state.py:662）重排物理↔逻辑专家映射。支持 `is_async`（eplb_state.py:685）异步重排，避免阻塞主前向。
- **弹性 EP**：`ElasticEPScalingExecutor`（[elastic_execute.py:143](vllm/vllm/distributed/elastic_ep/elastic_execute.py)）支持运行中 scale up/down，扩缩容前后做 `perform_scale_down_eplb_reshuffle`（elastic_execute.py:550）重新均衡专家。状态机 `ScaleUp/ScaleDown*State`（[elastic_state.py](vllm/vllm/distributed/elastic_ep/elastic_state.py)）+ standby worker 支持热扩容。

> **判断**：这是 vLLM 面向**超大规模 MoE 集群**（如 DeepSeek-V3 类）的核心差异化能力，目标是把 EP 各卡利用率拉平、并在流量波动时弹性增减 GPU。

### 2.3 vLLM：DPCoordinator 全局 wave 协调

多 DP 副本下需要全局对齐「请求波次」。`DPCoordinator`（[coordinator.py:23](vllm/vllm/v1/engine/coordinator.py)）维护 DP request wave 计数与跨引擎运行状态（coordinator.py:33-56），通过 `current_wave`/`wave_complete`/`start_wave`（[engine/__init__.py:116/239/242](vllm/vllm/v1/engine/__init__.py)）在引擎间同步，避免 DP rank 间因空闲波次错配导致的同步 all-reduce 卡顿。

### 2.4 vLLM v1 调度器

`Scheduler.schedule()`（[scheduler.py:357](vllm/vllm/v1/core/sched/scheduler.py)）：token_budget 驱动的统一调度，先调度 running（scheduler.py:395）再从 waiting 补充（scheduler.py:586），队列抽象 `create_request_queue(self.policy)`（scheduler.py:170）支持 FCFS/priority。预算耗尽时抢占（preempt，scheduler.py:499/519）。

### 2.5 SGLang：RadixCache —— 前缀缓存的招牌

SGLang 把前缀复用做成**树形结构**而非 hash 块表，这是其在多轮对话/共享前缀场景的核心优势。`RadixCache`（[radix_cache.py:286](sglang/python/sglang/srt/mem_cache/radix_cache.py)）：

- `match_prefix()`（radix_cache.py:360）在 Radix 树上做**最长前缀匹配**，命中即复用 KV，不只是块对齐命中；
- `cache_finished_req` / `cache_unfinished_req`（radix_cache.py:442/493）把请求 KV 插回树，连续请求自然共享；
- `evict()`（radix_cache.py:568）LRU 风格驱逐 + `TreeNode`（radix_cache.py:223）引用计数保护在用节点。
- 调度直接 **cache-aware**：`SchedulePolicy` 支持 `LPM`(longest prefix match) / `DFS_WEIGHT`（[schedule_policy.py:136-137](sglang/python/sglang/srt/managers/schedule_policy.py)），按前缀命中度排队，最大化缓存复用率。

### 2.6 SGLang：HiRadixCache 分级 KV

`HiRadixCache(RadixCache)`（[hiradix_cache.py:72](sglang/python/sglang/srt/mem_cache/hiradix_cache.py)）把 Radix 树扩展到 HBM 之外：

- `write_backup`(hiradix_cache.py:758) / `write_backup_storage`(hiradix_cache.py:834)：把冷节点 KV 下沉到 DRAM/远端存储；
- `load_back`(hiradix_cache.py:1140) / `init_load_back`(hiradix_cache.py:1212)：命中冷层时回载；
- `prefetch_from_storage`(hiradix_cache.py:1471)：预取，隐藏回载延迟。
- 远端后端：`hicache_storage.py` 接 Mooncake / 3FS / nixl。

> **判断**：vLLM 的 offloading 是「块级 + connector」，SGLang 的 HiRadix 是「树级 + 分层」，后者在**前缀树语义上做分层**，理论上对共享前缀的冷热分层更自然。

### 2.7 SGLang：PD 分离的角色化与 overlap

- Prefill 侧 `PrefillBootstrapQueue`（[prefill.py:102](sglang/python/sglang/srt/disaggregation/prefill.py)）+ `SchedulerDisaggregationPrefillMixin`（prefill.py:396）；Decode 侧 `DecodePreallocQueue`（[decode.py:273](sglang/python/sglang/srt/disaggregation/decode.py)）+ `DecodeTransferQueue`（decode.py:1439）。
- 双事件循环：`event_loop_normal_disagg_prefill`（prefill.py:470）/ `event_loop_overlap_disagg_prefill`（prefill.py:503），decode 侧对称。**overlap 版**把 KV 传输/预分配与前向计算重叠。
- 握手通过 `bootstrap_room` + `CommonKVManager`（[common/conn.py:108](sglang/python/sglang/srt/disaggregation/common/conn.py)）做 prefill↔decode 配对。

### 2.8 SGLang：DP attention + 调度 overlap

- `dp_attention.py` 提供 `_dp_gather_via_all_reduce`(dp_attention.py:472) / `_dp_gather_via_all_gather`(dp_attention.py:507) + `memcpy_triton`(dp_attention.py:461)，让 attention 走 DP、MoE 走 EP，减少 attention 的 TP 通信。
- 调度主循环 `event_loop_overlap`（[scheduler.py:1536](sglang/python/sglang/srt/managers/scheduler.py)）把**下一批的 CPU 调度（get_next_batch_to_run, scheduler.py:2588）与当前批 GPU 前向（run_batch, scheduler.py:3178）重叠**，隐藏调度开销。

### 2.9 vLLM-Ascend：NPU 后端差异点

- **PD 传输**：复用 vLLM connector 抽象，落地为 NPU 专用后端 —— `MooncakeConnector` + `mooncake_layerwise_connector`（[kv_transfer/__init__.py:30/53](vllm-ascend/vllm_ascend/distributed/kv_transfer/__init__.py)），以及 `kv_p2p` / `kv_pool`（基于昇腾 LLMDataDist）。`AscendMultiConnector`（[ascend_multi_connector.py:19](vllm-ascend/vllm_ascend/distributed/kv_transfer/ascend_multi_connector.py)）。
- **EPLB**：独立实现 `vllm_ascend/eplb/`，含 `eplb_worker.py` / `eplb_device_transfer_loader.py`（NPU 间专家权重搬运）/ `eplb_updator.py`。说明昇腾侧专家重排走的是自己的 device transfer 路径，而非直接复用 vLLM CUDA 版。
- **通信**：`device_communicators/` 下 `pyhccl.py` / `pyhccl_wrapper.py`（HCCL，对标 NCCL）+ `npu_communicator.py`。多机/超节点能力依赖 HCCL + 昇腾互联。

> **判断**：vllm-ascend 的策略是**「上层抽象沿用 vLLM、下层 device/通信/EPLB 搬运换成昇腾原生」**。架构与 vLLM 主线一致，差异集中在通信库(HCCL)、KV 传输(LLMDataDist/Mooncake-NPU)、EPLB 的设备间权重搬运。

## 三、分析判断：优化了哪些环节、提升哪些指标

### 3.1 三个框架优化的「环节/步骤」归纳

| 优化环节 | vLLM | SGLang | 直接收益指标 |
|----------|------|--------|--------------|
| **Prefill/Decode 解耦** | connector 插件化、拉推两态 | 角色化 + bootstrap 配对 + overlap | TTFT↓、TPOT 稳定、两阶段各自打满利用率 |
| **KV 跨节点搬运** | NIXL/Mooncake RDMA 单边、layerwise | Mooncake/NIXL/MoRI + hicache | 传输延迟↓、PD 分离可行性↑ |
| **前缀/上下文复用** | hash 块 prefix caching | RadixCache 最长前缀 + cache-aware 调度 | 重复 prefill 算力↓、吞吐↑（多轮/共享前缀） |
| **KV 分层存储** | offloading connector + kv_offload | HiRadixCache write_backup/load_back/prefetch | 显存容量等效扩大、长上下文/高并发承载↑ |
| **MoE 专家均衡** | EPLB 在线重排 + 弹性 EP | expert_distribution + EP dispatcher(DeepEP) | EP 各卡利用率拉平、长尾延迟↓ |
| **DP/EP 并行通信** | DPCoordinator wave 对齐 | DP attention gather/scatter | 减少同步空泡、attention 通信量↓ |
| **调度开销隐藏** | token_budget 统一调度 | event_loop_overlap 计算/调度重叠 | 调度不再阻塞前向、GPU 空泡↓ |
| **弹性伸缩** | elastic_ep scale up/down + standby | （偏外部 router 多实例） | 流量波动下成本/SLO 平衡 |

### 3.2 核心提升的关键指标

整体看，大规模分布式集群优化都在打这几个指标：

1. **TTFT（首 token 延迟）** —— 靠 PD 分离把 prefill 隔离、靠前缀复用跳过重复 prefill。
2. **TPOT / ITL（decode 阶段每 token 延迟与稳定性）** —— 靠 PD 分离让 decode 不被 prefill 抢占、靠 overlap 调度隐藏开销。
3. **吞吐 / Goodput（满足 SLO 的有效吞吐）** —— 靠 continuous batching + chunked prefill + cache-aware 调度 + EPLB 拉平利用率。
4. **有效显存容量 / 最大并发** —— 靠 KV 分层（HiRadix / offloading）把 KV 外溢到 DRAM/SSD/远端池。
5. **集群利用率均衡度** —— 靠 EPLB（专家）+ DPCoordinator（DP 波次）+ 弹性 EP（扩缩容）消除热点与空泡。

### 3.3 两条路线的本质差异（结论）

- **vLLM（含 ascend）= 抽象化 + 生态化**。PD 传输、KV 分层都做成可插拔 connector，强在「能接万物」（NIXL/Mooncake/LMCache/3FS）和**面向超大 MoE 的 EPLB + 弹性 EP**。ascend 沿用上层、换下层（HCCL/LLMDataDist/NPU-EPLB）。集群侧最强项：**MoE 专家均衡 + 弹性伸缩**。
- **SGLang = 缓存语义 + 调度协同**。把 RadixCache 前缀树做成一等公民，调度 cache-aware（LPM/DFS）、KV 分层走 HiRadix 树级分层、PD 与 DP attention 深度 overlap。集群侧最强项：**前缀复用 + 分级 KV + 计算/调度重叠**。

> 一句话：**vLLM 把"规模与弹性"做厚（EP/弹性/connector 生态），SGLang 把"复用与重叠"做深（Radix/HiRadix/overlap）**。两者在 PD 分离和多种 KV 传输后端上已高度趋同（都接 Mooncake/NIXL）。
