## 一、问题 A 根因与修复方向：核对准确 ✅

### 1.1 GPU 参考实现（本地实测，文档引用准确）

文档声称 GPU 用"req 行 + req 内 slot 列"，本地核对一致：

- **读**（fused_recurrent.py:107-110）：
  ```python
  i_t = tl.load(num_accepted_tokens + i_n).to(tl.int64) - 1   # 列 = num_accept-1
  state_idx = tl.load(ssm_state_indices + i_n * stride_indices_seq + i_t)
  ```
- **写**（fused_recurrent.py:154-156）：
  ```python
  final_state_idx = tl.load(ssm_state_indices + i_n * stride_indices_seq + i_t)  # i_t = range(0,T) 写循环变量
  ```

GPU 读写都用 `i_n(行) * stride + i_t(列)`，读列=`num_accept-1`、写列=`local_t`。**文档对"Ascend 写路径用全局 `seq_i`、缺 `batch_i` 行偏移 → 多 req+短 uql 写错行"的判断，逻辑成立。修复方向正确。**

### 1.2 触发条件判断准确

文档表格"单 req 不触发 / 多 req+uql=num_spec+1 不触发 / 多 req+uql<num_spec+1 触发"——与 GPU 二维坐标系下"token 绝对下标 ≠ 行优先 flatten 下标"的错位条件一致，✅。

## 二、stride 推导：结果对，但有不严谨处 ⚠️

### 2.1 GPU 的 stride 是张量真实 stride，不是 num_spec+1

本地实测（fused_recurrent.py）：
```python
elif ssm_state_indices.ndim == 1:
    stride_indices_seq, stride_indices_tok = ssm_state_indices.stride(0), 1   # :213
else:
    stride_indices_seq, stride_indices_tok = ssm_state_indices.stride()       # :215
# packed_decode 路径强制 1D：
assert ssm_state_indices.ndim == 1  # :367-369
stride_indices_seq = ssm_state_indices.stride(0)   # :446
```

**GPU 用 `.stride(0)`，不是 `num_spec+1`。** 文档 host 侧用 `indices_len / B` 推 stride：
- 常规：2D `[num_spec_decodes, num_spec+1]` 行优先 flatten 成 1D，长度 = `num_spec_decodes*(num_spec+1)`，`/B = num_spec+1`，**数值上等于行宽，正确**。
- **但这是"连续张量行宽 = stride(0)"的巧合**。若 `spec_state_indices_tensor` 被切片/非连续（如某些 cudagraph padding 路径），`indices_len/B` 可能 ≠ 真实行 stride。

> **建议**：host 侧 stride 应优先从 `ssm_state_indices` 的真实 shape 行宽（即 `num_spec+1`，等于 `spec_state_indices_tensor.size(-1)`）取，而非 `len/B` 反推——`len/B` 在 B 统计口径（含/不含 padding req）与 indices 长度口径不一致时会算错。⚠️ **这是一个潜在的隐性 bug**：cudagraph 下 `indices_len` 是 padding 后的 `batch_size*(num_spec+1)`，但 `B = num_spec_decodes`（真实），`len/B ≠ num_spec+1`！见 §三-③。

## 三、可能遗漏的独立精度 Bug（文档未覆盖，本地坐实风险）

> 这些是"问题 A 修复后仍可能精度异常"的候选。按风险排序。

### ③-A. conv_state 走完全不同的 kernel 和索引，文档明确未改 — 🔴 高风险

文档 §8.1 自己写明"conv1d custom op：独立索引路径，不在本次范围"。但 conv_state 同样参与 GDN 精度，且它的索引方式**和 ssm 不同**：

```python
# qwen_gdn_linear_attn.py — conv_state 用 [:, 0]（只取 slot 0）+ num_accepted + max_query_len
conv_state_indices=spec_state_indices_tensor[:, 0][: num_spec_decodes]   # :1350
num_accepted_tokens=num_accepted_tokens                                  # :1353
max_query_len=spec_state_indices_tensor.size(-1)                         # :1355
```
GPU causal_conv1d kernel 内部用 `conv_state_indices_ptr + idx_seq * stride_cache_indices + conv_state_init_index`（[causal_conv1d.py:133](vllm/vllm/model_executor/layers/mamba/ops/causal_conv1d.py)）。

> **风险判断**：Ascend 侧的 conv1d custom op 是否也按"多 req + 动态 uql"正确取 conv_state_indices？问题 A 文档**完全没碰这个 kernel**。**如果 Ascend conv1d 也有类似的 batch_i 行偏移缺失，那么修了 ssm 仍会因 conv_state 错位而精度异常。** 这是最可能的"遗漏 bug"。🔴 **强烈建议优先排查 Ascend conv1d update 的 state_indices 取址。**

### ③-B. NULL_BLOCK_ID 写守卫缺失 — 🟠 中风险（cudagraph 下）

GPU 写 state 有守卫（fused_recurrent.py:158）：
```python
if final_state_idx > 0:    # 跳过 NULL_BLOCK_ID(=0) padding 块才写
```
读也有（:114 `if state_idx <= 0: continue`）。

cudagraph 分支会 padding：`spec_state_indices_tensor[num_spec_decodes:].fill_(NULL_BLOCK_ID)`（[gdn_attn.py:426](vllm/vllm/v1/attention/backends/gdn_attn.py)）。

> **风险判断**：问题 A 文档的 Ascend 修复（修改 5/6）用 `GetValue(stateFlatIdx)` 取块后**直接读/写，未见 NULL_BLOCK_ID(0) 守卫**。若 Ascend 走 cudagraph 且取到 padding 块（block id=0），会**读/写物理块 0（脏数据/越界）**。🟠 需确认 Ascend 是否走 cudagraph + 是否有等价守卫。

### ③-C. host stride 在 cudagraph padding 下算错 — 🟠 中风险

承 §2.1：文档 host 用 `ssmStateIndicesStride = indices_len / B`（fix.md §8a:486）。
- cudagraph 下 `ssm_state_indices` 被 padding 到 `batch_size*(num_spec+1)`（gdn_attn.py:422 copy 到固定 buffer），而 `tilingData_.b` 是 `cuSeqlensShape - 1` = **真实 spec req 数**（不含 padding）。
- 则 `indices_len / b = batch_size*(num_spec+1) / num_spec_decodes ≠ num_spec+1`（当 batch_size > num_spec_decodes，即有 padding 时）→ **stride 算错 → 所有行偏移错**。

> **风险判断**：🟠 若 Ascend 也走 cudagraph，文档的 `len/B` stride 推导会在 padding 时失效。**修正应直接用 `num_spec+1`（= indices 张量的行宽），不用 len/B 反推。** 文档 §8a 注释提到"单测 per-token arange"用 len/B 也对，但**漏分析了 cudagraph padding 这一路径**。

### ③-D. uql 缩短时上一步 commit slot 与本步写 slot 不对齐 — 🟡 待坐实（即"问题 B"残留）

文档 §8.2.1 自己列了："上步 commit 在 slot 3，本步 uql=2 只写 slot 0、1；若上步 state 未在 slot 0/1，可能需要 preprocess 对齐。"

> **风险判断**：这正是我前几轮分析的"跨 step state 延续"问题（[[20260625-003658-...]] 的 align kernel 对齐截断）。问题 A（同 step 内行错位）和这个（跨 step slot 对齐）是**两个独立问题**。🟡 **问题 A 修复不解决跨 step 的 commit-slot 对齐**，这可能是另一半精度异常来源。需结合 preprocess（mamba_utils.py 的 state 拷贝）一起看。

### ③-E. num_accepted 上界检查从 `<= uql` 改 `<= stride` 的副作用 — 🟡 待坐实

文档修改 5 把上界从 `num_accept <= seqLen(uql)` 改成 `<= ssmStateIndicesStride(num_spec+1)`。
- GPU 侧：`i_t = num_accept - 1`，读 `i_n*stride + i_t`——只要 `num_accept <= num_spec+1` 就不越行。文档改对了方向。
- **但**：若某 req 上一步是 mtp3、本步 uql=2，`num_accept` 可能来自上一步（=3），此时 `num_accept-1=2 > uql-1=1`，读到 slot 2——**slot 2 在本步是否有有效 state？** 取决于本步是否写了 slot 2（uql=2 只写 slot 0/1）。🟡 这与 ③-D 同源，需确认 num_accepted 的 step 归属。

## 四、完整判断与建议

### 4.1 修复建议准确性

- **问题 A 的定位与修复：准确、必要、方向正确** ✅。读写统一 `batch_i*stride+local_slot` 对齐 GPU，是对的。
- **但"完全解决精度异常"不能下结论** ❓——问题 A 只是 ssm recurrent kernel 的索引，精度异常大概率是**多 bug 叠加**。

### 4.2 必须补排查的遗漏点（按优先级）

| 优先级 | 遗漏点 | 为什么 |
|--------|--------|--------|
| 🔴 P0 | **③-A conv_state（causal_conv1d）索引** | 独立 kernel、文档明确未改、同样有多 req 错位风险，最可能是残留 bug |
| 🟠 P1 | **③-C host stride 在 cudagraph padding 下算错** | `len/B` 推导在 padding 时失效，应改用 `num_spec+1` 行宽 |
| 🟠 P1 | **③-B NULL_BLOCK_ID 写守卫** | cudagraph padding 块需跳过，否则写脏块 |
| 🟡 P2 | **③-D/E 跨 step commit-slot 对齐 + num_accepted step 归属** | 同步调度下也出错的另一半根因，问题 A 不覆盖 |

### 4.3 验证建议（在文档 §9 基础上补充）

1. **conv vs ssm 分离验证**：单独 disable ssm（或固定 conv）压测，定位精度异常来自 conv 还是 ssm——区分 ③-A 是否成立。
2. **cudagraph on/off 对比**：若 cudagraph off 精度正常、on 异常，则 ③-B/③-C（padding 相关）成立。
3. **单 req vs 多 req**：文档已建议（问题 A 仅多 req 现）；补充 **单 req + 跨 step uql 切换（mtp3→mtp1）**，若单 req 也异常 → 是 ③-D/E（跨 step），非问题 A。
4. **逐 kernel bit-exact 对拍 GPU**：ssm recurrent、conv1d update 各自与 GPU 输出对拍，定位哪个 kernel 偏离。

## 五、待核实/存疑（服务器侧代码无法直读，明确标注）

1. **Ascend conv1d custom op 的 state_indices 取址**（③-A）：是否同样缺 batch_i 行偏移 —— 服务器代码，需对方核对。最高优先级。
2. **Ascend 是否走 cudagraph**（③-B/③-C）：决定 NULL 守卫与 padding stride 是否成立。
3. **Ascend 写路径是否有 NULL_BLOCK_ID(0) 守卫**（③-B）：文档修改 6 未提。
4. **num_accepted_tokens 的 step 归属**（③-D/E）：是当前 step 真实接受数还是上一步残留 —— 影响 commit-slot 对齐，需结合上层 worker 确认。
5. **host stride 实际取值**（③-C）：建议 Ascend 侧打印 `ssmStateIndicesStride` 在 cudagraph 多 req padding 下的值，验证是否 = num_spec+1。
