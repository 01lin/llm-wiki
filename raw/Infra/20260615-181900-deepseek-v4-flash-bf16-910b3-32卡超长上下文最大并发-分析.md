# DeepSeek V4 Flash BF16 + 昇腾 910B3 32 卡超长上下文最大并发分析

> 分析时间：2026-06-15  
> vLLM commit：`0d29612292c6b1e312af42ac00cf649af16a438b`  
> vLLM-Ascend commit：`8afdf356f6a2496bedfc538253366ef1a8c0d9aa`  
> Hugging Face 模型 revision：`553034d7dd9e06c2eeaee68cf85a17d6d4754cf0`  
> 硬件：4 台 Atlas 800 A2，每台 8 张 910B3 64G，共 32 卡  
> 基准场景：BF16 权重、BF16 KV Cache、`block_size=128`、MTP 1 层开启

## 1. 先给结论

### 1.1 结论表

以下结果采用：

- 单卡 `torch.npu` 上报总显存按 **64 GiB** 计算；
- `gpu_memory_utilization=0.9`，每卡可请求 57.6 GiB；
- 权重之外，为激活、HCCL、非 PyTorch 内存和 ACL Graph 暂留 6 GiB；
- `max_num_batched_tokens=8192`；
- `max_num_seqs` 已设置为不低于目标单 lane 并发，不构成额外上限；
- 每个 Data Parallel lane 同时允许一个请求处于最坏 prefill 准入峰值；
- 并发是“已经进入模型执行、KV 可以安全驻留”的请求数，不是 HTTP 排队长度。

| 口径 | 128K | 256K | 512K | 1M | 主要拓扑 |
|---|---:|---:|---:|---:|---|
| **PP=1 静态显存最大值** | **512** | **256** | **128** | **64** | TP1 + DP32 + EP32 |
| **较高并发折中** | **368** | **176** | **96** | **48** | TP2 + DP16 + EP32 |
| **较均衡生产候选** | **208** | **104** | **48** | **24** | TP4 + DP8 + EP32 |
| **按节点组织、通信更简单** | **112** | **56** | **28** | **12** | TP8 + DP4 + EP32 |
| **实验性 PP 极限** | **800** | **400** | **200** | **96** | 128K/256K 用 PP2；512K/1M 用 PP4 |
| **16P + 16D 分离，D 侧驻留上限** | **72** | **32** | **16** | **8** | D 侧 TP2 + DP8 |

最重要的判断：

1. **只追求显存能放下多少请求，当前 PP=1 的最大值是约 512/256/128/64。**
2. **TP1 + DP32 并不等于吞吐最好。**每层的 Expert Parallel all-to-all 跨 32 卡，且每个请求的稠密 Attention 只在单卡执行，通信和单请求算力都可能成为瓶颈。
3. **更建议把 TP2 + DP16 作为高并发起点，把 TP4 + DP8 作为吞吐和并发更均衡的起点。**
4. **Pipeline Parallel 能把 KV 层分片，源码推导上限可到 800/400/200/96；但支持矩阵没有标记 DeepSeek V4 Pipeline Parallel，也没有相应端到端用例，不能直接作为生产承诺。**
5. **PD 分离不会提高 BF16 模型的纯显存并发上限。**32 卡拆成 16P+16D 后，两侧都要复制模型权重，Expert Parallel 规模从 32 降到 16，每卡专家权重约翻倍。
6. 这些数字仍不是机器实测值。最终必须用启动日志中的 `Available KV cache memory` 和 `num_blocks` 替换本文的 6 GiB 运行时预留假设。

### 1.2 如果“64G”实际只上报约 59.6 GiB

部分设备或管理工具把 64 GB 十进制容量上报为约 59.6 GiB。相同假设下，PP=1 的结果会下降为：

| 拓扑 | 128K | 256K | 512K | 1M |
|---|---:|---:|---:|---:|
| TP1 + DP32 | 384 | 192 | 96 | 32 |
| TP2 + DP16 | 288 | 144 | 64 | 32 |
| TP4 + DP8 | 176 | 88 | 40 | 16 |
| TP8 + DP4 | 92 | 48 | 24 | 12 |

因此，**真实容量必须以 `torch.npu.mem_get_info()` 和 vLLM 启动日志为准，不能只看“64G”产品名称。**

## 2. 适用边界和重要风险

### 2.1 官方教程不是 BF16 配方

vLLM-Ascend 的 DeepSeek V4 Flash 教程只给出了：

- `DeepSeek-V4-Flash-w8a8-mtp`；
- A2 单机 8 卡：133,120 token、TP8、DP1、8192 batched tokens；
- A3 配方：1M、TP4、DP4、10240 batched tokens。

源码位置：

- `vllm-ascend/docs/source/tutorials/models/DeepSeek-V4-Flash.md:14-16`
- `vllm-ascend/docs/source/tutorials/models/DeepSeek-V4-Flash.md:147-176`
- `vllm-ascend/docs/source/tutorials/models/DeepSeek-V4-Flash.md:196-224`

因此，本文的 BF16 结论是：

> 基于 Hugging Face 权重结构和 vLLM/vLLM-Ascend BF16 执行代码做的容量推导，不是官方 BF16 32 卡实测结果。

### 2.2 Hugging Face 原始权重不是完整 BF16 文件

模型索引的原始存储约为 159.61 GB，包含：

- Routed Expert：FP4 打包在 I8 tensor 中；
- 其他大部分线性权重：FP8；
- Norm、Gate、部分 Compressor：BF16 或 FP32。

本文把它展开成 BF16 后估算：

| 模块 | 全局 BF16 等效权重 |
|---|---:|
| 主模型 | 529.693 GiB |
| MTP checkpoint 中的层权重 | 12.314 GiB |
| MTP 模块额外实例化的 embedding + head | 1.973 GiB |
| **总计** | **543.980 GiB** |

### 2.3 BF16 + MTP 当前加载路径需要实机确认

MTP 模型会独立创建：

- `VocabParallelEmbedding`；
- `SharedHead`；
- 一层完整 DeepSeek V4 Decoder/MoE。

依据：

- `vllm_ascend/models/deepseek_v4_mtp.py:56-102`
- `vllm_ascend/models/deepseek_v4_mtp.py:140-160`

但是，目标模型的 `embed.weight` 和 `head.weight` 只在 `quant_config.get_name() == "fp8"` 时映射给 MTP：

- `vllm_ascend/models/deepseek_v4_mtp.py:283-292`

所以真正运行 BF16 + MTP 前必须确认：

1. BF16 转换权重是否包含 `mtp.0.emb.tok_emb.weight` 和 `mtp.0.head.weight`；
2. 或者加载器是否需要补上 BF16 的共享权重映射；
3. 否则关闭 MTP，重新测权重和 KV Cache。

本文为保守起见，仍把 MTP 权重和 MTP KV Cache 全部计入。

## 3. DeepSeek V4 Flash KV Cache 基础结构

### 3.1 Attention 层分布

配置中共有 43 个主模型层：

- Layer 0、1：不压缩的 Sliding Window Attention；
- Layer 2、4、...、42：21 层 Compress-4 Attention；
- Layer 3、5、...、41：20 层 Compress-128 Attention；
- MTP：额外 1 层不压缩 Sliding Window Attention。

即：

| 缓存类型 | 层数 |
|---|---:|
| Sliding Window Attention | 43 主模型层 + 1 MTP 层 |
| Compress-4 主 KV | 21 |
| Compress-4 Index KV | 21 |
| Compress-4 Compressor State | 21 |
| Compress-128 主 KV | 20 |
| Compress-128 Compressor State | 20 |

### 3.2 A2、BF16、block size 128 的页面

vLLM-Ascend 对 A2 定义：

```text
logical block sizes = [128, 128, 8, 32]
page size buckets   = [16,640 B, 131,072 B]
```

源码：

- `vllm_ascend/models/layer/attention/layer.py:31-46`

含义：

- 小页面 16,640 B：Compress-4 Index KV；
- 大页面 131,072 B：Compress-4 主 KV、Compress-128 主 KV、SWA KV 和 State 缓存经过 padding 后共享的大页面槽位。

### 3.3 一个全局 block ID 到底按多少字节计费

DeepSeek V4 planner 先取两个页面桶之和：

```text
16,640 + 131,072 = 147,712 B
```

最长普通 bucket 为 22 个 slot，MTP 再增加 1 个 slot：

```text
num_layer_tuples = 22 + 1 = 23
```

因此，vLLM 用于计算 `num_blocks` 的规划成本为：

```text
bytes_per_global_block_id
  = 147,712 × 23
  = 3,397,376 B
  = 3.240 MiB
```

源码依据：

- `patch_kv_cache_utils.py:204-230`：统计页面桶和 MTP；
- `patch_kv_cache_utils.py:232-233`：`available_memory // bytes_per_block`；
- `patch_kv_cache_utils.py:235-245`：实际生成 tensor。

还可以区分三种口径：

| 口径 | 每 global block ID |
|---|---:|
| planner 计费 | 3,397,376 B |
| 实际 tensor 槽位，包括一个空小页槽 | 3,380,736 B |
| 有效非空层槽位 | 3,364,096 B |

并发上限必须用第一行，因为 `num_blocks` 就按第一行取整。

## 4. 单请求在四种上下文下占多少 block

令总上下文长度为 `L`。

### 4.1 稳态 decode 驻留

采用保守高水位：

```text
P4   = ceil(floor(L / 4) / 128)
P128 = ceil(floor(L / 128) / 128)

request_blocks_stable = P4 + P128 + 11
```

`+11` 是 Sliding Window、Compressor State、边界 block 和 MTP 的固定高水位。

| 上下文 | P4 | P128 | 稳态 block ID | planner 等效显存 | 有效非空页显存 |
|---|---:|---:|---:|---:|---:|
| 128K | 256 | 8 | 275 | 0.870 GiB | 0.862 GiB |
| 256K | 512 | 16 | 539 | 1.705 GiB | 1.689 GiB |
| 512K | 1024 | 32 | 1067 | 3.376 GiB | 3.343 GiB |
| 1M | 2048 | 64 | 2123 | 6.717 GiB | 6.651 GiB |

### 4.2 Prefill 准入峰值

对 `B = max_num_batched_tokens`：

```text
SWA(B)  = min(ceil(L / 128), ceil((127 + B) / 128) + 1)
C4S(B)  = min(ceil(L / 8),   ceil((7 + B) / 8) + 1)
C128S(B)= min(ceil(L / 32),  ceil((127 + B) / 32) + 1)

request_blocks_admission
  = P4 + P128 + 2 × SWA(B) + C4S(B) + C128S(B)
```

当 `B=8192`：

```text
admission - stable = 1408 global block IDs
额外 planner 余量 = 4.455 GiB / DP lane
```

| 上下文 | 稳态 block | prefill 准入 block | prefill 准入 planner 显存 |
|---|---:|---:|---:|
| 128K | 275 | 1683 | 5.325 GiB |
| 256K | 539 | 1947 | 6.160 GiB |
| 512K | 1067 | 2475 | 7.831 GiB |
| 1M | 2123 | 3531 | 11.172 GiB |

当 `B=10240`：

```text
admission - stable = 1760 global block IDs
额外 planner 余量 = 5.569 GiB / DP lane
```

这解释了为什么只用“完整上下文 KV 大小”除显存，会高估正在执行的并发。

## 5. 权重如何影响每卡可用 KV Cache

### 5.1 PP=1 时每卡 BF16 权重

在 32 卡、Expert Parallel 开启时：

- Expert Parallel size = DP × TP = 32；
- 528 GiB 的主模型+MTP routed experts 每卡固定约 16.5 GiB；
- TP 只继续切分 embedding、head、shared expert、`wo_a/wo_b` 等权重；
- `wq_a`、`wkv`、gate 等仍然复制；
- 开启 DSA CP 时，`wq_b` 也使用 `ReplicatedLinear`。

源码：

- Expert 分片：`deepseek_v4.py:371-397`
- Attention TP/复制关系：`deepseek_v4.py:726-788`

权重估算：

| TP | DP | EP | 每卡 BF16 权重 |
|---:|---:|---:|---:|
| 1 | 32 | 32 | 32.480 GiB |
| 2 | 16 | 32 | 26.726 GiB |
| 4 | 8 | 32 | 23.849 GiB |
| 8 | 4 | 32 | 22.410 GiB |

### 5.2 本文的 KV 可用显存假设

```text
K_rank
  = 64 GiB × 0.9
  - weight_memory
  - 6 GiB runtime reserve
```

得到：

| TP | 每卡权重 | 假设可用于 KV 的 K_rank |
|---:|---:|---:|
| 1 | 32.480 GiB | 19.120 GiB |
| 2 | 26.726 GiB | 24.874 GiB |
| 4 | 23.849 GiB | 27.751 GiB |
| 8 | 22.410 GiB | 29.190 GiB |

但 vLLM-Ascend 实际不是使用固定 6 GiB，而是启动时 profile：

```text
available_kv
  = requested_memory
  - weights
  - peak activation
  - non-torch memory
  - estimated graph memory
```

源码：

- `worker.py:280-292`：`total_memory × gpu_memory_utilization`
- `worker.py:336-420`：权重、激活、非 PyTorch、Graph profile
- `worker.py:424-426`：打印 `Available KV cache memory`
- `worker.py:598-635`：warmup 后给出实际权重、激活、Graph 和建议 KV 容量

特别需要注意：

- `worker.py:378-389` 对 DeepSeek V4 compressed attention 跳过 ACL Graph 内存预估；
- Graph 仍会在 KV 分配后 capture；
- 因此本文预留 6 GiB 可能仍偏乐观。

## 6. PP=1 的实际并发推导

### 6.1 计算公式

每个 rank 的 global block pool：

```text
pool_blocks = floor(K_rank_bytes / 3,397,376)
```

每个 DP lane 的稳态并发：

```text
C_resident_lane = floor(pool_blocks / request_blocks_stable)
```

允许一个最坏 prefill chunk 的安全并发：

```text
C_safe_lane
  = floor((pool_blocks - admission_delta_blocks)
          / request_blocks_stable)
```

全服务并发：

```text
C_cluster = DP × C_safe_lane
```

### 6.2 结果

`B=8192`：

| 拓扑 | pool blocks/rank | 128K | 256K | 512K | 1M |
|---|---:|---:|---:|---:|---:|
| TP1 + DP32 + EP32 | 6043 | **512** | **256** | **128** | **64** |
| TP2 + DP16 + EP32 | 7861 | **368** | **176** | **96** | **48** |
| TP4 + DP8 + EP32 | 8770 | **208** | **104** | **48** | **24** |
| TP8 + DP4 + EP32 | 9225 | **112** | **56** | **28** | **12** |

`B=10240`：

| 拓扑 | 128K | 256K | 512K | 1M |
|---|---:|---:|---:|---:|
| TP1 + DP32 | 480 | 224 | 128 | 64 |
| TP2 + DP16 | 352 | 176 | 80 | 32 |
| TP4 + DP8 | 200 | 104 | 48 | 24 |
| TP8 + DP4 | 108 | 52 | 24 | 12 |

结论：

- 减小 TP 会增加 DP lane 数量，因此显存驻留并发更高；
- 增大 TP 会降低每卡权重并提高单 lane KV 容量，但 lane 数量下降；
- 对当前压缩 KV 结构，DP lane 数的收益大于 TP 降权重的收益；
- 这只是容量结论，不等于 TP1 的 tokens/s 最高。

## 7. 为什么 TP1 + DP32 不是吞吐最优答案

### 7.1 每个请求只用一张卡做稠密部分

TP1 下：

- Attention 和 shared expert 的稠密矩阵不再跨卡切分；
- 每个 DP lane 的单请求算力只有一张卡；
- 43 层都要执行 Attention 和 shared expert。

### 7.2 每层仍有 EP32 all-to-all

由于 Expert Parallel size 是 DP × TP：

```text
EP = 32 × 1 = 32
```

每个 MoE 层都需要跨 32 卡 dispatch/combine。跨 4 台机器时：

- 小 batch 时通信占比高；
- 请求分布不均时可能出现 Expert 热点；
- TPOT 可能先被 HCCL all-to-all 限制，而不是被 KV 容量限制。

### 7.3 推荐的实际拓扑顺序

建议按以下顺序压测：

1. **TP4 + DP8 + EP32**  
   并发 208/104/48/24，稠密计算仍有 4 卡切分。

2. **TP2 + DP16 + EP32**  
   并发 368/176/96/48，作为更激进的高并发候选。

3. **TP8 + DP4 + EP32**  
   并发 112/56/28/12，最容易按“一台机器一个 TP8 lane”组织。

4. **TP1 + DP32 + EP32**  
   只作为显存极限和高 batch 实验，不作为默认生产结论。

## 8. Pipeline Parallel 的实验性容量上限

### 8.1 为什么 PP 能继续提高并发

DeepSeek V4 主模型实现了 `SupportsPP`，并通过 `make_layers()` 切分 43 层：

- `deepseek_v4.py:1035-1053`
- `deepseek_v4.py:1212`

vLLM 的层划分规则：

- PP2：`[22, 21]`
- PP4：`[11, 11, 11, 10]`
- PP8：`[5, 5, 5, 5, 6, 6, 6, 5]`

源码：

- `vllm/distributed/utils.py:109-145`

KV Cache 配置会：

1. 把全局 KV group 投影到各 PP worker；
2. 每个 PP stage 按本地层数计算 block pool；
3. 最后把所有 rank 的 `num_blocks` 收敛到最小值。

源码：

- `vllm/v1/core/kv_cache_utils.py:1937-1960`
- `vllm/v1/core/kv_cache_utils.py:1994-2000`
- `vllm/v1/core/kv_cache_utils.py:2053-2066`

### 8.2 PP 的 KV tuple 大小

| PP | 最重 stage 层数 | 最重 stage planner bytes/global block ID |
|---:|---:|---:|
| 1 | 43 | 3,397,376 B |
| 2 | 22 | 1,772,544 B |
| 4 | 11 | 1,033,984 B |
| 8 | 6 | 590,848 B |

### 8.3 实验性结果

仍使用 `B=8192`：

| 拓扑 | 128K | 256K | 512K | 1M |
|---|---:|---:|---:|---:|
| PP2 + TP1 + DP16 | **800** | **400** | 192 | **96** |
| PP4 + TP1 + DP8 | 784 | **400** | **200** | **96** |
| PP8 + TP1 + DP4 | 684 | 348 | 176 | 88 |

静态最优组合：

| 上下文 | 最大并发 | 拓扑 |
|---|---:|---|
| 128K | **800** | PP2 + TP1 + DP16 |
| 256K | **400** | PP2 或 PP4 |
| 512K | **200** | PP4 + TP1 + DP8 |
| 1M | **96** | PP2 或 PP4 |

### 8.4 为什么它只能叫“实验性”

1. 支持矩阵中 DeepSeek V4 Flash 的 Pipeline Parallel 列为空：
   - `docs/source/user_guide/support_matrix/supported_models.md:18-20`
2. 当前仓库没有 DeepSeek V4 + PP 的端到端测试配置。
3. MTP 模型虽然声明 `SupportsPP`，但会在每个 worker 上创建完整的 MTP 层、embedding 和 head：
   - `deepseek_v4_mtp.py:140-160`
   - `deepseek_v4_mtp.py:200-208`
4. PP2/PP4 会引入 pipeline bubble 和跨 stage hidden-state 通信。
5. TP1 仍然存在单卡稠密算力不足和 EP all-to-all 问题。
6. PP2 的 128K 上限需要每 lane 约 50 个 sequence；PP4 的 128K 上限需要每 lane 约 98 个 sequence。调高 `max_num_seqs` 会扩大 activation、调度 metadata 和 ACL Graph 开销，可能使 6 GiB runtime reserve 不再成立。

所以：

> 96 个 1M 请求是代码结构和静态显存推导的实验上限，不是当前仓库已经验证的 910B3 生产能力。

## 9. Decode Context Parallel 为什么没有计入最终上限

### 9.1 源码看起来本应能节省 KV

上游 Full Attention 会把每 rank 的最大上下文除以：

```text
DCP × PCP
```

源码：

- `vllm/v1/kv_cache_interface.py:226-234`

Ascend 的压缩 MLA 也做了相同处理：

- `patch_kv_cache_interface.py:187-195`

Ascend 还专门允许 DeepSeek V4 多 KV group 使用 Context Parallel：

- `patch_kv_cache_utils.py:27-56`
- `patch_kv_cache_coordinator.py:154-164`

而 DCP 不增加 world size，只复用 TP rank：

- `vllm/config/parallel.py:331-334`
- `vllm/config/parallel.py:490-499`

如果完整可用，DCP 会是最有效的 KV 并发优化。

### 9.2 当前版本的阻断点

DeepSeek V4 的 Sliding Window cache 使用 `AscendSlidingWindowMLASpec`，它继承上游 `SlidingWindowSpec`：

- `patch_kv_cache_interface.py:215-230`

但 `SlidingWindowSpec.max_memory_usage_bytes()` 仍然有：

```python
assert decode_context_parallel_size == 1
```

源码：

- `vllm/v1/kv_cache_interface.py:510-519`

Ascend 的 `AscendSlidingWindowMLASpec` 没有覆盖这个方法。因此 DeepSeek V4 的 hybrid KV group 在启动容量检查阶段仍可能被该断言阻断。

### 9.3 优化可行性

要让 DCP 真正成为 DeepSeek V4 的容量放大器，需要：

1. 为 `AscendSlidingWindowMLASpec.max_memory_usage_bytes()` 增加 DCP/PCP 感知；
2. `max_admission_blocks_per_request()` 使用有效 block size：

```text
block_size_effective = block_size × DCP × PCP
```

3. 对 SWA 回收、prefix cache hash alignment、MTP last-block drop 做一致性测试；
4. 增加 DeepSeek V4 的 DCP2/DCP4/DCP8 端到端用例；
5. 验证 KV tensor 实际是否按 DCP rank 均匀分片。

在修复前，本文不把 DCP 理论收益计入最大并发。

## 10. PD 分离为什么不是显存最大方案

### 10.1 BF16 下基本只能 16P + 16D

完整展开后的模型约 544 GiB。8 张 64G 卡即使不考虑运行时开销也无法安全部署完整 BF16 模型。

同时 routed expert 数为 256，Expert Parallel size 需要满足专家均匀切分。32 卡拆分时，最自然且可容纳 BF16 权重的方案是：

```text
16 cards for Prefill
16 cards for Decode
```

### 10.2 拆分后每卡专家权重翻倍

混部 32 卡：

```text
routed expert per rank = 528 / 32 = 16.5 GiB
```

16 卡一侧：

```text
routed expert per rank = 528 / 16 = 33 GiB
```

每卡留给 KV 的空间显著下降。

### 10.3 D 侧驻留与 P 侧准入

16 卡一侧、64 GiB 上报、6 GiB runtime reserve：

| 侧内拓扑 | D 侧稳态驻留：128K/256K/512K/1M | P 侧 B8192 准入安全并发 |
|---|---|---|
| TP2 + DP8 | 72 / 32 / 16 / 8 | 32 / 16 / 8 / 0 |
| TP4 + DP4 | 48 / 24 / 12 / 4 | 28 / 12 / 8 / 4 |
| TP8 + DP2 | 28 / 14 / 6 / 2 | 18 / 8 / 4 / 2 |

因此 1M 推荐至少：

- P 侧：TP4 + DP4，可同时准入约 4 个最坏 prefill；
- D 侧：TP2 + DP8，可驻留约 8 个完整 1M 请求。

这远低于 32 卡混部 PP=1 的 64，和实验性 PP 的 96。

PD 分离的价值主要是：

- 隔离 prefill 对 decode TPOT 的干扰；
- 独立扩缩 P/D 资源；
- 结合 Mooncake/Ascend Store 做 KV 迁移和复用；
- 提高 SLO 稳定性。

它不是这组固定 32 卡资源下的显存并发最大方案。

## 11. 并发数字不等于吞吐数字

### 11.1 1M decode 的 KV 读取量仍然很大

虽然驻留 KV 只有约 6.65 GiB/请求/rank，但 decode 每生成一个 token，需要读取：

- 21 层 Compress-4 历史主 KV；
- 21 层 Compress-4 index KV；
- 20 层 Compress-128 历史 KV；
- 44 层 Sliding Window 的近期窗口；
- Compressor State。

前序源码分析得到，1M 时每个 decode token 的主要 KV 读取量约为：

```text
约 900 MB/token/rank
```

所以高并发时，TPOT 很可能先受 HBM 带宽、DSA kernel 和 all-to-all 限制，而不是先受 KV 容量限制。

### 11.2 生产并发建议留出 15% 到 25% 余量

静态表是整数 block 极限。生产建议：

```text
production_concurrency
  = floor(static_safe_concurrency × 0.75 ~ 0.85)
```

例如：

| 拓扑 | 1M 静态安全并发 | 建议初始生产并发 |
|---|---:|---:|
| TP2 + DP16 | 48 | 36 到 40 |
| TP4 + DP8 | 24 | 18 到 20 |
| TP8 + DP4 | 12 | 9 到 10 |
| PP2/PP4 实验路径 | 96 | 先从 48 以下验证 |

## 12. 如何用实际启动日志替换本文假设

### 12.1 最可靠的容量公式

对 PP=1：

```text
pool_blocks_rank
  = floor(Available_KV_Cache_Memory_Bytes / 3,397,376)

safe_concurrency_cluster
  = DP × floor(
      (pool_blocks_rank - prefill_delta_blocks)
      / request_stable_blocks
    )
```

其中：

| B | prefill_delta_blocks |

| 2048 | 352 |
| 4096 | 704 |
| 8192 | 1408 |
| 10240 | 1760 |

## 13. 建议的实验矩阵

### 第一阶段：确认静态容量

固定：

- BF16；
- MTP 1；
- `block_size=128`；
- `gpu_memory_utilization=0.9`；
- `max_num_batched_tokens=8192`；
- `max_num_seqs` 大于目标并发；
- 关闭 prefix caching，先测纯驻留容量。

测试：

| 组 | TP | DP | PP | 目标 |
|---|---:|---:|---:|---|
| A | 8 | 4 | 1 | 节点内 TP 基线 |
| B | 4 | 8 | 1 | 均衡候选 |
| C | 2 | 16 | 1 | 高并发候选 |
| D | 1 | 32 | 1 | 静态显存极限 |
| E | 1 | 16 | 2 | PP 实验 |
| F | 1 | 8 | 4 | PP 实验 |

### 第二阶段：确认可执行并发

对每个上下文长度：

1. 从表中 50% 并发开始；
2. 每次增加 10%；
3. 连续运行 30 分钟；
4. 要求无 OOM、无永久 waiting、无异常 preemption；
5. 记录 p50/p95/p99 TTFT 和 TPOT；
6. 当 TPOT p99 超过 SLO，即使显存还能放，也停止增加并发。

### 第三阶段：Agentic workload

使用：

- 128K 到 1M 的共享系统提示词；
- 32 到 256 轮交互；
- 每轮新增 512 到 4096 token；
- 70% 可复用前缀；
- 30% 分支或工具调用；
- 1 到 4 个并行 tool result 回填。

对比：

1. 无 prefix cache；
2. 本地 prefix cache；
3. Mooncake/Ascend Store 远端 KV；
4. PD 混部；
5. 16P+16D。

## 14. 最终建议

### 如果目标是最大显存并发

先验证：

```text
TP1 + DP32 + EP32 + PP1
```

静态 prefill-safe 上限约：

```text
128K: 512
256K: 256
512K: 128
1M:    64
```

但必须接受跨 32 卡 Expert Parallel 通信和单卡稠密计算风险。

### 如果目标是并发和吞吐平衡

优先：

```text
TP2 + DP16 + EP32
```

静态上限：

```text
128K: 368
256K: 176
512K:  96
1M:    48
```

生产初始值建议按其 75% 到 85%。

### 如果目标是更低实施风险

使用：

```text
TP8 + DP4 + EP32
```

每台机器一个 TP8 lane，静态上限：

```text
128K: 112
256K:  56
512K:  28
1M:    12
```

### 如果愿意修改和验证源码

优先级：

1. 修复 DeepSeek V4 SlidingWindowMLASpec 的 DCP 容量计算；
2. 增加 DeepSeek V4 DCP2/4/8 端到端测试；
3. 验证 PP2/PP4 + MTP 的权重加载、KV group 投影和 pipeline 调度；
4. 再评估 DCP 与 PP 联合后的新上限。

从“投入产出比”看，**完整打通 DCP 比继续堆 DP 更有价值**：它可以减少 TP rank 之间的 KV 重复，同时不增加 DCP world size。
