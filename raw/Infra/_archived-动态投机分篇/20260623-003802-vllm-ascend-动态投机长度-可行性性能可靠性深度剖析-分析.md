## 0. 三维度结论速览

| 维度 | 结论 | 置信度 | 依据 |
|------|------|--------|------|
| **精度（可行性）** | ✅ **可保证逐 token 比特级一致** | 高（代码铁证） | rejection sampler 原生支持 per-request 变长草稿（`num_draft_tokens` + `PLACEHOLDER_TOKEN_ID`），只要 `k_active ≤ K_max ≤ MAX_SPEC_LEN` |
| **性能（图模式）** | ⚠️ **需修正方案**：减小 k_active 会改变 query 长度 → 掉出已捕获的 FULL 图。必须用「padding 到 1+K_max」或「分桶捕获多 query 长度」补救 | 中（发现真实约束） | `BatchDescriptor` 无独立 query_len 字段，按 `num_tokens=(1+K)×num_reqs` 编码；uniform_decode 判定要求 `==uniform_decode_query_len` |

## 1. 性能效率剖析（重点：图模式 + 异步遮掩）

### 1.1 图模式（ACL Graph / CUDA Graph）的真实约束

**核心机制**（实测）：投机长度通过 `uniform_decode_query_len = 1 + num_speculative_tokens` 影响图捕获，而图的分发 key 是 `BatchDescriptor`。

- `BatchDescriptor` 字段只有 `num_tokens` / `num_reqs` / `uniform`（[forward_context.py:37](file:///Users/linyi/code/Documents/code/vllm/vllm/forward_context.py)~[43](file:///Users/linyi/code/Documents/code/vllm/vllm/forward_context.py)）——**没有独立的 query_len 字段**。投机长度通过 `num_tokens = uniform_decode_query_len × num_reqs` 这个**乘积间接编码**。
- dispatcher 在初始化时按 `uniform_decode_query_len`（=`1+K`）注册 FULL 图的 key（[cudagraph_dispatcher.py:211](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/cudagraph_dispatcher.py)~[231](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/cudagraph_dispatcher.py)）：`max_num_tokens = uniform_decode_query_len × max_num_seqs`，只对 `capture_size ∈ [uniform_decode_query_len, max_num_tokens]` 建图。
- dispatcher 注释明确："the keys stored in dispatcher are the **only source of truth** for valid cudagraph"（[cudagraph_dispatcher.py:23](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/cudagraph_dispatcher.py)）——运行时 key 不在集合里就 pass through（无图）。
- runner 的 uniform_decode 判定（[model_runner_v1.py:2864](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)~[2868](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)）：必须 `max_num_scheduled_tokens == self.uniform_decode_query_len` 且 `num_tokens == max_num_scheduled_tokens × num_reqs` 才判 uniform decode、走 FULL 图。

### 1.2 capture 路径如何固化 query 长度

`_dummy_run`/capture 里（[model_runner_v1.py:3332](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)）：
```
max_query_len = self.uniform_decode_query_len if uniform_decode else num_tokens   # =1+K（固定）
num_reqs = cdiv(num_tokens, max_query_len)
num_scheduled_tokens_list = [max_query_len] * num_reqs   # 每 req 的 query 长度 = 1+K
```
注释也写死了（[model_runner_v1.py:3326](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)~[3327](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)）："speculative decode, where `max_query_len == 1 + num_spec_decode_tokens`"。**捕获的 FULL decode 图，每个 req 的 query 长度是固定的 `1+K`**。

### 1.3 ★ 关键修正：原方案"减小 k_active 无劣化"不严谨

> 原方案（[[20260623-000214-vllm-ascend-动态投机长度-第一阶段方案设计-分析]] §2.4/§4）判断"预留 K_max、运行时 k_active<K_max 时 draft 循环少跑几步即可、无劣化"。**这在 proposer buffer 维度成立，但在图模式维度不成立**——遗漏了 query 长度变化导致掉图。

精确的因果链：
1. 若 proposer 真的只跑 `range(k_active)` 步，则该 req 的 **decode query 长度变成 `1+k_active`**（verify 1 + 草稿 k_active）。
2. 主模型 verify 前向的 `max_num_scheduled_tokens` = `1+k_active` ≠ `uniform_decode_query_len`(=`1+K_max`)。
3. uniform_decode 判定 false（[model_runner_v1.py:2867](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)）→ **掉出 FULL decode 图** → 走 piecewise 或 eager → **TPOT 劣化**（与"无劣化"硬要求冲突）。

**这是原方案必须修补的漏洞。** 两种修补方案：

| 方案 | 做法 | 优点 | 代价 |
|------|------|------|------|
| **A. Padding 到 1+K_max（推荐）** | 主模型 verify 始终按 `1+K_max` 的 query 长度跑（不足的草稿位用 PLACEHOLDER 填充），rejection sampler 只接受前 `1+k_active` 的有效部分 | 图始终命中 `1+K_max` 桶，无掉图；只捕获一档图，显存/启动成本低 | verify 前向算了 `K_max−k_active` 个无效草稿位（设备算力浪费，但 batch=1 小 batch 下 query 维度算力本就不饱和，浪费有限） |
| **B. 分桶捕获多 query 长度** | 对每个可能的 `k_active`（1..K_max）都捕获一档 `1+k` 的 FULL 图，运行时按 k_active 选对应图 | 无算力浪费，每档都是紧致图 | 图数量 ×K_max，显存与启动 capture 时间显著上升；且需改 dispatcher 注册多档 `uniform_decode_query_len` |

> **推荐 A**：极致时延场景 batch 小、query 维度算力不饱和，"多算几个 PLACEHOLDER 草稿位"的设备开销远小于"掉出 FULL 图"的 host 开销。且 A 不改 dispatcher 的 key 体系（只需保证 verify query 恒为 `1+K_max`），与上游解耦更干净。**这是修正后方案的核心设计点。**

### 1.4 异步调度遮掩（async scheduling）的兼容性

**机制**：execute_model 前向 launch 后返回 None，调度器即可排下一步，CPU 调度与 NPU 前向重叠（见 [[20260614-164853-vllm-vllm-ascend-三模块下钻-Scheduler闭环-DSA-execute-model-分析]] 模块 C）。

与投机长度的耦合点（实测）：
- async + spec 时有条件 `deepcopy(scheduler_output)`（[model_runner_v1.py:1955](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)~[1965](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)）：当 `use_async_scheduling and num_spec_tokens and _draft_token_ids is None`。
- **跨步草稿状态 `prev_num_draft_len`**（[model_runner_v1.py:1971](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)~[1985](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)）：记录每个 req 上一步排了几个草稿，`_update_states` 依赖它；已有防护——若 req 不在 `prev_req_id_to_index` 则 `prev_num_draft_len = 0` 兜底（避免 KeyError）。

**对热切换的影响判断**：
- async 遮掩本身**不依赖投机长度恒定**——它遮掩的是"CPU 调度 vs NPU 前向"，与本步排几个草稿无关。**k_active 切换不破坏遮掩效果**。
- 但 `prev_num_draft_len` 是**跨步状态**：上一步用 k=8 排草稿、本步切 k=3，`_update_states` 用 `prev_num_draft_len=8` 处理上一步遗留、用本步 k=3 排新草稿——只要切换在调度步边界（§可靠性），这个跨步状态天然正确（它本就是"上一步实际值"，不是"配置常量"）。
- **结论**：async 遮掩可兼容；切换的跨步一致性靠"边界锁存 + prev_num_draft_len 用实际值"保证，现有代码结构已支持。

### 1.5 性能效率小结

| 机制 | 是否兼容 | 关键动作 |
|------|---------|---------|
| FULL decode 图 | ⚠️ 需 padding 到 1+K_max（修正点） | verify query 恒 `1+K_max`，rejection 只取有效部分 |
| async 调度遮掩 | ✅ 兼容 | 切换边界锁存；prev_num_draft_len 用实际值 |
| DSA 多流 prolog / mc2 | ✅ 不受影响 | 与投机长度正交 |
| weight prefetch | ✅ 不受影响 | 与投机长度正交 |

## 2. 可行性剖析（精度不变 = 输出逐 token 一致）

### 2.1 精度命门：rejection sampler 是否支持变长草稿

**代码铁证**：rejection sampler 用 **per-request 的实际草稿数**驱动，不依赖"全局固定投机长度"。

- `metadata.num_draft_tokens`（[rejection_sampler.py:171](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py)/[313](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py)）：是 **list/tensor**，每个 req 一个值——天然支持每个 req 草稿数不同。
- `metadata.max_spec_len`（[rejection_sampler.py:119](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py)）：`assert max_spec_len <= MAX_SPEC_LEN`——只要 `k_active ≤ MAX_SPEC_LEN` 就合法。
- `PLACEHOLDER_TOKEN_ID = -1`（[rejection_sampler.py:30](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py)）：无效/被拒草稿位用占位符，`accepted_tokens[accepted_tokens == PLACEHOLDER_TOKEN_ID] = 0`（[:233](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py)）+ `valid_mask`（[:269](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py)）过滤。

**结论**：rejection sampler 设计上就是"变长草稿 + 占位符填充"——**`k_active` 在 `[1, K_max]` 任意取值，接受/拒绝逻辑都正确，输出与固定 k 比特级一致**。这是可行性最强的一环。

### 2.2 精度为什么不变（投机解码的数学不变性）

投机解码的正确性保证是：**verify 阶段用目标模型 logits 做 rejection sampling，被接受的 token 分布严格等于目标模型直接采样的分布**。这个保证**与草稿数量无关**——草稿多了只是"猜得多、可能接受得多"，草稿少了"猜得少"，但每个被接受的 token 都通过了目标模型的 rejection 检验。

- 接受核算（[scheduler.py:1477](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)~[1490](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)）：`num_accepted = max(len(generated) − num_sampled, 0)`，`num_rejected` 回退 `num_computed_tokens` ——**用的是本步实际 `num_draft_tokens`，不是配置常量**。k_active 变化时此式自动适配。
- 因此**动态 k_active 不改变任何被接受 token 的概率分布** → 输出 token 序列在相同随机种子下逐 token 一致（贪心则完全确定）。

### 2.3 §1.3 padding 方案 A 对精度的影响（需确认点）

方案 A 让 verify 始终按 `1+K_max` 跑、填充 PLACEHOLDER 草稿位。需确认：**填充的无效草稿位经过目标模型前向后，其 logits 不会污染有效位的 rejection 判定**。
- 依据：rejection 是 per-position 独立的，有效位只读自己位置的 logits；PLACEHOLDER 位的 `num_draft_tokens` 不计入该 req 的有效草稿数 → 被 `valid_mask` 过滤。
- **风险等级：低**，但需 Phase 0 用 GSM8K 比特级对拍（动态 k=3 vs 固定 k=3 输出完全一致）实测确认。

### 2.4 可行性小结

| 环节 | 精度安全性 | 依据 |
|------|-----------|------|
| rejection sampler 变长草稿 | ✅ 原生支持 | `num_draft_tokens` per-req + PLACEHOLDER |
| 接受/拒绝核算 | ✅ 用实际草稿数 | scheduler.py:1477 自动适配 |
| 数学不变性 | ✅ 与草稿数无关 | 投机解码本质保证 |
| padding 无效位污染 | ⚠️ 低风险，需对拍 | per-position 独立 + valid_mask |

## 3. 可靠性剖析（长稳运行不宕机）

### 3.1 三条防线（缺一不可）

**防线 1：切换在调度步边界生效（防止单步内状态错位）**
- 风险：verify step 中途改 k → proposer 已按旧 k 排 KV slot、buffer 索引越界或接受核算错位 → assert 失败/IndexError → 宕机。
- 防护：`controller.update(k)` 只置"待生效值"；调度器 `schedule()` 开头锁存本步 `k_active`，本步全程不变。借鉴现有"边界原子性"——`schedule()` 本就是每步原子产出 `SchedulerOutput`。

**防线 2：边界值校验（防止越界访问预留 buffer）**
- 风险：`k_active > K_max` → 访问 `slot_mapping_group[k_active]` 越界（list 只有 K_max 条）→ IndexError 宕机。
- 防护：`controller.update(k)` 强制 `1 ≤ k ≤ K_max`，越界拒绝并告警；`K_max ≤ MAX_SPEC_LEN`（[rejection_sampler.py:119](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py) 的 assert 上限）。

**防线 3：跨步草稿状态清理（防止 KeyError）**
- 风险：切换时 req 的 `prev_num_draft_len` 与新 k 不一致 → `_update_states` KeyError。
- 防护：**现有代码已有此防护**（[model_runner_v1.py:1971](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)~[1985](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)）：req 不在 `prev_req_id_to_index` 时 `prev_num_draft_len = 0` 兜底。方案只需保证切换不引入新的"req 状态与 k 不一致"路径——因 `prev_num_draft_len` 存的是**上一步实际草稿数**（非配置 k），切换天然安全。

### 3.2 长稳运行的额外保障

| 风险点 | 影响 | 缓解 |
|--------|------|------|
| 频繁切换致图反复 miss（若用方案 B 分桶） | 抖动/掉图 | 用方案 A（单图桶）规避；或切换加最小驻留时间（hysteresis） |
| K_max 预留显存 + 长跑显存碎片 | OOM | K_max 取保守上限（≤8）；buffer 一次性预分配（已是 `__init__` 期，[llm_base_proposer.py:208](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/spec_decode/llm_base_proposer.py)），无运行时分配 |
| controller 并发读写 k_active | 数据竞争 | k_active 用单一整数 + 边界锁存（GIL 下整数读写原子）；只在调度步读 |
| 切换瞬间 accept_len 统计抖动 | 监控误判 | 统计按本步实际 k 归一化；第二阶段寻优需感知此点 |
| 与 EPLB / PD 分离 / prefix cache 交互 | 功能矩阵复杂 | 第一阶段显式声明边界（先非 PD、EPLB 静态），仿 TokenSpeed 的 phase 边界 |

### 3.3 可靠性小结

可靠性可达成，**但不是"自动安全"**——依赖三条防线 + 切换驻留时间（hysteresis）。其中防线 3 现有代码已具备，防线 1/2 需方案显式实现。最大可靠性收益来自**选方案 A（单图桶）**：避免了方案 B 频繁切换时的图 miss 抖动，长稳更稳。

## 4. 综合判断与方案修正清单

### 4.1 三维度综合

- **可行性（精度）**：✅ 高置信度可达成。rejection sampler 原生支持变长草稿，数学不变性保证输出一致。唯一需对拍确认的是 padding 无效位不污染（低风险）。
- **性能效率**：⚠️ 可达成"无劣化"，**但必须采纳 §1.3 方案 A（padding 到 1+K_max）**，否则减小 k_active 会掉出 FULL 图导致劣化——这是原方案的修正点。async 遮掩天然兼容。
- **可靠性**：✅ 可达成长稳，依赖三条防线（边界锁存 / 边界值校验 / 跨步状态清理）+ 切换 hysteresis，其中一条已有现成防护。

### 4.2 对原方案的修正清单（必须回写）

1. **§1.3 修正**：明确"减小 k_active"在图模式下不是零成本——采纳 **padding 到 `1+K_max`** 方案，verify query 恒定 `1+K_max`，draft 只填前 k_active 个有效草稿、其余 PLACEHOLDER。
2. **新增可靠性三防线**到实现清单。
3. **新增 Phase 0 验证项**：①（原有）多 query 桶 host 开销 → 改为验证「padding 方案下 k_active=3 是否命中 1+K_max 图、TPOT vs 固定 k=3」；② 精度比特级对拍（动态 vs 固定输出一致）；③ 频繁切换 1h 长稳无 OOM/assert。

### 4.3 修正后的"无劣化"重新论证

采纳 padding 方案 A 后：
- 图：verify 恒按 `1+K_max` 跑 → **始终命中同一 FULL 图，无掉图**。
- 设备算力：verify 前向算 `1+K_max` 个位置（含 `K_max−k_active` 个 PLACEHOLDER）。**这是与"固定 k=K_max"相同的算力**，比"固定 k=k_active"略多——但 batch 小、query 维度不饱和，差异有限。
- draft 阶段：只跑 `range(k_active)` 步草稿前向 → 与固定 k_active 一致。
- **重新结论**：动态 k_active（padding 到 K_max）的 TPOT ≈ **固定 K_max 的 verify 开销 + 固定 k_active 的 draft 开销**。与"固定 k_active"对比，verify 多算 PLACEHOLDER 位（小 batch 下可忽略），draft 持平。**需 Phase 0 实测这个差异是否在 ±2% 验收带内**——这是比原方案更诚实、更精确的判断。

> ⚠️ 诚实标注：修正后"无劣化"的成立**取决于 Phase 0 实测**"verify 多算 PLACEHOLDER 位"的开销是否在验收带内。若 batch 较大致 query 维度饱和、padding 开销显著，则需退回方案 B 或限制 K_max。这是本方案当前最大的不确定点。
