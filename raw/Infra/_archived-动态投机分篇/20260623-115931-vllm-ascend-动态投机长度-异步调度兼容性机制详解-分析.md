## 0. 直接回答（结论先行）

**异步调度提前执行不依赖"一个固定投机长度"，而是依赖三个语义不同的量。动态投机只需对其中一个（KV/占位 list 上限）喂 `K_max`，另两个本就用"本步实际草稿数"——所以天然兼容。**

| 量 | 语义 | 现状是否依赖固定值 | 动态投机喂什么 |
|----|------|------------------|---------------|
| `num_output_placeholders` | async 提前占位的 token 计数 | ❌ **已用本步实际草稿数** | 不用管，自动适配 |
| `spec_token_ids`（占位 list） | 提前排下一步时的草稿占位 | ⚠️ 按固定长度建，但**会被裁剪** | 建 `K_max` 长，运行时裁到 k_active |
| `num_lookahead_tokens` | KV slot 预留量 | ✅ 按固定 num_spec_tokens | 喂 `K_max`（预留够），或每步喂 k_active |

> 一句话：**喂 `K_max` 给"上限类"的量（KV 预留 + 占位 list 长度），让"计数类"的量（placeholders）继续用本步实际值**——异步提前执行的正确性不被破坏。

## 1. 异步调度"提前执行"机制详解（先讲清现状）

### 1.1 为什么需要"提前占位"

async scheduling 的收益来自：`execute_model` 把前向 launch 到 NPU 后**立即 return None**（[model_runner_v1.py:2315](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)~[2335](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)，注释 "without breaking async scheduling"），EngineCore 不等结果就调 `schedule()` 排下一步，让「下一步 CPU 调度/prepare」与「本步 NPU 前向」重叠。

**矛盾**：排下一步时，上一步的 token（含草稿接受结果）**还在 NPU 上算、没回来**。`schedule()` 要决定"这个请求下一步排几个 token、预留多少 KV"，但它不知道上一步实际生成了几个 token（接受了几个草稿）。

**解法**：用 `num_output_placeholders` **乐观占位**——假设上一步会生成"采样 token + 草稿 token"这么多，先按这个数往前排；真实结果回来后再修正。

### 1.2 占位的核心变量：num_output_placeholders

它是 `Request` 的字段（[request.py:141](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/request.py)），表示"已乐观假设会产出、但尚未确认的 token 数"。

**在 schedule() 中参与下一步 token 预算**（[scheduler.py:420](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)~[423](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)）：
```python
num_new_tokens = (
    request.num_tokens_with_spec
    + request.num_output_placeholders   # ★ 把乐观占位算进下一步 token 数
    - request.num_computed_tokens
)
```

### 1.3 占位怎么"加"——关键：用本步实际草稿数

`AsyncScheduler._update_after_schedule`（[async_scheduler.py:19](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/async_scheduler.py)~[42](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/async_scheduler.py)）：
```python
cur_num_spec_tokens = len(spec_decode_tokens.get(req_id, ()))   # ★ 本步实际调度的草稿数
request.num_output_placeholders += (
    self.num_sampled_tokens_per_step + cur_num_spec_tokens       # 采样1 + 实际草稿数
)
request.spec_token_ids = self._spec_token_placeholders          # 占位 list（下节）
```
> **决定性事实**：placeholder 的增量用的是 `cur_num_spec_tokens`（本步实际排的草稿数），**不是固定 `num_spec_tokens` 常量**。这意味着 async 占位机制**本就支持每步草稿数不同**——动态投机在这一层天然兼容。

### 1.4 占位怎么"减"——出 token 时扣回

`AsyncScheduler._update_request_with_output`（[async_scheduler.py:63](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/async_scheduler.py)~[70](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/async_scheduler.py)）：
```python
request.num_output_placeholders -= len(new_token_ids)   # 真实产出几个，就扣几个
assert request.num_output_placeholders >= 0
self.kv_cache_manager.cache_blocks(
    request, request.num_computed_tokens - request.num_output_placeholders)  # KV 缓存指针扣回未确认部分
```
> 真实结果回来后，placeholder 按**实际生成数**扣回。乐观假设与实际的差额（被拒草稿）通过这里 + 接受核算（[scheduler.py:1477](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)）回退指针修正。**整个加减闭环用的都是实际值，不依赖固定投机长度。**

## 2. 三个"投机长度"语义的精确拆分（你问题的核心）

异步提前执行实际用到"投机长度"的地方有三处，**语义不同、对动态投机的要求不同**：

### 2.1 占位计数 num_output_placeholders —— 已动态友好 ✅

如 §1.3/§1.4：用 `cur_num_spec_tokens`（本步实际）加、用 `len(new_token_ids)`（实际产出）减。**不需要固定值，动态投机零改动即兼容。**

### 2.2 草稿占位 list `_spec_token_placeholders` —— 建 K_max，运行时裁剪 ⚠️→✅

构造（[async_scheduler.py:16](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/async_scheduler.py)）：
```python
self._spec_token_placeholders: list[int] = [-1] * self.num_spec_tokens
```
赋值（async_scheduler.py:41）：`request.spec_token_ids = self._spec_token_placeholders`。

**关键：这个占位 list 会被裁剪**（[scheduler.py:548](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)~[551](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)）：
```python
num_scheduled_spec_tokens = num_new_tokens + num_computed_tokens - num_tokens - num_output_placeholders
if len(spec_token_ids) > num_scheduled_spec_tokens:
    spec_token_ids = spec_token_ids[:num_scheduled_spec_tokens]   # ★ 占位 list 超长部分被裁掉
```
> **这是答案的关键**：占位 list **只要够长就行，多余部分按本步实际需求裁掉**。所以动态投机下——**`_spec_token_placeholders` 按 `K_max` 建（[-1]*K_max），运行时自动裁到 k_active**，无需每步重建 list。
>
> 而且这只是个 host 侧 `[-1]` 占位（真实草稿后续由 §2.3 覆盖），裁剪是纯 CPU list slice，无任何同步/分配开销。

### 2.3 真实草稿回填 update_draft_token_ids —— worker 实际产出，长度=k_active ✅

worker 算完草稿后，通过 `update_draft_token_ids` 把**真实草稿**回填（[scheduler.py update_draft_token_ids](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)）：
```python
request.spec_token_ids = spec_token_ids   # worker 实际产出的草稿，长度 = k_active
```
> 占位 list（§2.2）只在"提前排下一步、真实草稿还没回来"的窗口期临时占位；worker 算出真实草稿后即被覆盖。覆盖值长度天然是 k_active（worker 按 [draft 循环 range(k_active)](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/spec_decode/llm_base_proposer.py) 产出）。**动态投机在这一层也天然兼容。**

### 2.4 KV 预留 num_lookahead_tokens —— 唯一需"喂数"的地方

[scheduler.py:220](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)~[231](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py)：`num_lookahead_tokens = num_spec_tokens (+1)`，用于 [allocate_slots](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py) 预留 KV 草稿槽。

**两种喂法**：
- **喂 K_max（推荐，更安全）**：始终按 K_max 预留 KV slot。代价：k_active<K_max 时多预留几个 slot（KV 占用略高），但**绝不会因预留不足导致草稿写越界**。
- 喂 k_active（更省 KV）：每步按实际预留。需保证切换时刻 KV 预留与实际草稿数严格一致，边界复杂。

> **判断**：第一阶段喂 `K_max`（安全优先，KV 多占可接受）；第二阶段寻优时若 KV 紧张再优化为 k_active。这与 [[20260623-100003-vllm-ascend-动态投机长度-实现级设计-分析]] §2.1 的 lookahead 处理对齐。

## 3. 跨步切换的"实际兼容"走查（坐实，非理论）

场景：上一步用 k=8 排草稿，本步 controller 切到 k=3。逐步走真实代码：

| 步骤 | 代码行为 | 是否正确 |
|------|---------|---------|
| t 步排程 | placeholder += 1+8（本步实际排 8 草稿，async_scheduler.py:38）；spec_token_ids = [-1]*K_max 裁到 8 | ✅ 用实际 8 |
| t 步 worker | draft 循环 range(8) 产 8 草稿；update_draft_token_ids 回填真实 8 草稿 | ✅ |
| controller 切 k=3 | latch_for_step() 在 t+1 步 schedule() 开头锁存 k_active=3 | ✅ 边界生效 |
| t+1 步排程 | num_lookahead 按 K_max 预留 KV；本步排 3 草稿（k_active=3）；placeholder += 1+3 | ✅ KV 够（K_max）、占位用实际 3 |
| t 步结果回来 | placeholder -= len(new_token_ids)（t 步实际生成，含接受的草稿）；接受核算用 t 步实际草稿数 8 | ✅ 用 t 步实际 8，非本步 3 |
| t+1 步 worker | draft 循环 range(3) 产 3 草稿 | ✅ |
| prev_num_draft_len | 存 t 步实际草稿数（[model_runner_v1.py:1971](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py)），GPU 修正 kernel 用它 | ✅ 跨步用实际值 |

**为什么实际兼容（核心论点）**：
- placeholder 的加（用本步实际草稿）/减（用实际产出）/接受核算（用 t 步实际草稿）**全程用"那一步的实际草稿数"**，从不假设"所有步草稿数相同"。
- 切换只改"本步排几个草稿"这个 CPU 标量，t 步遗留用 t 步的值处理、t+1 步用 t+1 步的值——**两步的草稿数本来就允许不同**（这是 async 占位机制的固有能力，不是为动态投机新增的）。
- KV 喂 K_max 保证任何 k_active≤K_max 都不会预留不足。

> **结论**：异步调度的提前执行机制**设计上就用"每步实际草稿数"驱动**（placeholder/接受核算/prev_num_draft_len 无一依赖"固定投机长度"常量），唯一按固定值建的 KV 预留和占位 list 喂 `K_max` 即可。动态投机长度**实际兼容**，不是理论推断——代码里 t 步 k=8、t+1 步 k=3 的混合步本就能正确处理。

## 4. 动态投机在异步调度上的设计与实现（落地）

### 4.1 设计原则

1. **不碰 async 的"实际值驱动"内核**：placeholder 加减、接受核算、prev_num_draft_len、update_draft_token_ids 全部不改——它们本就动态友好。
2. **只把"按固定 num_spec_tokens 建的上限"喂 K_max**：`_spec_token_placeholders` 建 `[-1]*K_max`、`num_lookahead_tokens` 按 K_max 预留。
3. **k_active 只控制 worker 侧 draft 循环次数 + verify token 数**（[llm_base_proposer.py:566](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/spec_decode/llm_base_proposer.py)），不进 async 占位逻辑。

### 4.2 实现改动点（异步相关）

| 改动 | 位置 | 内容 |
|------|------|------|
| 占位 list 建 K_max | [async_scheduler.py:16](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/async_scheduler.py) | `[-1] * k_max`（启动期覆写 num_spec_tokens=k_max 即自动生效，见实现级设计 §1.3） |
| lookahead 喂 K_max | [scheduler.py:220](file:///Users/linyi/code/Documents/code/vllm/vllm/v1/core/sched/scheduler.py) | 按 K_max 预留（或每步 k_active，第一阶段用 K_max） |
| draft 循环 k_active | [llm_base_proposer.py:566](file:///Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/spec_decode/llm_base_proposer.py) | `range(k_active)` |

> **关键工程手法**：启动期把 `num_speculative_tokens` 覆写为 `K_max`（实现级设计 §1.3），则 async_scheduler 的 `_spec_token_placeholders` 和 scheduler 的 `num_lookahead_tokens` **自动按 K_max 建**，无需单独改 async_scheduler——动态性完全收敛到 worker 侧 `range(k_active)`。这使异步调度代码**几乎零改动**，兼容性最强、跟随上游成本最低。

### 4.3 验证"实际兼容"的方法

- 开 async scheduling + 动态投机，跑 3↔8 高频切换，对比 async on/off 的遮掩比 → 持平。
- msprof 抓 t 步 k=8、t+1 步 k=3 的混合步，确认无 assert、placeholder 加减平衡、KV 无越界。
- 精度：贪心对拍动态 vs 固定，输出 token 一致。
