## 0. TL;DR

1. **结论先行**：「动态投机长度」在 vLLM/vLLM-Ascend 现有架构下**可行**，但热切换的方向不对称——**减小投机长度几乎零成本可热改；增大投机长度受三类「按投机长度预分配/预捕获」的结构约束**。因此第一阶段的工程正解是「**预留最大投机长度 `K_max`（buffer + graph capture 全按 K_max 建），运行时在 `[1, K_max]` 内动态取 `k_active`**」——这样所有切换都退化成「减小方向」，天然无新增 buffer/重捕获开销，满足「无时延劣化」硬要求。
2. **投机长度的固化面（代码实测）**有三类：① 调度器实例常量（`num_spec_tokens`/`num_lookahead_tokens`，scheduler.py:219-231）；② MTP proposer 的 per-step buffer list 与 draft 循环（llm_base_proposer.py:208-220/566）；③ `uniform_decode_query_len = 1 + num_spec_tokens` 渗透的 graph capture / cos-sin / mc2 容量（model_runner_v1.py:485-486/3332）。
3. **"无劣化"为什么能成立**：`k_active=3` 在 `K_max=8` 预留下运行，draft 循环 `for draft_step in range(k_active)` 只跑 3 步、其余 5 步的 buffer/图槽位闲置不执行——单步设备计算量与「固定 k=3」**完全一致**，host 侧多出的仅是「读一个 `k_active` 变量」的纳秒级开销。预留的 K_max 只增加**显存常驻**（buffer 按 K_max 分配）与**启动期 capture 时间**，不进 decode 热路径。
4. **解耦/插件化**：投机长度的"决策"与"执行"必须分离。决策侧做成独立 `SpecLengthController`（读运行时信号 → 产出 `k_active`），通过 vllm-ascend 的 `additional_config` + `patch/` 机制注入，**不改 vLLM 上游**；执行侧只需在调度器 / proposer / runner 三处把"读 config 常量"改成"读 controller 当前值"——改动点 ≤ 5 处、且都在 vllm_ascend 层，满足"低成本跟随上游版本"。

### 2.4 固化面小结：可热改性矩阵

> ⚠️ **重要修正（2026-06-23 合并自可行性深剖）**：原矩阵把「`uniform_decode_query_len`=1+K 减小方向」标为 ✅ 是**错误的**。图的 dispatch key（`BatchDescriptor`）没有独立 query_len 字段，投机长度按 `num_tokens=(1+K)×num_reqs` 间接编码——减小 k_active 会改变 query 长度、掉出已捕获的 FULL 图。详见 [[20260623-003802-vllm-ascend-动态投机长度-可行性性能可靠性深度剖析-分析]] §1.3，修正方案见本节末与 §3.5。

| 固化点 | 减小 K（k_active<K_max，**含修正**） | 增大 K（超过已建 K_max） |
|--------|------------------------|------------------------|
| 调度器 `num_lookahead_tokens` | ✅ 改实例变量即可（少预留 KV） | ⚠️ 改变量可行，但 KV 预留变多 |
| proposer buffer list（×K） | ✅ 循环少跑，尾部闲置 | ❌ list 条目不够 → 需重建 |
| draft 循环 `range(K)` | ✅ `range(k_active)` | ✅ 但依赖上面 buffer + 图 |
| `uniform_decode_query_len`=1+K（图桶） | ❌→需 padding 修正：直接减小会掉出 FULL 图 → 必须 verify 恒 padding 到 `1+K_max` | ❌ 无对应 capture → miss |
| `draft_token_ids_cpu` 形状 | ✅ 用前 k_active 列 | ❌ 形状不够 |

**顶层设计结论（修正后）**：预留 `K_max`（buffer/图/容量全按 K_max 建）+ 运行时 `k_active∈[1,K_max]`，但**主模型 verify 前向必须恒按 `1+K_max` 的 query 长度跑**（不足草稿位填 `PLACEHOLDER_TOKEN_ID`），使图始终命中同一 FULL 桶；draft 阶段只跑 `range(k_active)` 步。这样：图无掉图、proposer 无重建、精度无损（rejection sampler 原生支持变长草稿）。这是第一阶段"无劣化"可证明的工程基石。

## 3. 整体方案：预留 K_max + 运行时 k_active（解耦三层）

### 3.1 架构分层（决策 / 状态 / 执行 解耦）

```
┌─────────────────────────────────────────────────────────────┐
│ 决策层  SpecLengthController（插件，vllm_ascend 新增）          │
│   - get_active_len() -> int                                   │
│   - update(k)  ← 热切换入口（API / config 热更新 / 第二阶段策略）│
│   - decide(signals)  ← 第二阶段占位，第一阶段返回外部设定值      │
│   经 additional_config={"dynamic_spec":{"k_max":8,"k_init":3}} 注入│
└─────────────────────────────────────────────────────────────┘
              │ get_active_len()（每步读，O(1)）
┌─────────────▼───────────────────────────────────────────────┐
│ 状态层  ForwardContext / 共享只读变量                          │
│   - 把 k_active 放进每步 forward_context（与 attn_metadata 同路）│
│   - 借现有「forward_context 旁路」机制传递（见 e2e 调用栈分析）  │
└─────────────────────────────────────────────────────────────┘
              │
┌─────────────▼───────────────────────────────────────────────┐
│ 执行层  三处把「读 K 常量」换成「读 k_active」                  │
│   ① Scheduler: 排程/接受核算用 k_active（buffer 按 K_max 预留） │
│   ② MTP proposer: draft 循环 range(k_active)                  │
│   ③ Runner: 选 query=1+k_active 对应的已捕获图（K_max 全预捕获）│
└─────────────────────────────────────────────────────────────┘
```

### 3.2 启动期：一切按 K_max 预留（付一次性成本）

- proposer 三组 buffer list、`piece_all_attn_layer_name` 按 **K_max** 建（llm_base_proposer.py:208-220/294 的 `range(K)` → `range(K_max)`）。
- `uniform_decode_query_len` 按 **1+K_max** 设；ACL Graph **对 query=1+K_max 桶做 capture**（model_runner_v1.py:3332 路径）。
- cos/sin（:485）、mc2 容量（:486）、`draft_token_ids_cpu`（gpu_model_runner.py:875）按 K_max 预算。
- 代价：显存常驻 + 启动 capture 时间按 K_max 计（一次性，不进热路径）。

### 3.3 运行时：热切换 = 改一个整数

- `SpecLengthController.update(k)` 把 `k_active` 改成新值（受限 `1 ≤ k ≤ K_max`）。
- 下一个调度步，三处执行层读到新 `k_active`：
  - 调度器按 `k_active` 决定 `num_lookahead_tokens`（少/多预留 KV 草稿槽）与排程 token 预算；
  - proposer draft 循环跑 `range(k_active)`，只用 list 前 `k_active` 条 buffer；
  - **runner 的主模型 verify 前向恒按 query=`1+K_max` 跑（padding 方案）**：不足的 `K_max−k_active` 个草稿位填 `PLACEHOLDER_TOKEN_ID`，使 `BatchDescriptor` 始终命中同一 FULL 图桶；rejection sampler 只接受前 `1+k_active` 有效位（见 §3.5）。
- **无新增 buffer、无重捕获、无重启、无掉图** → 满足"几乎无时延劣化"。

### 3.4 切换时序的正确性边界（借 TokenSpeed 接受长度驱动语义）

热切换必须在**调度步边界**生效，不能在一个 verify step 中途改 k——否则 proposer 已按旧 k 排好 KV slot，接受核算会错位。设计：
- `controller.update(k)` 只置"待生效值"；
- 调度器在 `schedule()` 开头（每步原子）把待生效值锁存为本步 `k_active`，本步全程不变；
- 接受/拒绝核算（scheduler.py:1477-1490，`num_accepted = len(generated) − num_sampled`）用本步锁存的 `k_active` 对应的 draft 宽度。

> 这与 [[20260614-164853-vllm-vllm-ascend-三模块下钻-Scheduler闭环-DSA-execute-model-分析]] 模块 A.3 的"接受长度回退指针"闭环对齐——k 切换只改"本步排几个草稿"，回退指针逻辑不变。

### 3.5 ★ padding 方案（图模式无掉图的核心机制）

源于可行性深剖发现的「减小 k_active 会掉出 FULL 图」约束（[[20260623-003802-vllm-ascend-动态投机长度-可行性性能可靠性深度剖析-分析]] §1.3）。机制：

- **verify query 长度恒定 `1+K_max`**：主模型一次 verify 前向的输入永远是「1 个真 token + K_max 个草稿位」，其中前 `k_active` 个是 proposer 真实草稿、后 `K_max−k_active` 个填 [`PLACEHOLDER_TOKEN_ID`=-1](vscode://file/Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py:30)。
- **图始终命中**：`num_tokens=(1+K_max)×num_reqs` 恒等于捕获时的桶，[uniform_decode 判定](vscode://file/Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py:2867)恒为 true，FULL 图无 miss。
- **精度无损**：rejection sampler 用 per-req 实际 [num_draft_tokens](vscode://file/Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py:171)=`k_active`，PLACEHOLDER 位被 [valid_mask](vscode://file/Users/linyi/code/Documents/code/vllm/vllm/v1/sample/rejection_sampler.py:269) 过滤、不计入接受。
- **代价**：verify 多算 `K_max−k_active` 个无效草稿位（设备算力）。batch 小、query 维度算力不饱和时可忽略；需 Phase 0 实测（§6）。

### 3.6 ★ 零 CPU-NPU 同步约束（保住异步遮掩的硬红线）

vllm-ascend 现有 async spec decode 的去同步机制（实测）：[CPU 侧乐观假设"全接受"、不等设备结果就排下一步，真实接受数在 GPU kernel 用上一步 `valid_sampled_token_count_gpu` 修正](vscode://file/Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py:1048)（`update_num_computed_tokens_for_batch_change`，[:1051](vscode://file/Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py:1051)~[1064](vscode://file/Users/linyi/code/Documents/code/vllm-ascend/vllm_ascend/worker/model_runner_v1.py:1064)，`non_blocking=True`，热路径无 D2H 同步）。

动态投机长度**绝不能破坏这个机制**，设计约束：
- `k_active` 是 **CPU 侧纯整数**，切换决策（`controller`）**不读任何设备张量**——杜绝引入 `.item()/.cpu()/synchronize()`。
- padding 的 PLACEHOLDER 填充在 **CPU 侧 numpy/host buffer 完成**（draft buffer 本就是 host pin_memory），不新增 D2H。
- 接受核算仍走现有 GPU 修正 kernel，`k_active` 只改"本步 draft 宽度"这个 CPU 标量，不进设备同步路径。
- **结论**：方案不引入任何新同步点 → async 遮掩效果与固定投机长度完全一致。

## 4. 「无劣化」的代码级论证（采纳 padding 方案后重新论证）

要证明「动态@k_active=3（K_max=8 预留 + padding）」≈「固定 k=3」，逐项对比单 decode step 的开销：

| 开销项 | 固定 k=3 | 动态 k_active=3 / K_max=8（padding） | 差异 |
|--------|----------|--------------------------|------|
| draft 循环次数 | `range(3)` 3 次草稿前向 | `range(k_active=3)` 3 次草稿前向 | **0** |
| draft attn_metadata 构建 | 3 步 | 3 步（list 前 3 条） | **0** |
| verify 图下发 | query=4 图 | query=9 图（1+K_max，恒命中） | **0**（都命中已捕获图） |
| **verify 设备计算量** | 4 个位置（1+3） | **9 个位置（1+8，含 5 个 PLACEHOLDER）** | **+5 位**（唯一差异） |
| draft 设备计算量 | 3 草稿前向 | 3 草稿前向 | **0** |
| KV 草稿槽预留 | lookahead=3 | lookahead=k_active=3 | **0** |
| CPU-NPU 同步 | 无（async 修正） | 无（§3.6 保证） | **0** |
| host 额外 | — | 读 `k_active` 整数 + CPU 填 PLACEHOLDER | ~µs 级，可忽略 |
| 显存常驻 | 按 k=3 | 按 K_max=8 | 多占显存（不进时延） |
| 启动 capture | query=4 一档 | query=9 一档（单桶，非多桶！） | 持平（padding 方案只需 1 档图） |

**核心论点（修正后）**：唯一进热路径的差异是 **verify 前向多算 `K_max−k_active=5` 个 PLACEHOLDER 位**。draft 阶段、图命中、KV、同步全部持平。

- 为什么这 5 位开销小：极致时延场景 batch 小（≤8），verify 前向的 query 维度（`(1+K_max)×num_reqs`）远未饱和昇腾 Cube/Vector 算力，多算几个 token 位接近"免费"——这与「固定 k=K_max」的 verify 开销相同，而「固定 k=K_max」本就是该模型的常用配置。
- 相比原（错误）论证的进步：原表声称"设备计算量差异 0"是**基于"减小 k 不掉图"的错误前提**；修正后诚实承认"+5 PLACEHOLDER 位"，但论证其在小 batch 下可忽略。

> ⚠️ **唯一待 Phase 0 实测确认点（已收敛）**：verify 多算 `K_max−k_active` 个 PLACEHOLDER 位的开销，在目标 batch 区间（≤8）是否在 ±2% 验收带内。若 batch 增大致 query 维度饱和、padding 开销显著 → 退方案 B（分桶捕获）或限制 K_max。这是本方案当前最大、且唯一的不确定点。注意 padding 方案**只需捕获 1 档图**（query=1+K_max），不存在原方案担心的"多 query 桶图选择 host 开销"问题——该担忧已被 padding 方案消解。

## 6. 分阶段交付与验收

### Phase 0：基线 + 固化面验证（1 周）
- msprof 实测固定 k=3/5/8 的 TPOT、`graph_hit_rate`、`d2h_sync_count`、`accept_len`、KV 占用。
- **验证唯一假设**：K_max=8 预捕获多 query 桶后，k_active=3 的 per-step host 时间是否 ≈ 固定 k=3（§4 ⚠️ 点）。不通过则需优化图选择路径。

### Phase 1：静态预留 + 手动热切换（2-3 周）
- 实现 K_max 预留（buffer list / capture / 容量全按 K_max）。
- 实现 `SpecLengthController` + 手动 `update(k)` API。
- 三处执行层改读 `k_active`，切换在调度步边界锁存。
- **验收红线**：① 动态 k_active=3（K_max=8，padding）vs 固定 k=3，相同并发/数据，TPOT 持平（±2%）；② 3→8→3 热切换不重启、不报错、**输出 token 与固定 k 比特级一致**（贪心对拍）；③ `graph_hit_rate→1.0`，无 capture miss；④ **热路径 `d2h_sync_count` 不增**（vs 固定 k 基线，§3.6 红线）。

### Phase 2（占位，不在本文范围）
- `SpecLengthController.decide(signals)` 自动寻优：按并发、上下文长度、实时 `accept_len` 选最优 `k_active`，最大化加速比。

### 风险与开放问题（对齐 padding 方案后修订）

| 风险 | 影响 | 缓解 |
|------|------|------|
| **verify 多算 K_max−k_active 个 PLACEHOLDER 位** | 可能劣化（唯一不确定点） | Phase 0 实测小 batch 下开销 ≤±2%；超标则限 K_max 或退方案 B（§3.5/§4） |
| 切换中途生效致接受核算错位 | 正确性红线 | 调度步边界锁存（§3.4） |
| 引入 D2H 同步破坏 async 遮掩 | 性能红线 | k_active 纯 CPU 整数、PLACEHOLDER host 侧填充、不读设备张量（§3.6） |
| 频繁切换图抖动 | 抖动 | padding 方案单图桶天然无抖动；加切换最小驻留 hysteresis |
| 调度器 patch 随上游变动 | 维护成本 | 改动收敛、grep 校验、推上游原生支持 |
| K_max 预留的 lookahead 致 KV 占用偏高 | 吞吐 | lookahead 按 k_active 动态算（非 K_max），仅 buffer 按 K_max |
