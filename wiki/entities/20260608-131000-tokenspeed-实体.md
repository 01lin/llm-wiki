# TokenSpeed

**TokenSpeed** (LightSeek Foundation) is a from-scratch LLM inference engine targeting **agentic workloads** (high concurrency, short decode, long context) on **NVIDIA Blackwell** (B200/B300). It aims for "TRT-LLM-level performance + vLLM-level usability." Preview release; reported 540 TPS on Qwen3.5 agentic (B200) vs ~150-200 for [[20260608-122850-vllm-ascend-实体|vLLM-Ascend]] on A3.

## Four-layer architecture
1. **Entrypoint** (Python): AsyncLLM + SMG gateway, `tokenspeed serve`.
2. **Scheduler** (C++ control plane): `Scheduler::NextExecutionPlan()` -> ExecutionPlan; type-safe FSM request lifecycle; RadixTree KV + PageAllocator.
3. **Modeling** (local-SPMD): a static compiler auto-generates collective comm from module-boundary placement annotations (no hand-written TP/PP/EP).
4. **Kernels** (tokenspeed-kernel): KernelRegistry + 3-axis scoring + cache; backends CUDA/TRT-LLM/FlashInfer/DeepGEMM/Triton; plus tokenspeed-mla for Blackwell.

## Key differentiators
- **C++ FSM scheduler**: sub-1ms control-plane latency vs vLLM/SGLang Python schedulers' 5-20ms (GIL-bound). Critical for agentic (many short decodes).
- **Retract**: under GPU memory pressure, asynchronously write a decoding request's KV to host and reload later - avoids vLLM-style preemption recompute. See [[20260608-131200-tokenspeed-vs-vllm-ascend-comparison-来源]].
- **3-level KV** (GPU / host / L3 persistent) indexed by [[20260608-131400-radix-tree-prefix-cache-概念|RadixTree prefix cache]]; HybridPrefixCache co-manages KV + Mamba state.
- **Placement type system + layer compiler**: REPLICATE/SHARD/PARTIAL placements compiled into AllGather/AllReduce/FusedReduceNorm ops.
- **Pluggable kernel registry**: 3-axis (oracle/objective/priority) scoring, REFERENCE/PORTABLE/PERFORMANT/SPECIALIZED/PLUGIN bands, runtime override.
- **tokenspeed-mla**: `fold_sq_factor` decode (fold q_seqlen into num_heads for BMM1 M-dim utilization) + AOT MLA prefill beating TRT-LLM.

## Limits
Preview maturity; narrow HW (Blackwell-first; Hopper/AMD incomplete); P/D disaggregation, EPLB, KV store, VLM, full metrics still WIP; C++ scheduler harder to hack than Python. There is active design work to port it to Ascend ([[20260608-131300-tokenspeed-ascend-self-evolving-loop-design-来源]]) - the recommended path being "reuse vLLM-Ascend kernels + keep TokenSpeed's C++ scheduler."

## Counter-arguments / Data gaps
- 540 vs 150-200 TPS is cross-hardware (B200 vs A3) - not an apples-to-apples engine comparison.
- Public benchmarks are sparse (chunked prefill, etc.); many claims are architectural, not measured.
- TokenSpeed-Ascend is a design proposal, not yet built.
